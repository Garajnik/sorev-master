### ГЛАВА 3. ПРОЕКТИРОВАНИЕ (~20–25 стр.)

**3.1. Разработка архитектуры приложения**

Архитектура — **клиент-сервер** с двумя типами клиентов:
- **Главный судья (десктоп)** — подключается по WebSocket `/ws/mainJudge`; получает обновления счёта и список судей в реальном времени
- **Боковой судья (мобильный)** — подключается по WebSocket `/ws/{judgeName}`; отправляет оценки через REST POST и получает события раунда (participantupd, kicked, roundend)

Сервер FastAPI выполняет роль: хранилища состояния (`ConnectionManager`), маршрутизатора WebSocket-сообщений и статик-сервера для SPA.

Диаграмма компонентов / развёртывания (UML): один хост в ЛВС, N мобильных клиентов по Wi-Fi.

**3.2. Моделирование бизнес-процессов**

- BPMN: поток «Создание раунда → Подключение судей → Ход раунда → Завершение раунда / Тайбрейк»
- Use Case: Главный судья (создать раунд, начать/завершить, отключить судью, просмотреть таблицу), Боковой судья (подключиться, выставить оценку, отменить оценку, тайбрейк)
- Диаграмма последовательностей: отправка оценки от мобильного судьи до обновления таблицы главного судьи

**3.3. Проектирование базы данных**

ER-диаграмма (одна таблица):

```
participants
├── id   INTEGER PRIMARY KEY AUTOINCREMENT
└── name TEXT NOT NULL UNIQUE
```

Участники раунда хранятся в оперативной памяти (`ConnectionManager.participants`), что оправдано краткосрочным характером раунда.

**3.4. Проектирование API**

*REST-эндпоинты:*

| Метод | URL | Назначение |
|---|---|---|
| POST | `/connect_judge` | Сигнал о подключении судьи |
| GET | `/local_ip` | Получить IP-адрес сервера (для QR) |
| GET | `/kick_judge/{judge}` | Отключить судью |
| POST | `/send_score` | Отправить оценку `{color, judge, punch, score}` |
| POST | `/undo_score` | Отменить последнюю оценку |
| POST | `/connect_participants` | Установить участников раунда `{blue, red}` |
| GET | `/participants` | Получить текущих участников |
| GET | `/db/participants` | Список участников из БД |
| POST | `/db/participants` | Добавить участника в БД |
| GET | `/scores` | Получить все оценки текущего раунда |
| POST | `/round_end` | Завершить раунд |
| POST | `/tiebreaker` | Передать голос при тайбрейке |
| WS | `/ws/{judgeName}` | WebSocket-соединение судьи |

*WebSocket-сообщения (сервер → главный судья):*
- `{data: "judgeupd", judges: [...]}` — обновление списка судей
- `{data: "score", score: {color, judge, punch, score}}` — новая оценка
- `{data: "undo", undo: {color, judge, punch, score}}` — отмена оценки

*WebSocket-сообщения (сервер → боковой судья):*
- `{data: "participantupd", participants: [...]}` — обновление участников
- `{data: "kicked"}` — принудительное отключение
- `{data: "roundend"}` — завершение раунда

**3.5. Проектирование пользовательского интерфейса**

Экраны / маршруты:

| Маршрут | Компонент | Описание |
|---|---|---|
| `/` | `NewRoundPage` | Создание раунда: поля «Синий / Красный» с автодополнением из БД |
| `/table` | `TablePage` | Десктоп главного судьи: таблица оценок, таймер, QR, кик |
| `/connect` | `NewJudgePage` | Страница входа бокового судьи: ввод имени |
| `/mobile` | `MobilePage` | Интерфейс бокового судьи: кнопки оценок, undo, тайбрейк |

**3.6. Проектирование клиентских модулей**

- **`MobilePage`**: блоки кнопок по видам ударов (Удар рукой, Удар ногой, Бросок, Замечание, Предупреждение) для синего и красного; бадж со счётчиком нажатий; кнопка Undo; диалоги Kicked / Раунд завершён / Тайбрейк
- **`TablePage`**: заголовок с именами участников; шапка с именами судей и кнопкой kick; таблица строк `[Удар рукой, Удар ногой, Бросок, Замечания, Предупреждение]`; строка «Сумма», строка «Счёт»; итоговый счёт N:M; контролы раунда с таймером
- **`NewRoundPage`**: два `Autocomplete` (MUI) с freeSolo и подгрузкой из `/db/participants`; диалог сохранения новых участников
- **Компоненты**: `ScoreCell`, `ScoreChip`, `ButtonRow`, `SquareButton`, `QRCodeDialog`, `DisconnectDialog`

### ГЛАВА 4. ПРАКТИЧЕСКАЯ РЕАЛИЗАЦИЯ (~25–30 стр.)

**4.1. Структура и организация проекта**

```
sorev-master/
├── backend/
│   ├── main.py          # FastAPI-приложение, ConnectionManager, SQLite
│   ├── participants.db  # База данных участников
│   └── venv/
├── src/
│   ├── App.jsx          # Маршрутизация React Router
│   ├── api/
│   │   └── api.js       # REST-функции (fetch-обёртки)
│   ├── Components/      # Переиспользуемые компоненты
│   └── Pages/           # Страницы приложения
├── dist/                # Production-сборка (Vite build)
├── package.json
└── vite.config.js
```

**4.2. Реализация серверной части (Backend)**

- `ConnectionManager` — in-memory хранилище состояния: словарь `{judgeName: WebSocket}`, ссылка на WebSocket главного судьи, текущие участники
- Инициализация SQLite при старте (`init_db()`)
- Маршруты FastAPI: REST для оценок и участников, WebSocket-эндпоинт `/ws/{judgeName}`
- Обработка дублирующихся подключений: закрытие с кодом 4001
- `fastapi-offline` обеспечивает работу Swagger UI без CDN
- Определение IP-адреса сервера через `socket.connect("8.8.8.8", 80)` для генерации QR-кода

**4.3. Реализация клиентской части (Frontend)**

- React 18, функциональные компоненты с хуками (`useState`, `useEffect`, `useRef`, `useMemo`)
- WebSocket-соединение устанавливается в `useEffect` и закрывается при размонтировании
- В `TablePage`: `judgesDictRef` (useRef) как «живой» словарь `{judgeName → judgeKey}`, чтобы обработчик WebSocket всегда видел актуальный маппинг без создания новых подписок
- Алгоритм подсчёта очков: суммирование числовых оценок, обработка `"H"` суффикса (нокдаун = базовый балл + 3), добавление штрафных очков соперника
- `MobilePage`: локальный `localScoresRef` для определения тайбрейка при `roundend` без запроса к серверу

**4.4. Работа с базой данных**

- Таблица `participants` с ограничением `UNIQUE` на `name` и `INSERT OR IGNORE` для идемпотентного добавления
- Все запросы выполняются синхронно (sqlite3 не поддерживает async/await), что допустимо для лёгкой нагрузки локального сервера

**4.5. Безопасность приложения**

Вопросы безопасности данных в локальных сетях рассмотрены в авторской статье «Способы защиты данных в системах, работающих внутри локальной сети» [2]. В соответствии с выводами статьи в данной системе реализованы следующие меры:

- **Изоляция сети** — система развёртывается в выделенной Wi-Fi-сети мероприятия, недоступной из интернета; это само по себе сокращает поверхность атаки
- **Защита от SQL-инъекций** — все обращения к SQLite выполняются через параметризованные запросы (`sqlite3` placeholders), исключая подстановку произвольного SQL
- **CORS** настроен на `*` — обоснованно для изолированной LAN, где все клиенты заведомо доверенные; в случае публичного развёртывания источники следует ограничить
- **Аутентификация** отсутствует намеренно — снижает порог входа для судей; при необходимости расширения возможна реализация JWT-токенов (отмечено как направление развития)
- **Отсутствие передачи персональных данных** — система оперирует только именами участников и числовыми оценками; чувствительных данных не хранит и не передаёт

**4.6. Описание ключевых фрагментов кода с пояснениями**

- `ConnectionManager.connect()` — логика предотвращения дублирующихся подключений и уведомления главного судьи
- `setScoreElement()` — иммутабельное обновление вложенного состояния React и обработка «Н»-модификатора
- `getScoreSum()` — алгоритм подсчёта суммы с учётом штрафов соперника
- Восстановление счёта при переподключении судьи (`loadScoresFromServer`)
