### ВВЕДЕНИЕ (~5 стр.)

Что включить:

- **Актуальность темы** — ручной учёт очков в боевых видах спорта является источником ошибок и споров; цифровые решения для судейства редки, дороги и требуют интернета; предлагаемая система работает автономно в локальной сети. Актуальность offline-подхода подтверждается в авторской статье «Перспективы развития приложений, работающих вне доступа интернет-сети» [1]
- **Объект исследования** — процесс судейства соревнований по боевым видам спорта (каратэ, кикбоксинг, тхэквондо)
- **Предмет исследования** — программное обеспечение для автоматизации оценки и подсчёта очков в режиме реального времени на базе веб-технологий
- **Цель работы** — разработка распределённой информационной системы судейства соревнований, функционирующей в локальной сети без доступа к интернету
- **Задачи:**
  1. Проанализировать предметную область, существующие аналоги и целевую аудиторию
  2. Сформулировать требования и спроектировать архитектуру системы
  3. Разработать и протестировать программное обеспечение (backend, frontend, БД)
  4. Сформировать бизнес-план и финансовую модель для вывода продукта на рынок
- **Методы исследования** — системный анализ, объектно-ориентированное проектирование, прототипирование, функциональное и интеграционное тестирование, методы маркетингового и финансового анализа
- **Практическая значимость** — система бесплатна, не требует интернета и сложного развёртывания; готова к использованию на региональных соревнованиях; разработан план коммерциализации продукта

### ГЛАВА 2. ПРОЕКТИРОВАНИЕ РАЗРАБАТЫВАЕМОЙ СИСТЕМЫ (~25–30 стр.)

Что включить:

**2.1. Требования к разрабатываемой системе**

*Функциональные требования:*
- Регистрация участников раунда (синий/красный) с автодополнением из БД
- Подключение до 3 боковых судей через QR-код
- Отправка оценок боковым судьёй в реальном времени (REST POST)
- Отмена последнего действия (Undo)
- Отображение итоговой таблицы очков у главного судьи (WebSocket)
- Управление раундом: запуск, таймер, завершение
- Отключение судьи (kick) главным судьёй
- Хранение базы участников в SQLite
- Тайбрейк при равном счёте по всем трём судьям

*Нефункциональные требования:*
- Задержка передачи оценки < 200 мс в локальной сети
- Работа без интернета (offline-режим)
- Поддержка мобильных браузеров (iOS Safari, Android Chrome)
- Единый дистрибутив: один Python-процесс + dist-папка фронтенда
- Защита данных в рамках локальной сети (со ссылкой на статью [2])

**2.2. Выбор и обоснование технологического стека**

| Уровень | Технология | Обоснование |
|---|---|---|
| Frontend | React 18 + Vite | Компонентная архитектура, SPA, быстрая сборка |
| UI-компоненты | Material UI (MUI) | Готовые адаптивные компоненты |
| Маршрутизация | React Router v6 | Декларативная навигация |
| Backend | Python + FastAPI | Async, автодокументация OpenAPI, WebSocket |
| Offline-режим | fastapi-offline | Swagger UI без CDN |
| СУБД | SQLite | Встраиваемая, без отдельного сервера |
| Real-time | WebSocket | Двунаправленный канал, минимальные задержки |
| Сборка | Vite build | Оптимизированный production-бандл |

- Сравнение альтернатив (React vs Vue, FastAPI vs Flask/Django, SQLite vs PostgreSQL)
- Обоснование выбора по критериям производительности, простоты, лицензионных условий

**2.3. Проектирование архитектуры приложения**
- Архитектура клиент-сервер с двумя типами клиентов: главный судья (десктоп) и боковой судья (мобильный)
- Роль сервера FastAPI: хранилище состояния (`ConnectionManager`), маршрутизатор WebSocket-сообщений, статик-сервер для SPA
- Диаграмма компонентов (UML)
- Диаграмма развёртывания: один хост в ЛВС, N мобильных клиентов по Wi-Fi
- Описание подключений: WebSocket `/ws/mainJudge` и `/ws/{judgeName}`

**2.4. Моделирование бизнес-процессов**
- BPMN-диаграмма потока: «Создание раунда → Подключение судей → Ход раунда → Завершение раунда / Тайбрейк»

- `MobilePage`: локальный `localScoresRef` для определения тайбрейка без запроса к серверу
- Реализация QR-кода для подключения судей
- Реализация таймера раунда

**3.4. Работа с базой данных**
- Таблица `participants` с ограничением `UNIQUE` на `name`
- `INSERT OR IGNORE` для идемпотентного добавления
- Параметризованные запросы (защита от SQL-инъекций)
- Обоснование синхронной работы с SQLite

**3.5. Безопасность приложения**
Со ссылкой на авторскую статью [2]:
- Изоляция сети (выделенный Wi-Fi мероприятия)

- CORS-политика (обоснование `*` для LAN)
- Отсутствие аутентификации как сознательное проектное решение
