# ГЛАВА 3. РАЗРАБОТКА ИНФОРМАЦИОННОЙ СИСТЕМЫ ПОДДЕРЖКИ ПРОЦЕССА СПОРТИВНОГО СУДЕЙСТВА

В третьей главе выпускной квалификационной работы рассматривается практическая реализация информационной системы поддержки процесса спортивного судейства в боевых искусствах и единоборствах, спроектированной во второй главе. Описываются общая архитектура приложения, реализация серверной и клиентской частей, механизм их интеграции на основе REST-запросов и протокола WebSocket, методика и результаты тестирования работоспособности, а также практический эффект от внедрения системы. Изложение ведётся применительно к разработанному клиент-серверному приложению, предназначенному для сбора индивидуальных оценок трёх боковых судей в режиме реального времени, их автоматического подсчёта и вычисления финального результата поединка по армейскому рукопашному бою.

## 3.1 Анализ и описание разработки системы

Под архитектурой программной системы понимается совокупность её структурных элементов, их внешне видимых свойств и связей между ними, определяющая принципы организации, взаимодействия и развития системы. Выбор архитектуры является основополагающим решением этапа разработки, поскольку от него зависят способ обмена данными между компонентами, требования к инфраструктуре развёртывания и трудоёмкость дальнейшего сопровождения. Для разрабатываемой системы определяющим архитектурным требованием стала необходимость доставки оценок боковых судей главному судье в режиме реального времени при работе в локальной сети без доступа к сети Интернет.

Разработанная система построена по клиент-серверной архитектуре и состоит из трёх логических компонентов:

1) серверная часть — приложение на языке Python с использованием веб-фреймворка FastAPI, выполняющее роль центрального узла системы: оно принимает оценки судей, хранит состояние текущего поединка, ведёт справочник участников в базе данных SQLite и рассылает уведомления подключённым клиентам;
2) клиентская часть главного судьи — веб-интерфейс, открываемый в браузере компьютера или ноутбука, на котором отображается сводная таблица оценок, выполняется управление раундом и составом судейской коллегии;
3) клиентская часть бокового судьи — мобильный веб-интерфейс, открываемый в браузере смартфона, с помощью которого судья выставляет оценки участникам поединка.

Существенной особенностью архитектуры является то, что обе клиентские части реализованы в виде единого одностраничного приложения (SPA — Single Page Application) на библиотеке ReactJS: конкретный интерфейс определяется маршрутом, открытым в браузере устройства. Такое решение позволило сократить объём кодовой базы и исключить необходимость установки специализированных приложений на устройства судей — для работы достаточно стандартного браузера.

Взаимодействие клиентов с сервером осуществляется по двум каналам. Команды, инициируемые пользователем (создание раунда, отправка оценки, отмена действия, завершение раунда), передаются на сервер HTTP-запросами в формате JSON через программный интерфейс (API). События, инициируемые сервером (поступление новой оценки, изменение списка подключённых судей, отключение судьи, завершение раунда), доставляются клиентам по протоколу WebSocket, обеспечивающему постоянное двунаправленное соединение и минимальную задержку доставки сообщений. Комбинация REST и WebSocket позволила разграничить ответственность каналов связи: HTTP-запросы изменяют состояние системы по инициативе клиента, а WebSocket-сообщения мгновенно оповещают заинтересованные стороны об этих изменениях. Технологический стек системы соответствует обоснованию, приведённому в разделе 2.2 настоящей работы. Клиентская часть реализована на библиотеке ReactJS версии 18 с применением сборщика Vite, библиотеки интерфейсных компонентов Material UI (MUI) и библиотеки маршрутизации React Router. Серверная часть реализована на языке Python с использованием фреймворка FastAPI, ASGI-сервера Uvicorn и библиотеки валидации данных Pydantic; постоянное хранение справочника участников обеспечивает встраиваемая СУБД SQLite. Дополнительно применяется пакет fastapi-offline, благодаря которому автоматически генерируемая документация API доступна без обращения к внешним ресурсам сети Интернет.

Выбор данного стека обусловлен следующими причинами. Во-первых, ReactJS реализует декларативную модель отрисовки: при изменении состояния приложения соответствующие фрагменты интерфейса перестраиваются автоматически, что принципиально важно для сводной таблицы главного судьи, обновляющейся при каждой входящей оценке. Во-вторых, FastAPI обеспечивает асинхронную обработку запросов и встроенную поддержку протокола WebSocket, без которой реализация обмена в реальном времени потребовала бы подключения сторонних решений. В-третьих, связка «веб-клиент — Python-сервер — SQLite» позволяет развернуть всю систему в виде единственного процесса на компьютере главного судьи: сервер одновременно обрабатывает запросы API и раздаёт собранные статические файлы клиентского приложения из каталога dist, сформированного командой сборки Vite. Следовательно, на площадке соревнований не требуется ни доступ к сети Интернет, ни выделенная серверная инфраструктура — достаточно ноутбука и точки доступа Wi-Fi, образующих локальную сеть.

Процесс разработки системы был организован итерационно и включал следующие этапы:

1. Реализация серверного каркаса: определение моделей данных, REST-маршрутов и WebSocket-обработчика.
2. Реализация клиентских страниц: создание раунда, таблица главного судьи, подключение и пульт бокового судьи.
3. Интеграция частей: подключение клиентского API-модуля к серверным маршрутам, отладка обмена WebSocket-сообщениями.
4. Реализация базы данных участников и функции автодополнения имён.
5. Реализация вспомогательных функций: таймер раунда, отмена действий, тайбрейк, принудительное отключение судьи.
6. Тестирование системы и устранение выявленных дефектов.

Таким образом, разработанная архитектура непосредственно отражает структуру автоматизируемого процесса: каждому участнику судейской коллегии соответствует собственный клиентский интерфейс, а сервер выполняет функции, аналогичные функциям секретаря соревнований, — собирает оценки, ведёт протокол и формирует итоговый результат.

## 3.2 Разработка серверной части

Серверная часть информационной системы представляет собой приложение на языке Python, исходный код которого сосредоточен в модуле main.py каталога backend. Несмотря на компактность, модуль имеет выраженную внутреннюю структуру и включает следующие логические слои:

1) слой моделей данных — классы на основе Pydantic BaseModel, описывающие структуру передаваемых данных и обеспечивающие их автоматическую валидацию;
2) слой маршрутов API — обработчики HTTP-запросов, сопоставленные адресам программного интерфейса средствами декораторов FastAPI;
3) слой управления соединениями и бизнес-логики — класс ConnectionManager, инкапсулирующий состояние текущего поединка и логику рассылки WebSocket-сообщений;
4) слой доступа к данным — функции работы с базой данных SQLite, реализующие операции над справочником участников;
5) слой раздачи статических файлов — механизм, обеспечивающий доставку собранного клиентского приложения в браузеры пользователей.

Приложение создаётся как экземпляр класса FastAPIOffline, что обеспечивает работоспособность интерактивной документации API в автономном режиме. К приложению подключается промежуточное программное обеспечение CORSMiddleware, разрешающее кросс-доменные запросы внутри локальной сети, а также механизм StaticFiles, монтирующий каталог собранных ресурсов клиентского приложения по адресу /assets. Маршрут-перехватчик с шаблоном /{full_path:path} реализует типовую для одностраничных приложений схему: если запрошенный путь соответствует существующему файлу каталога dist, сервер возвращает этот файл, в противном случае возвращается корневой документ index.html, после чего маршрутизация выполняется на стороне клиента средствами React Router.

Валидация входных данных реализована на основе моделей Pydantic. Так, модель Score описывает структуру судейской оценки и включает четыре поля: color — цвет участника («blue» или «red»), judge — имя судьи, выставившего оценку, punch — категорию технического действия, score — числовое значение оценки. Аналогичную структуру имеет модель UndoScore, применяемая при отмене действия. Модель Participants содержит поля blue и red с именами участников раунда, а модель ParticipantEntry — поле name для добавления записи в справочник. Если тело входящего запроса не соответствует объявленной модели, FastAPI автоматически отклоняет запрос с кодом 422 и описанием ошибки, что исключает попадание некорректных данных в бизнес-логику системы.

Центральным элементом бизнес-логики серверной части является класс ConnectionManager, реализующий шаблон проектирования «менеджер соединений». Класс хранит словарь connected_judges, сопоставляющий имена подключённых боковых судей их WebSocket-соединениям, отдельную ссылку main_judge_ws на соединение главного судьи и объект participants с именами участников текущего раунда. Класс выполняет следующие функции:

1) connect — приём нового WebSocket-подключения с контролем уникальности имени судьи: попытка подключения под уже занятым именем отклоняется закрытием соединения со специальным кодом 4001, что предотвращает конфликт оценок двух устройств, работающих под одним именем;
2) disconnect — исключение судьи из списка подключённых при разрыве соединения или принудительном отключении;
3) update_connected_judges — отправка главному судье актуального списка подключённых судей после каждого изменения состава коллегии;
4) send_score и send_undo — пересылка поступившей оценки либо команды отмены в интерфейс главного судьи;
5) connect_participant — сохранение имён участников раунда и их рассылка подключённым боковым судьям.

Программный интерфейс серверной части включает маршруты, перечень которых приведён в таблице 3.1.

Таблица 3.1 — Основные маршруты программного интерфейса системы

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | /connect_judge | Регистрация бокового судьи перед установлением WebSocket-соединения |
| GET | /local_ip | Получение IP-адреса сервера в локальной сети для формирования QR-кода |
| GET | /kick_judge/{judge} | Принудительное отключение бокового судьи главным судьёй |

| POST | /connect_participants | Установка участников текущего раунда |
| GET | /participants | Получение имён участников текущего раунда |

| WS | /ws/{judgeName} | WebSocket-соединение судьи (для главного судьи — /ws/mainJudge) |

WebSocket-обработчик, сопоставленный маршруту /ws/{judgeName}, принимает подключение через метод manager.connect, после чего удерживает соединение открытым в цикле ожидания сообщений. При разрыве соединения возбуждается исключение WebSocketDisconnect, обрабатываемое вызовом manager.disconnect, благодаря чему список подключённых судей у главного судьи всегда отражает фактическое состояние коллегии.

Слой доступа к данным реализует работу со справочником участников. При запуске сервера функция init_db создаёт в файле participants.db таблицу participants с двумя полями: целочисленным первичным ключом id с автоинкрементом и текстовым полем name с ограничением уникальности NOT NULL UNIQUE. Добавление участника выполняется оператором INSERT OR IGNORE, что делает операцию идемпотентной: повторное добавление существующего имени не приводит ни к ошибке, ни к дублированию записи. Все запросы к базе данных выполняются в параметризованной форме, что исключает возможность SQL-инъекций. Выборка справочника осуществляется с сортировкой по имени, что упрощает работу функции автодополнения на клиенте.

Отдельного пояснения заслуживает функция get_local_ip, определяющая IP-адрес сервера в локальной сети. Функция открывает UDP-сокет с условным внешним адресом и считывает адрес собственного сетевого интерфейса, выбранного операционной системой для маршрутизации; фактическая передача данных при этом не происходит, поэтому метод работает и при отсутствии доступа к сети Интернет. Полученный адрес используется клиентской частью для формирования QR-кода подключения судей.

Таким образом, серверная часть системы сочетает три роли: REST-сервис для приёма команд, WebSocket-маршрутизатор для доставки уведомлений в реальном времени и веб-сервер статических файлов клиентского приложения. Подобная консолидация позволила свести развёртывание системы к запуску единственного процесса командой uvicorn на компьютере главного судьи.

## 3.3 Разработка клиентской части

Клиентская часть информационной системы представляет собой одностраничное приложение на библиотеке ReactJS, построенное по компонентному принципу: интерфейс собирается из иерархии переиспользуемых компонентов, каждый из которых инкапсулирует собственную разметку, стили и логику. Управление состоянием компонентов осуществляется штатными средствами React — хуками useState, useEffect, useRef и useMemo, что избавило проект от подключения внешних библиотек управления состоянием, избыточных при данном масштабе приложения.

Корневой компонент App настраивает маршрутизацию средствами React Router и сопоставляет адресам приложения четыре страницы, перечень которых приведён в таблице 3.2.

Функция getScoreSum вычисляет сумму баллов участника по конкретному судье: суммируются числовые оценки категорий «удар рукой», «удар ногой», «бросок» и результат тайбрейка, к оценкам с модификатором «Н» добавляется 3 балла, после чего прибавляются штрафные баллы за нарушения соперника — по 1 баллу за каждое замечание и по 2 балла за каждое предупреждение, вынесенные противоположному участнику. Функция calcScore определяет победителя по мнению отдельного судьи: участник с большей суммой получает одно судейское очко. Функция calcFinalScore суммирует судейские очки по всем трём судьям и формирует финальный счёт поединка (например, 2:1 или 3:0). Следовательно, вычисление результата полностью повторяет регламентную процедуру определения победителя, выполняемую судейской коллегией вручную.

## 3.4 Интеграция клиентской и серверной частей

Интеграция клиентской и серверной частей представляет собой организацию их информационного взаимодействия, при котором действия пользователей преобразуются в запросы к серверу, а изменения состояния системы немедленно отражаются в интерфейсах всех заинтересованных участников. В разработанной системе интеграция реализована на двух уровнях: уровне HTTP-запросов и уровне WebSocket-сообщений.

Все обращения клиентской части к программному интерфейсу сервера инкапсулированы в отдельном модуле api.js, что соответствует принципу разделения ответственности: компоненты страниц не содержат сетевого кода и оперируют функциями прикладного уровня (postScore, undoScore, fetchParticipants, connectParticipants и другими). Базовый адрес сервера формируется динамически из адреса, по которому открыто приложение, с указанием порта 8000; благодаря этому клиент работает корректно при любом IP-адресе сервера в локальной сети без дополнительной настройки. Запросы выполняются стандартным браузерным интерфейсом Fetch API; данные передаются в формате JSON с заголовком Content-Type: application/json. Например, функция postScore формирует POST-запрос на маршрут /send_score, передавая в его теле сериализованный объект оценки, и возвращает разобранный ответ сервера вызывающему компоненту.

Канал реального времени организован следующим образом. При открытии страницы сводной таблицы компонент TablePage устанавливает WebSocket-соединение с сервером по адресу /ws/mainJudge; мобильный пульт бокового судьи подключается по адресу /ws/{имя судьи}. Соединения создаются в хуке useEffect с функцией очистки, закрывающей соединение при размонтировании компонента, что исключает утечку ресурсов при навигации между страницами. Входящие сообщения обрабатываются в обработчике onmessage: тип события определяется полем data сообщения, после чего вызывается соответствующая функция обновления состояния React, и интерфейс перестраивается автоматически. Перечень типов WebSocket-сообщений системы приведён в таблице 3.3.

Таблица 3.3 — Типы WebSocket-сообщений системы

| Тип сообщения | Получатель | Назначение |
|---|---|---|
| judgeupd | Главный судья | Актуализация списка подключённых боковых судей |
| score | Главный судья | Доставка новой судейской оценки в сводную таблицу |

Рассмотрим полный цикл передачи оценки, иллюстрирующий взаимодействие всех уровней интеграции. Боковой судья нажимает кнопку оценки на мобильном пульте; компонент MobilePage формирует объект с полями judge, punch, color, score и передаёт его функции postScore, которая отправляет POST-запрос на маршрут /send_score. Сервер валидирует тело запроса по модели Score и вызывает метод manager.send_score, который пересылает оценку в открытое WebSocket-соединение главного судьи в виде сообщения типа score. Обработчик onmessage компонента TablePage извлекает данные оценки и вызывает функцию setScoreElement, выполняющую иммутабельное обновление состояния scores; React, обнаружив изменение состояния, перерисовывает соответствующую ячейку таблицы, строку суммы и финальный счёт. Весь цикл от нажатия кнопки до обновления таблицы выполняется в пределах локальной сети и занимает доли секунды, что обеспечивает восприятие работы системы как мгновенной. Аналогичным образом реализованы остальные сценарии обмена:

1. Отмена действия: запрос POST /undo_score преобразуется в сообщение undo главному судье; функция removeLastScore удаляет последнюю оценку соответствующей категории либо снимает модификатор «Н» без удаления самой оценки.
2. Подключение судьи: установление WebSocket-соединения нового судьи вызывает рассылку сообщения judgeupd, по которому таблица главного судьи перестраивает столбцы под актуальный состав коллегии.
3. Создание раунда: запрос POST /connect_participants сохраняет участников на сервере и инициирует сообщение participantupd, доставляющее имена участников на пульты подключённых судей.
4. Завершение раунда: запрос POST /round_end преобразуется в сообщение roundend; каждый пульт сравнивает локальные суммы баллов и при их равенстве открывает диалог тайбрейка, решение которого передаётся запросом POST /tiebreaker и учитывается в финальном счёте.
5. Принудительное отключение: запрос GET /kick_judge/{judge} приводит к разрыву соединения и доставке судье сообщения kicked с уведомлением в интерфейсе.

Отдельно реализован механизм восстановления состояния. Оценки текущего раунда сохраняются на сервере, и при обновлении страницы или переподключении главного судьи компонент TablePage запрашивает их маршрутом GET /scores: функция loadScoresFromServer преобразует серверное представление данных (сгруппированное по именам судей) во внутренний формат таблицы и восстанавливает её содержимое. На основании этого случайное обновление страницы браузера или кратковременный сбой соединения не приводят к потере протокола поединка, что существенно для эксплуатации системы в условиях реальных соревнований.

Таким образом, интеграция клиентской и серверной частей построена по событийной модели: каждое действие пользователя порождает HTTP-запрос, а каждое изменение состояния системы — WebSocket-уведомление заинтересованным клиентам. Подобная организация обеспечивает согласованность данных на всех устройствах судейской коллегии без ручной синхронизации и без периодического опроса сервера.

Для разрабатываемой системы основным видом проверки выбрано функциональное тестирование, при котором система рассматривается как «чёрный ящик» и проверяется корректность её реакции на действия пользователей в типовых и граничных сценариях. 2) некорректные тела HTTP-запросов отклоняются серверной валидацией Pydantic с кодом 422, не достигая бизнес-логики;
3) разрыв WebSocket-соединения судьи обрабатывается сервером штатно: судья исключается из списка подключённых, а главный судья получает обновлённый список;

5) ввод данных в форму создания раунда контролируется клиентской валидацией обязательных полей.

## 3.6 Экономическая эффективность и практический эффект от внедрения системы

Под экономической эффективностью информационной системы понимается соотношение полезного эффекта от её применения и затрат на её создание и эксплуатацию. Для систем, автоматизирующих организационные процессы, полезный эффект выражается прежде всего в сокращении трудозатрат, уменьшении количества ошибок и ускорении выполнения процесса. Оценка практического эффекта существенна для настоящего проекта, поскольку целью разработки являлось не исследование технологий само по себе, а решение конкретной прикладной задачи — устранение недостатков ручного судейства поединков по армейскому рукопашному бою.

При традиционной организации судейства боковые судьи фиксируют оценки в бумажных записках или протоколах, после чего секретарь либо главный судья собирает записи, выполняет подсчёт сумм с учётом штрафных баллов и определяет победителя. Данный процесс характеризуется следующими недостатками: затратами времени на сбор и сверку записей после каждого поединка; риском арифметических ошибок при ручном подсчёте; невозможностью наблюдать ход оценивания до завершения поединка; возникновением спорных ситуаций, разбор которых требует дополнительного времени.

Разработанная система устраняет перечисленные недостатки за счёт следующих эффектов:

1. Сокращение времени подведения итогов. Суммы баллов и финальный счёт вычисляются автоматически по мере поступления оценок, поэтому результат поединка известен немедленно после его завершения; этап сбора и сверки судейских записок исключается полностью.
2. Снижение ручного труда. Секретарь освобождается от переноса оценок в сводный протокол и арифметических вычислений; главный судья получает готовую таблицу с детализацией по каждому судье и категории действий.
3. Уменьшение количества ошибок. Автоматический подсчёт исключает арифметические ошибки; контроль уникальности имён судей и валидация данных на сервере исключают искажение протокола; механизм отмены позволяет корректно исправить ошибочное нажатие.
4. Повышение прозрачности судейства. Главный судья наблюдает оценки всех судей в режиме реального времени, что позволяет своевременно выявлять расхождения в оценивании и сокращает количество спорных ситуаций.
5. Ускорение проведения соревнований в целом. Сокращение паузы между поединками увеличивает пропускную способность площадки в течение соревновательного дня.
6. Отсутствие затрат на инфраструктуру. Система функционирует в локальной сети без доступа к сети Интернет, построена исключительно на свободно распространяемых технологиях и не требует приобретения лицензий или специализированного оборудования — достаточно имеющихся у организаторов ноутбука, точки доступа Wi-Fi и смартфонов судей.

Оценим экономию времени количественно. При ручной организации судейства подведение итогов одного поединка включает сбор записок трёх судей, подсчёт сумм с учётом нокдаунов и штрафов, сверку и объявление результата, что занимает в среднем [2–4] минуты; при использовании системы результат формируется автоматически, и на его объявление затрачивается не более [0,5] минуты. Расчёт экономии времени для типового соревновательного дня, включающего [50] поединков, приведён в таблице 3.5.

В денежном выражении экономия может быть оценена через стоимость рабочего времени судейской коллегии: при ставке [указать ставку] рублей в час и составе коллегии из [5] человек экономия составляет [указать сумму] рублей за день соревнований. Кроме того, исключение ошибок подсчёта снижает репутационные риски организаторов и вероятность подачи протестов, разбор которых сопряжён с дополнительными организационными издержками.

Практический эффект системы не ограничивается экономией времени. Электронная фиксация каждой оценки с привязкой к судье и категории действия формирует детализированный протокол поединка, который может использоваться для анализа качества судейства, обучения начинающих судей и разбора апелляций. Низкий порог внедрения — запуск одного процесса на ноутбуке и сканирование QR-кода смартфонами судей — делает систему доступной для соревнований муниципального и регионального уровня, не располагающих бюджетом на дорогостоящие коммерческие решения.

## 3.7 Выводы по главе

В третьей главе выпускной квалификационной работы описана практическая реализация информационной системы поддержки процесса спортивного судейства в боевых искусствах и единоборствах. По результатам выполненной разработки можно сформулировать следующие выводы.

1. Реализована клиент-серверная архитектура, в которой единственный серверный процесс на базе FastAPI совмещает функции REST-сервиса, WebSocket-маршрутизатора и веб-сервера статических файлов, а клиентские интерфейсы главного и боковых судей реализованы в виде одностраничного приложения на ReactJS с библиотекой компонентов Material UI.
2. Разработана серверная часть, включающая валидацию данных на основе моделей Pydantic, менеджер соединений ConnectionManager с контролем уникальности судей, программный интерфейс управления поединком и слой доступа к базе данных SQLite со справочником участников.
3. Разработана клиентская часть, охватывающая полный цикл проведения поединка: создание раунда с автодополнением участников, сводную таблицу главного судьи с автоматическим подсчётом сумм и финального счёта, подключение судей по QR-коду и мобильный пульт выставления оценок с механизмом отмены действий.
4. Выполнена интеграция частей системы по событийной модели: команды пользователей передаются HTTP-запросами в формате JSON, а уведомления доставляются по протоколу WebSocket, что обеспечивает отображение каждой оценки в таблице главного судьи в режиме реального времени; реализовано восстановление состояния поединка при переподключении.
5. Проведено функциональное тестирование системы по пятнадцати сценариям, охватывающим типовые и граничные случаи, включая тайбрейк, отмену модификатора нокдауна и нештатные ситуации; все сценарии пройдены успешно, корректность автоматического подсчёта подтверждена сверкой с контрольным ручным подсчётом по регламенту.
6. Оценён практический эффект от внедрения: система сокращает время подведения итогов поединка, исключает арифметические ошибки ручного подсчёта, повышает прозрачность судейства и не требует затрат на лицензии и инфраструктуру, что делает её доступной для соревнований регионального уровня.

Таким образом, разработанная информационная система полностью реализует требования, сформулированные на этапе проектирования, прошла проверку работоспособности во всех предусмотренных сценариях и готова к практическому использованию для поддержки процесса судейства поединков по армейскому рукопашному бою.
