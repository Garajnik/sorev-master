# ГЛАВА 3. РАЗРАБОТКА ИНФОРМАЦИОННОЙ СИСТЕМЫ ПОДДЕРЖКИ ПРОЦЕССА СПОРТИВНОГО СУДЕЙСТВА

Третья глава посвящена практической реализации системы, которая была спроектирована в предыдущей главе. Здесь показано, как устроено приложение в целом, как сделаны его серверная и клиентская части и как они связаны между собой — через REST-запросы и протокол WebSocket. Отдельно рассмотрены проверка работоспособности и тот эффект, который даёт применение системы на соревнованиях. Речь идёт о клиент-серверном приложении для армейского рукопашного боя: оно собирает оценки трёх боковых судей в реальном времени, само их подсчитывает и выводит итоговый результат поединка.

## 3.1 Анализ и описание разработки системы

Под архитектурой программной системы понимают совокупность её структурных элементов, их внешне видимых свойств и связей между ними, задающую принципы организации и развития системы. Это одно из ключевых проектных решений. От него зависят сразу несколько вещей: способ обмена данными между компонентами, требования к развёртыванию и то, насколько трудоёмким окажется последующее сопровождение. Определяющим требованием в данном случае стала доставка оценок боковых судей главному судье в реальном времени — причём при работе в локальной сети, без выхода в Интернет.

Система построена по клиент-серверной схеме и складывается из трёх логических компонентов:

1) серверная часть — приложение на Python с использованием веб-фреймворка FastAPI. Это центральный узел системы: он принимает оценки, хранит состояние текущего поединка, ведёт справочник участников в базе данных SQLite и рассылает уведомления подключённым клиентам;
2) клиентская часть главного судьи — веб-интерфейс, который открывается в браузере компьютера или ноутбука. На нём отображается сводная таблица оценок, отсюда же ведётся управление раундом и составом судейской коллегии;
3) клиентская часть бокового судьи — мобильный веб-интерфейс в браузере смартфона, через который судья выставляет оценки участникам.

Важная особенность архитектуры в том, что обе клиентские части — это на самом деле одно одностраничное приложение (SPA, Single Page Application) на библиотеке ReactJS. Какой именно интерфейс увидит пользователь, решает лишь адрес, открытый в браузере устройства. Благодаря такому подходу кодовая база получилась компактнее, а судьям не приходится устанавливать на свои устройства отдельные программы — достаточно обычного браузера.

С сервером клиенты общаются по двум каналам. Команды, которые инициирует сам пользователь — создание раунда, отправка оценки, отмена действия, завершение раунда, — уходят на сервер HTTP-запросами в формате JSON через программный интерфейс (API). А вот события, которые рождаются на стороне сервера — новая оценка, изменение списка подключённых судей, отключение судьи, конец раунда, — приходят к клиентам уже по WebSocket. Этот протокол держит постоянное двунаправленное соединение и доставляет сообщения практически без задержки. Такое разделение оказалось удобным: HTTP меняет состояние системы по команде клиента, а WebSocket лишь оповещает заинтересованные стороны о том, что состояние изменилось. Технологический стек соответствует обоснованию из раздела 2.2. Клиент написан на ReactJS 18; при сборке используется Vite, для интерфейса — библиотека компонентов Material UI (MUI), для навигации — React Router. Сервер написан на Python на фреймворке FastAPI, запускается через ASGI-сервер Uvicorn, данные проверяются библиотекой Pydantic, а справочник участников хранится во встраиваемой СУБД SQLite. Дополнительно подключён пакет fastapi-offline — с ним интерактивная документация API работает даже без доступа к внешним ресурсам сети Интернет.

Почему был выбран именно такой стек? Во-первых, ReactJS использует декларативную модель отрисовки: меняется состояние приложения — нужные фрагменты интерфейса перестраиваются сами. Для сводной таблицы главного судьи, которая обновляется на каждой входящей оценке, это критично. Во-вторых, FastAPI обрабатывает запросы асинхронно и поддерживает WebSocket «из коробки»; без этой поддержки пришлось бы тянуть в проект сторонние решения. В-третьих, связка «веб-клиент — Python-сервер — SQLite» позволяет запустить всю систему как один процесс прямо на ноутбуке главного судьи. Сервер при этом и обрабатывает запросы API, и раздаёт статические файлы клиента из каталога dist, который собирает Vite. На площадке соревнований не нужны ни Интернет, ни отдельная серверная инфраструктура — хватает ноутбука и точки доступа Wi-Fi, образующих локальную сеть.

Разработка велась итерационно, по следующим этапам:

1. Серверный каркас: модели данных, REST-маршруты, WebSocket-обработчик.
2. Клиентские страницы: создание раунда, таблица главного судьи, подключение и пульт бокового судьи.
3. Интеграция: подключение клиентского API-модуля к маршрутам сервера и отладка обмена сообщениями через WebSocket.
4. База данных участников и автодополнение имён.
5. Вспомогательные функции — таймер раунда, отмена действий, тайбрейк, принудительное отключение судьи.
6. Тестирование и устранение найденных дефектов.

В итоге архитектура напрямую повторяет структуру самого процесса судейства: у каждого члена коллегии — свой клиентский интерфейс, а сервер берёт на себя роль секретаря соревнований — собирает оценки, ведёт протокол и считает итог.

## 3.2 Разработка серверной части

Серверная часть — это приложение на Python, весь код которого собран в модуле main.py каталога backend. Модуль компактный, но структура у него вполне выраженная; внутри выделяются следующие логические слои:

1) слой моделей данных — классы на основе Pydantic BaseModel; они описывают структуру передаваемых данных и заодно проверяют её;
2) слой маршрутов API — обработчики HTTP-запросов, привязанные к адресам интерфейса декораторами FastAPI;
3) слой управления соединениями и бизнес-логики — класс ConnectionManager, который держит состояние текущего поединка и отвечает за рассылку WebSocket-сообщений;
4) слой доступа к данным — функции работы с SQLite, через которые ведётся справочник участников;
5) слой раздачи статики — он отдаёт собранный клиент в браузеры пользователей.

Само приложение создаётся как экземпляр класса FastAPIOffline; за счёт этого интерактивная документация API остаётся доступной в автономном режиме. К приложению подключается CORSMiddleware, который разрешает кросс-доменные запросы внутри локальной сети, и StaticFiles, монтирующий каталог собранных ресурсов по адресу /assets. Отдельно стоит маршрут-перехватчик с шаблоном /{full_path:path}. Он реализует обычную для SPA логику: если запрошенный путь ведёт к реальному файлу из каталога dist — сервер отдаёт этот файл; если нет — отдаёт корневой index.html, а дальше маршрутизацией занимается React Router уже на стороне клиента.

Входные данные проверяются моделями Pydantic. Например, модель Score описывает судейскую оценку и состоит из четырёх полей: color — цвет участника («blue» или «red»), judge — имя выставившего оценку судьи, punch — категория технического действия, score — само число баллов. У модели UndoScore, которая применяется при отмене действия, структура такая же. Модель Participants хранит поля blue и red с именами участников раунда, а ParticipantEntry — единственное поле name для добавления записи в справочник. Если тело запроса не подходит под объявленную модель, FastAPI сам отклонит его с кодом 422 и описанием ошибки. Так некорректные данные просто не доходят до бизнес-логики.

Ядром бизнес-логики на сервере служит класс ConnectionManager — по сути, менеджер соединений. Он хранит словарь connected_judges, где именам подключённых боковых судей сопоставлены их WebSocket-соединения, отдельную ссылку main_judge_ws на соединение главного судьи и объект participants с именами участников текущего раунда. Дополнительно менеджер отслеживает два поля журналирования: флаг round_active (True в ходе раунда, False до его начала и после завершения) и целочисленный current_round_id — идентификатор строки в таблице rounds, к которой привязываются все оценки текущего поединка. За классом закреплены такие функции:

1) connect — принимает новое WebSocket-подключение и проверяет, не занято ли имя. Если кто-то пытается подключиться под уже используемым именем, соединение закрывается со специальным кодом 4001. Это нужно, чтобы два устройства под одним именем не начали выставлять оценки одновременно. Судье, подключившемуся в ходе уже идущего раунда, немедленно отправляется сообщение roundstate, чтобы его пульт корректно отобразил активное состояние;
2) disconnect — убирает судью из списка подключённых, когда соединение рвётся или судью отключают принудительно;
3) update_connected_judges — после каждого изменения в составе коллегии отправляет главному судье свежий список подключённых;
4) send_score и send_undo — сначала записывают событие в таблицу round_scores вызовом insert_round_score (при условии, что current_round_id установлен), после чего пересылают оценку или команду отмены в интерфейс главного судьи;
5) connect_participant — сохраняет имена участников раунда и рассылает их подключённым боковым судьям;
6) send_round_start — переводит round_active в True, вызывает create_round с именами участников и сохраняет возвращённый идентификатор в current_round_id; затем рассылает всем боковым судьям WebSocket-сообщение roundstart. Благодаря этому все последующие оценки и отмены автоматически привязываются к записи текущего раунда в таблице rounds.

WebSocket-обработчик привязан к маршруту /ws/{judgeName}. Он принимает подключение через manager.connect и дальше держит соединение открытым, ожидая сообщения в цикле. Когда соединение обрывается, возникает исключение WebSocketDisconnect — его перехватывает вызов manager.disconnect. За счёт этого список подключённых судей у главного судьи всегда показывает реальный состав коллегии.

Слой доступа к данным обслуживает три таблицы SQLite в файле participants.db. Функция init_db вызывается при каждом старте приложения и создаёт все три таблицы с директивой CREATE TABLE IF NOT EXISTS — то есть уже накопленные данные при перезапуске сервера не теряются.

Таблица participants — справочник спортсменов — имеет автоинкрементный первичный ключ id и текстовое поле name с ограничениями NOT NULL UNIQUE. Новый участник добавляется оператором INSERT OR IGNORE: повторная вставка того же имени не вызывает ни ошибки, ни дубликата. Все запросы параметризованы — SQL-инъекции исключены. Справочник выбирается с сортировкой по имени для удобного автодополнения.

Таблица rounds — журнал поединков. Функция create_round принимает имена участников синего и красного углов, сохраняет их вместе с меткой времени запуска в поле started_at и возвращает идентификатор созданной строки; это значение запоминается как current_round_id менеджера соединений и связывает все последующие события с текущим поединком. Функция finish_round заполняет поле ended_at при завершении раунда.

Таблица round_scores — хронологический журнал оценок. Функция insert_round_score вызывается при каждом судейском событии: как при выставлении оценки (action = 'score'), так и при её отмене (action = 'undo'). Каждая строка фиксирует идентификатор раунда, имя судьи, цвет участника, категорию действия, числовое значение и точную метку времени. Хранение отмен в виде отдельных строк вместо физического удаления записей сохраняет полную хронологию поединка и упрощает аудит спорных ситуаций.

Накопленная история доступна через маршруты GET /db/rounds (список всех раундов в порядке убывания идентификатора) и GET /db/rounds/{round_id}/scores (оценки конкретного раунда вместе с метаданными самого раунда).

Отдельно стоит сказать про функцию get_local_ip, которая определяет IP-адрес сервера в локальной сети. Она открывает UDP-сокет с условным внешним адресом и читает адрес того сетевого интерфейса, который операционная система выбрала для маршрутизации. Данные при этом реально никуда не отправляются, поэтому функция работает и без доступа к Интернету. Полученный адрес затем идёт в клиент — на его основе строится QR-код для подключения судей.

Получается, что серверная часть совмещает сразу три роли: это и REST-сервис для приёма команд, и WebSocket-маршрутизатор для доставки уведомлений в реальном времени, и веб-сервер, раздающий статику клиента. Такое объединение свело всё развёртывание к запуску одного процесса командой uvicorn на ноутбуке главного судьи.

## 3.3 Разработка клиентской части

Клиент — это одностраничное приложение на ReactJS, собранное по компонентному принципу: интерфейс складывается из иерархии переиспользуемых компонентов, и каждый держит при себе собственную разметку, стили и логику. Состоянием управляют штатные хуки React — useState, useEffect, useRef и useMemo. Внешние библиотеки управления состоянием для приложения такого масштаба были бы избыточны, и в проект их не добавляли.

Корневой компонент App настраивает навигацию через React Router и привязывает к адресам приложения четыре страницы (таблица 3.2).

Подсчёт результатов в TablePage держится на трёх функциях. Функция getScoreSum считает сумму баллов участника у конкретного судьи: складываются числовые оценки категорий «удар рукой», «удар ногой», «бросок» и результат тайбрейка, к оценкам с модификатором «Н» добавляется 3 балла, после чего прибавляются штрафные баллы за нарушения соперника — по 1 баллу за каждое замечание и по 2 за каждое предупреждение, вынесенные противоположному участнику. ## 3.4 Интеграция клиентской и серверной частей

Интегрировать клиент и сервер — значит наладить их информационное взаимодействие так, чтобы действия пользователей превращались в запросы к серверу, а изменения состояния системы тут же отражались в интерфейсах всех, кого это касается. В данной системе интеграция держится на двух уровнях — HTTP-запросах и WebSocket-сообщениях.

Все обращения клиента к API сервера вынесены в отдельный модуль api.js. Это отвечает принципу разделения ответственности: компоненты страниц не содержат сетевого кода и работают только с функциями прикладного уровня — postScore, undoScore, fetchParticipants, connectParticipants и так далее. Базовый адрес сервера собирается на лету из того адреса, по которому открыто приложение, с портом 8000. Поэтому клиент работает при любом IP-адресе сервера в локальной сети, и ничего дополнительно настраивать не нужно. Сами запросы идут через стандартный Fetch API; данные передаются в JSON с заголовком Content-Type: application/json. Так, postScore формирует POST-запрос на /send_score, кладёт в тело сериализованный объект оценки и возвращает разобранный ответ сервера вызвавшему компоненту.

Канал реального времени устроен так. Открывая сводную таблицу, компонент TablePage поднимает WebSocket-соединение с сервером по адресу /ws/mainJudge; мобильный пульт подключается по адресу /ws/{имя судьи}. Соединения создаются в хуке useEffect, и у него есть функция очистки, которая закрывает соединение при размонтировании компонента, — это спасает от утечки ресурсов при переходах между страницами. Входящие сообщения разбирает обработчик onmessage: по полю data он определяет тип события, вызывает нужную функцию обновления состояния React, и интерфейс перестраивается сам. Все типы WebSocket-сообщений собраны в таблице 3.3.

|---|---|---|
| judgeupd | Главный судья | Актуализация списка подключённых боковых судей |

Проследим весь путь одной оценки — на нём видно, как работают оба уровня интеграции. Боковой судья жмёт кнопку на мобильном пульте. MobilePage собирает объект с полями judge, punch, color, score и отдаёт его функции postScore, а та отправляет POST-запрос на /send_score. Сервер проверяет тело по модели Score и вызывает manager.send_score; этот метод пересылает оценку в открытое WebSocket-соединение главного судьи сообщением типа score. На стороне главного судьи обработчик onmessage компонента TablePage достаёт данные оценки и вызывает setScoreElement — функция иммутабельно обновляет состояние scores. React замечает изменение и перерисовывает только нужную ячейку, строку суммы и финальный счёт. Весь путь от нажатия до обновления таблицы укладывается в доли секунды и проходит внутри локальной сети, так что система воспринимается как мгновенная. Остальные сценарии обмена сделаны по той же логике:

1. Отмена действия. Запрос POST /undo_score превращается в сообщение undo главному судье; функция removeLastScore либо удаляет последнюю оценку нужной категории, либо снимает модификатор «Н», не трогая саму оценку.
2. Подключение судьи. Как только новый судья поднимает WebSocket-соединение, рассылается сообщение judgeupd, и таблица главного судьи перестраивает столбцы под новый состав коллегии.
3. Создание раунда. Запрос POST /connect_participants сохраняет участников на сервере и запускает сообщение participantupd, которое доставляет их имена на пульты подключённых судей.
4. Завершение раунда. Запрос POST /round_end сбрасывает флаг round_active, заполняет поле ended_at в таблице rounds через finish_round и рассылает всем пультам сообщение roundend. Каждый пульт сравнивает локальные суммы баллов, и при равенстве открывает диалог тайбрейка; его решение уходит запросом POST /tiebreaker и попадает в финальный счёт. После сброса round_active любые оценки, кроме тайбрейка, сервер отклоняет с кодом 409.
5. Запуск и журналирование раунда. Запрос POST /round_start активирует флаг round_active, вызывает create_round с именами участников и сохраняет возвращённый идентификатор в current_round_id. После этого каждый входящий POST /send_score и POST /undo_score не только доставляется главному судье через WebSocket, но и немедленно дублируется в таблицу round_scores через insert_round_score — с привязкой к current_round_id и точной меткой времени. История поединка накапливается в реальном времени и после завершения доступна через GET /db/rounds/{round_id}/scores.
6. Принудительное отключение. Запрос GET /kick_judge/{judge} рвёт соединение и доставляет судье сообщение kicked, по которому в интерфейсе появляется уведомление.

Отдельно сделан механизм восстановления состояния. Оценки текущего раунда живут на сервере, и при обновлении страницы или переподключении главного судьи компонент TablePage запрашивает их маршрутом GET /scores. Функция loadScoresFromServer переводит серверное представление (там данные сгруппированы по именам судей) во внутренний формат таблицы и заново наполняет её. Из-за этого случайное обновление страницы или короткий сбой соединения не стирают протокол поединка — а для реальных соревнований это важно.

В сумме интеграция выстроена по событийной модели: любое действие пользователя рождает HTTP-запрос, а любое изменение состояния — WebSocket-уведомление для тех клиентов, кого оно касается. Так данные остаются согласованными на всех устройствах коллегии, и для этого не нужно ни синхронизировать их вручную, ни периодически опрашивать сервер.

## 3.5 Тестирование и проверка работоспособности

Тестирование — это проверка того, что готовая система действительно делает то, что от неё требовалось, и поиск дефектов до того, как её начнут использовать. Основным видом проверки выбрано функциональное тестирование: система рассматривается как «чёрный ящик», и проверяется, насколько правильно она реагирует на действия пользователей в типовых и граничных сценариях. Выбор объясняется спецификой проекта — здесь важнее всего корректность сквозных сценариев судейства, а они задействуют сразу и клиент, и сервер, и канал реального времени.

Проверка шла в условиях, близких к боевым: сервер запускался на компьютере под Windows, а клиентские устройства — ноутбук главного судьи и смартфоны боковых судей — подключались к нему по локальной сети Wi-Fi без доступа к Интернету. 1) ошибки сетевых запросов на клиенте перехватываются через try/catch и обработчики catch у промисов, так что при кратком пропадании сервера интерфейс не падает;

3) обрыв WebSocket-соединения сервер обрабатывает штатно — судья выбывает из списка подключённых, а главный судья получает обновлённый список;

5) ввод в форму создания раунда контролируется клиентской проверкой обязательных полей.

## 3.6 Экономическая эффективность и практический эффект от внедрения системы

Экономическая эффективность информационной системы — это, грубо говоря, соотношение пользы от её применения и затрат на её создание и эксплуатацию. Для систем, которые автоматизируют организационные процессы, польза проявляется прежде всего в трёх вещах: меньше трудозатрат, меньше ошибок, быстрее проходит сам процесс. Для этого проекта оценка практического эффекта особенно важна, ведь цель была не в изучении технологий ради технологий, а в решении конкретной задачи — убрать недостатки ручного судейства поединков по армейскому рукопашному бою.

Как судят сейчас. Боковые судьи записывают оценки на бумажные записки или в протоколы, потом секретарь или главный судья собирает эти записи, считает суммы с учётом штрафов и объявляет победителя. У такой схемы хватает слабых мест: время уходит на сбор и сверку записей после каждого поединка; при ручном счёте легко ошибиться в арифметике; до конца поединка никто не видит, как идёт оценивание; а спорные ситуации приходится разбирать дополнительно.

Разработанная система снимает эти проблемы за счёт нескольких эффектов.

1. Итоги подводятся быстрее. Суммы и финальный счёт считаются автоматически по ходу поступления оценок, поэтому результат поединка готов сразу после его окончания — этап сбора и сверки записок отпадает целиком.
2. Меньше ручной работы. Секретарю больше не нужно переписывать оценки в сводный протокол и пересчитывать их вручную; главный судья получает готовую таблицу с разбивкой по каждому судье и категории действий.
3. Меньше ошибок. Автоматический счёт убирает арифметические ошибки; контроль уникальности имён и серверная валидация не дают исказить протокол; а механизм отмены позволяет аккуратно поправить ошибочное нажатие.
4. Судейство прозрачнее. Главный судья видит оценки всех судей в реальном времени, поэтому расхождения в оценивании можно заметить вовремя, и спорных ситуаций становится меньше.
5. Соревнования идут быстрее. Пауза между поединками сокращается, а значит, за соревновательный день площадка успевает провести больше боёв.
6. Нет затрат на инфраструктуру. Система живёт в локальной сети без Интернета, собрана только на свободно распространяемых технологиях и не требует ни лицензий, ни специального оборудования — хватает ноутбука, точки доступа Wi-Fi и смартфонов судей, которые у организаторов и так есть.

Прикинем экономию времени в числах. При ручной схеме итоги одного поединка — это сбор записок трёх судей, подсчёт сумм с нокдаунами и штрафами, сверка и объявление; в среднем уходит [2–4] минуты. Польза от системы не сводится к экономии времени. Раз каждая оценка фиксируется электронно и привязана к судье и категории действия, на выходе получается подробный протокол поединка. Его можно использовать по-разному: разбирать качество судейства, учить начинающих судей, рассматривать апелляции. А низкий порог входа — один процесс на ноутбуке плюс QR-код на смартфонах судей — делает систему подъёмной для соревнований муниципального и регионального уровня, у которых нет бюджета на дорогие коммерческие решения.

## 3.7 Выводы по главе

В третьей главе описана практическая реализация информационной системы поддержки спортивного судейства в боевых искусствах и единоборствах. По итогам разработки можно сделать следующие выводы.

1. Реализована клиент-серверная архитектура: единственный серверный процесс на FastAPI совмещает роли REST-сервиса, WebSocket-маршрутизатора и веб-сервера статики, а интерфейсы главного и боковых судей собраны в одно одностраничное приложение на ReactJS с библиотекой компонентов Material UI.
2. Разработана серверная часть — с валидацией данных на моделях Pydantic, менеджером соединений ConnectionManager, который контролирует уникальность судей и ведёт идентификатор текущего раунда для журналирования, программным интерфейсом управления поединком и расширенным слоем доступа к базе SQLite: три таблицы (participants, rounds, round_scores) хранят справочник участников и хронологический журнал всех поединков с точностью до секунды.
3. Разработана клиентская часть, закрывающая весь цикл поединка: создание раунда с автодополнением участников, сводная таблица главного судьи с автоматическим подсчётом сумм и финального счёта, подключение судей по QR-коду, мобильный пульт с механизмом отмены действий и страница истории прошедших поединков с хронологическим журналом оценок и визуальной маркировкой отмен.
4. Части системы интегрированы по событийной модели: команды идут HTTP-запросами в JSON, а уведомления — по WebSocket, благодаря чему каждая оценка попадает в таблицу главного судьи в реальном времени; реализовано и восстановление состояния поединка при переподключении.
5. Проведено функциональное тестирование по пятнадцати сценариям — от типовых до граничных, включая тайбрейк, отмену модификатора нокдауна и нештатные ситуации. Все сценарии пройдены, а корректность автоматического подсчёта подтверждена сверкой с ручным подсчётом по регламенту.
6. Оценён практический эффект: система ускоряет подведение итогов, убирает арифметические ошибки ручного счёта, делает судейство прозрачнее и не требует затрат на лицензии и инфраструктуру — а значит, доступна соревнованиям регионального уровня.

Итак, разработанная система полностью отвечает требованиям, заданным на этапе проектирования, прошла проверку работоспособности во всех предусмотренных сценариях и готова к практическому применению для поддержки судейства поединков по армейскому рукопашному бою.
