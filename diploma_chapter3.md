Настоящая глава посвящена практической реализации распределённой системы судейства соревнований по боевым видам спорта, спроектированной во второй главе. ## 3.1 Структура и организация проекта

Исходный код разрабатываемой системы организован в виде единого корневого каталога `sorev-master`, в котором сосуществуют серверная и клиентская части. Подобная организация — так называемый «монорепозиторий» — выбрана сознательно. Серверная и клиентская части находятся в столь тесной функциональной связи, что их раздельное хранение в отдельных репозиториях не дало бы практической пользы: изменение схемы данных программного интерфейса требовало бы синхронных правок в обеих частях, что при раздельном хранении было бы неудобно для разработчика, ведущего проект в одиночку. Единое хранилище кода позволяет вносить согласованные изменения в обе части одной фиксацией изменений в системе управления версиями.

Рисунок 3.1 — Структура каталогов проекта

Содержимое каталога `backend` относится к серверной части системы. Файл `main.py` содержит весь исходный код серверного приложения: определения моделей данных, обработчики маршрутов программного интерфейса, обработчик протокола WebSocket и реализацию класса хранения состояния. Файл `participants.db` — это файл базы данных SQLite, содержащий справочник участников соревнований; он создаётся автоматически при первом запуске сервера. Каталог `venv` хранит изолированное окружение Python с установленными зависимостями, перечисленными в файле `requirements.txt`. Хранение окружения внутри каталога проекта обеспечивает воспроизводимость сборки: на любой машине, на которой установлен Python подходящей версии, развёртывание окружения сводится к выполнению одной команды установки пакетов из файла зависимостей.

Каталог `src` содержит исходный код клиентской части на языке JavaScript с применением библиотеки React. Точкой входа клиентского приложения является файл `main.jsx`, в котором корневой компонент `App` монтируется в дерево DOM-узлов браузера. Сам корневой компонент описан в файле `App.jsx`, его содержимое сводится к настройке маршрутизации между четырьмя страницами приложения. Каталог `Pages` содержит реализации этих четырёх страниц: `NewRoundPage` отвечает за создание нового раунда, `TablePage` — за интерфейс главного судьи с таблицей оценок, `NewJudgePage` — за подключение бокового судьи, `MobilePage` — за мобильный интерфейс выставления оценок. Каталог `Components` объединяет переиспользуемые компоненты пользовательского интерфейса, не привязанные к конкретной странице: квадратные кнопки оценок, ячейки таблицы, диалоговые окна. Каталог `api` содержит модуль `api.js`, инкапсулирующий все обращения клиентской части к серверу.

Файл `index.html` представляет собой шаблон корневого документа, в который инструмент сборки Vite встраивает скомпилированный код клиентского приложения. Файл `package.json` описывает зависимости и сценарии сборки, файл `vite.config.js` — настройки самого инструмента сборки. Каталог `node_modules` содержит установленные зависимости клиентской части и в систему управления версиями не помещается, поскольку может быть полностью восстановлен по содержимому файлов `package.json` и `package-lock.json`.

Каталог `dist` содержит скомпилированный пакет клиентского приложения, сформированный командой `npm run build`. Содержимое этого каталога — это набор статических файлов: оптимизированные сценарии JavaScript с хэшированными именами, файлы стилей CSS, документ HTML и сопутствующие ресурсы. Именно содержимое каталога `dist` раздаётся серверной частью через встроенный механизм статической раздачи библиотеки Starlette, лежащей в основе фреймворка FastAPI. Подобная схема обеспечивает то, что во время эксплуатации системы не требуется отдельный веб-сервер для клиентской части: один и тот же процесс Python и обрабатывает обращения программного интерфейса, и раздаёт клиентские файлы.

Конфигурация инструмента сборки Vite, определённая в файле `vite.config.js`, лаконична и сводится к подключению плагина для поддержки React и указанию выходного каталога:

```js
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  build: {
    outDir: "./dist",
    emptyOutDir: true,
  },
});
```

Свойство `emptyOutDir: true` обеспечивает очистку выходного каталога перед каждой сборкой, что исключает накопление в нём устаревших файлов от предыдущих сборок. Свойство `outDir: "./dist"` совпадает с относительным путём, по которому серверная часть ищет файлы клиентского приложения, что устраняет необходимость в дополнительной настройке после сборки.

Файл `package.json` определяет следующие сценарии работы с проектом: `dev` — запуск Vite в режиме разработки со встроенным сервером горячей перезагрузки модулей, `build` — формирование готового к развёртыванию пакета, `lint` — статическая проверка кода с помощью ESLint, `preview` — локальный предварительный просмотр собранного пакета. В число прямых зависимостей входят `react` и `react-dom` версии 18, библиотека маршрутизации `react-router-dom` версии 6, библиотека компонентов `@mui/material` версии 7 с пакетами `@emotion/react` и `@emotion/styled`, обеспечивающими механизм стилизации, и библиотека `qrcode.react`, применяемая для отрисовки QR-кодов на странице главного судьи. В число зависимостей разработки входят пакет `@vitejs/plugin-react`, плагин для языка JSX, статический анализатор ESLint и набор плагинов к нему, а также сам инструмент сборки Vite.

Файл `backend/requirements.txt` фиксирует точные версии зависимостей серверной части. В их число входят сам фреймворк FastAPI версии 0.135, лежащий в его основе фреймворк Starlette версии 0.52, библиотека валидации данных Pydantic версии 2.12, реализация asyncio-сервера Uvicorn версии 0.41 и библиотека `fastapi-offline` версии 1.7, обеспечивающая автономную работу интерактивной документации программного интерфейса. Фиксация точных версий — намеренное решение: оно гарантирует, что развёртывание серверной части на любой машине приведёт к получению идентичного по поведению окружения. В отсутствие подобной фиксации, при использовании заглавных версий или указаний типа «не ниже», обновление любой из зависимых библиотек могло бы привести к незаметному изменению поведения сервера, что особенно нежелательно в условиях эксплуатации на соревнованиях, где сбой системы недопустим.

## 3.2 Реализация серверной части

Серверная часть системы реализована единым модулем — файлом `main.py`, размещённым в каталоге `backend`. Подобный отказ от дробления серверного кода на множество модулей является сознательным архитектурным выбором, обусловленным общим объёмом кода (порядка двухсот строк) и тесной взаимосвязью между его частями. Вынесение, скажем, класса хранения состояния в отдельный модуль не привело бы к улучшению читаемости: для понимания работы системы по-прежнему было бы необходимо читать оба файла одновременно. Размещение всего кода в одном файле, напротив, упрощает навигацию и понимание потока выполнения, делая весь серверный код доступным для прочтения «сверху вниз» за один сеанс.

### 3.2.1 Инициализация базы данных при запуске модуля

Первое значимое действие, выполняемое при запуске серверного процесса, — это инициализация локальной базы данных SQLite. Соответствующий код размещён в начале файла, до импорта самого фреймворка FastAPI:

```python
import json
import os
import socket
import sqlite3
from typing import Dict, Union

DB_PATH = os.path.join(os.path.dirname(__file__), "participants.db")


def init_db():
    con = sqlite3.connect(DB_PATH)
    con.execute(
        "CREATE TABLE IF NOT EXISTS participants "
        "(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL UNIQUE)"
    )
    con.commit()
    con.close()


init_db()
```

Размещение вызова `init_db()` на верхнем уровне модуля, до создания экземпляра приложения, обеспечивает важное свойство: серверный процесс не сможет начать обслуживание запросов до тех пор, пока база данных не будет приведена в работоспособное состояние. Если в результате какого-либо отказа — отсутствия прав на запись, повреждения файла базы данных, нехватки места на диске — выполнение функции инициализации завершится с ошибкой, серверный процесс не запустится вовсе, и пользователь немедленно увидит соответствующее сообщение в выводе. Подобный подход, известный в инженерии программного обеспечения под названием «быстрого отказа», предпочтительнее отложенной диагностики, при которой ошибка обнаружилась бы лишь при первом обращении клиента к базе данных.

Использование инструкции `CREATE TABLE IF NOT EXISTS` обеспечивает идемпотентность операции: при повторных запусках сервера, когда таблица уже существует, инструкция выполняется без эффекта и не приводит к ошибке. Путь к файлу базы данных вычисляется на основании текущего расположения модуля через `os.path.dirname(__file__)`. Это гарантирует, что база данных всегда располагается в одном и том же каталоге относительно исходного кода, независимо от того, из какого рабочего каталога был запущен сервер. Если бы использовался относительный путь, например, `"participants.db"`, файл базы данных создавался бы в каталоге, из которого был выполнен запуск, что привело бы к разным базам данных при запуске сервера разными способами и к потере данных при смене способа запуска.

Структура таблицы `participants` соответствует спроектированной во второй главе модели: целочисленный первичный ключ с автоинкрементом и текстовое поле имени с ограничением уникальности. Уникальность имени — это не только нормализация данных, но и предпосылка для применения конструкции `INSERT OR IGNORE` при добавлении новых участников, описанной ниже.

### 3.2.2 Создание экземпляра приложения и настройка промежуточного программного обеспечения

После завершения инициализации базы данных модуль приступает к импорту средств фреймворка FastAPI и созданию экземпляра приложения:

```python
from fastapi import (
    FastAPI,
    WebSocket,
    WebSocketDisconnect,
)
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import HTMLResponse, JSONResponse
from fastapi.staticfiles import StaticFiles
from fastapi_offline import FastAPIOffline
from pydantic import BaseModel

app = FastAPIOffline()
```

Принципиальное значение имеет факт использования класса `FastAPIOffline` из библиотеки `fastapi-offline` вместо стандартного класса `FastAPI`. Внешне они эквивалентны: оба регистрируют маршруты, обрабатывают запросы и предоставляют интерактивную документацию программного интерфейса. Различие состоит в том, что стандартный класс `FastAPI` формирует страницу документации Swagger UI с обращениями к внешним сетям передачи статических файлов — в частности, к серверу `unpkg.com`, с которого загружаются JavaScript-файлы интерфейса документации и таблицы стилей. В условиях работы системы в полностью изолированной локальной сети подобные обращения завершаются ошибками сетевого таймаута, страница документации не отображается, что нарушает требование о работе системы без подключения к интернету. Класс `FastAPIOffline` решает эту проблему путём подмены адресов внешних ресурсов на локальные маршруты, обслуживаемые тем же серверным процессом; сами файлы Swagger UI входят в дистрибутив библиотеки и раздаются с локального диска.

Подключение каталога статических файлов осуществляется через метод `mount`:

```python
app.mount("/assets", StaticFiles(directory="../dist/assets/"), name="assets")
```

Относительный путь `../dist/assets/` указан с учётом того, что серверный процесс запускается из каталога `backend`; при запуске сервера из родительского каталога относительный путь необходимо скорректировать. Каталог `assets` создаётся инструментом сборки Vite и содержит хэшированные файлы JavaScript и CSS, на которые ссылается главный документ HTML.

Далее в коде определяется политика разделения ресурсов между доменами (CORS):

```python
origins = ["*"]

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Значение `"*"` в списке разрешённых источников означает, что обращения к программному интерфейсу принимаются с любого источника. Подобная конфигурация была бы недопустима для приложения, доступного через интернет, поскольку открыла бы возможность для межсайтовых обращений с произвольных страниц, ведущих к утечкам данных или несанкционированным действиям от имени пользователя. В рассматриваемой же системе данная конфигурация оправдана: сервер заведомо работает в изолированной локальной сети, в которой отсутствуют посторонние страницы, способные инициировать межсайтовые обращения. Допуск произвольного источника при таких условиях избавляет от необходимости вручную перечислять адреса всех мобильных устройств, подключающихся к серверу, что было бы практически невозможно: IP-адреса в локальной сети, как правило, выдаются динамически и заранее неизвестны. Указанный вопрос подробнее рассматривается в разделе 3.5, посвящённом безопасности.

### 3.2.3 Модели данных запросов

Структура тел приходящих на сервер запросов описывается классами, унаследованными от базового класса `BaseModel` библиотеки Pydantic:

```python
class Score(BaseModel):
    color: str
    judge: str
    punch: str
    score: int


class UndoScore(BaseModel):
    color: str
    judge: str
    punch: str
    score: int


class Participants(BaseModel):
    blue: str
    red: str

    def toJson(self):
        return json.dumps(self, default=lambda o: o.__dict__)


class ParticipantEntry(BaseModel):
    name: str
```

Модели `Score` и `UndoScore` намеренно сделаны структурно идентичными: и при добавлении новой оценки, и при её отмене сервер получает одни и те же сведения — цвет участника, имя судьи, вид технического действия и числовое значение. Сохранение этих моделей как двух отдельных классов, несмотря на их идентичность, обусловлено стремлением к выразительности кода: имя класса в сигнатуре функции-обработчика сообщает читателю о намерении не хуже, чем содержимое самого тела функции. В будущем, если состав полей одной из операций потребует расширения, разделение классов позволит внести изменения в одну из них без затрагивания другой.

Модель `Participants` описывает пару участников раунда — синего и красного. Метод `toJson` обеспечивает её сериализацию в текстовое представление JSON, применяемое при ответе на запрос текущих участников. Применение `lambda o: o.__dict__` в качестве функции преобразования делает сериализацию устойчивой к возможным расширениям модели: при добавлении новых полей они автоматически включатся в результат без правки самого метода. Модель `ParticipantEntry` описывает добавление одного участника в справочник базы данных и содержит единственное поле — имя.

Помимо собственно валидации Pydantic выполняет ещё одну важную функцию: при отсутствии обязательных полей или при несоответствии их типов клиенту автоматически возвращается структурированный ответ с указанием конкретного поля и природы ошибки. Это снимает с разработчика серверной логики обязанность вручную проверять каждое поле и обеспечивает единообразные диагностические сообщения для всех обработчиков, использующих модели Pydantic.

### 3.2.4 Определение сетевого адреса сервера

Особого описания заслуживает функция определения сетевого адреса, по которому сервер доступен в локальной сети. Указанный адрес необходим для формирования QR-кода, по которому боковые судьи подключаются к серверу со своих смартфонов:

```python
def get_local_ip():
    with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as s:
        try:
            s.connect(("8.8.8.8", 80))
            local_ip = s.getsockname()[0]
        except Exception:
            local_ip = "127.0.0.1"
    return local_ip
```

Прямолинейный способ узнать собственный сетевой адрес — обращение к функции `socket.gethostbyname(socket.gethostname())` — для рассматриваемой задачи не подходит. Эта функция возвращает адрес, ассоциированный с именем хоста, который во многих конфигурациях операционной системы соответствует значению `127.0.0.1`, то есть петлевому адресу, не доступному из других узлов локальной сети. Возвращение подобного значения привело бы к тому, что в QR-код был бы закодирован неработоспособный адрес.

Применённый в коде приём решает эту задачу иным способом. Создаётся сокет UDP, и для него инициируется условное соединение с произвольным внешним адресом — в качестве такого выбран адрес 8.8.8.8, принадлежащий публичной службе DNS компании Google. Фактическая передача данных по этому сокету не выполняется и фактическое соединение не устанавливается, поскольку UDP — протокол без установления соединения. Однако в процессе подготовки к мнимому соединению сетевой стек операционной системы выполняет важную работу: он анализирует таблицу маршрутизации, выбирает сетевой интерфейс, по которому шёл бы трафик до указанного внешнего адреса, и связывает с сокетом локальный IP-адрес этого интерфейса. Этот адрес можно получить вызовом `getsockname()`. В результате функция возвращает именно тот адрес, по которому ноутбук виден в локальной сети, — то есть адрес, выданный ему точкой доступа Wi-Fi.

Существенным является то, что соединение с внешним адресом не требует фактической достижимости этого адреса. Метод `connect()` для UDP-сокета не отправляет никаких пакетов и не требует ответа от удалённого узла; он лишь регистрирует параметры предполагаемого соединения в стеке протоколов. Это означает, что описанная функция корректно работает даже при полностью отключённом подключении к интернету, что критически важно для целевых условий эксплуатации.

Конструкция `with socket.socket(...) as s` гарантирует автоматическое закрытие сокета по завершении блока, в том числе при возникновении исключения, что предотвращает утечку файловых дескрипторов. Блок обработки исключений обеспечивает возврат петлевого адреса в случае каких-либо ошибок: подобное значение не позволит подключиться смартфонам, но позволит серверу продолжить работу, и пользователь увидит проблему в QR-коде (адрес 127.0.0.1 заметен глазом) вместо непонятной аварийной остановки сервера.

### 3.2.5 Класс хранения состояния `ConnectionManager`

Центральным элементом серверной части является класс `ConnectionManager`, инкапсулирующий всё временное состояние серверного процесса — словарь подключённых боковых судей, ссылку на постоянное соединение с главным судьёй и пару текущих участников раунда:

```python
class ConnectionManager:
    def __init__(self):
        self.connected_judges: Dict[str, WebSocket] = {}
        self.main_judge_ws: WebSocket
        self.participants: Participants = Participants(blue="", red="")
```

Поле `connected_judges` представляет собой словарь, ключами которого служат имена боковых судей, а значениями — установленные постоянные соединения WebSocket. Применение словаря, а не списка, обусловлено двумя соображениями. Во-первых, имена судей служат естественными идентификаторами, что делает обращение к соединению по имени операцией постоянной сложности. Во-вторых, словарная структура естественным образом исключает возможность регистрации двух соединений с одинаковым именем — попытка добавить запись с уже существующим ключом будет обнаружена явной проверкой до выполнения добавления.

Поле `main_judge_ws` хранит ссылку на постоянное соединение с главным судьёй. В отличие от соединений боковых судей, здесь хранится единственное значение, поскольку в архитектуре системы предусмотрен только один главный судья на серверный процесс. Аннотация типа `WebSocket` без значения по умолчанию подчёркивает, что поле подлежит инициализации в процессе работы системы — при первом установлении соединения главным судьёй; до этого момента обращение к полю приведёт к ошибке. Подобный подход — отказ от инициализации поля значением `None` — намеренно делает попытку обращения к незаполненному полю заметной: вместо того, чтобы тихо передать пустое значение в метод сериализации сообщения и получить неинформативное сообщение об ошибке, программа аварийно завершится с явным указанием на причину.

Поле `participants` хранит пару текущих участников раунда. Изначально оно инициализируется парой пустых строк, что соответствует ситуации перед началом первого раунда. После создания раунда соответствующий обработчик заполняет это поле фактическими именами участников. Хранение участников в полях экземпляра — а не в отдельной структуре, привязанной к каждому подключению, — отражает тот факт, что в любой момент времени в системе проводится только один раунд: участники едины для всех подключённых судей.

Метод `connect` отвечает за установление нового постоянного соединения. Его реализация заслуживает подробного рассмотрения:

```python
async def connect(self, websocket: WebSocket, judgeName):
    if judgeName in self.connected_judges:
        await websocket.close(code=4001)
        return False
    await websocket.accept()
    if judgeName == "mainJudge":
        self.main_judge_ws = websocket
    else:
        self.connected_judges[judgeName] = websocket
    print(
        f"{judgeName} connected. Judges online: {list(self.connected_judges.keys())}\n"
    )
    await self.update_connected_judges()
    return True
```

Первое действие метода — проверка, не подключён ли уже судья с указанным именем. Подобная ситуация может возникнуть, например, при перезагрузке страницы боковым судьёй: исходное соединение, не закрытое корректно, ещё некоторое время числится открытым на сервере, а новое подключение приходит с тем же именем. Если бы метод просто заменил старое соединение новым в словаре, возникла бы аномальная ситуация: на стороне сервера ссылка на исходное соединение оказалась бы утрачена без его явного закрытия, что привело бы к утечке сетевого ресурса. Применённое решение прямолинейно: при попытке подключения с уже занятым именем сервер закрывает новое соединение со специальным кодом ошибки 4001 — этот код относится к диапазону, зарезервированному стандартом RFC 6455 для использования в прикладных протоколах, — и возвращает признак неуспешного подключения. Клиентская часть, получив подобный код, отображает пользователю сообщение о невозможности подключения с занятым именем и предлагает указать другое.

При успешном прохождении проверки уникальности метод вызывает `accept()`, переводящий соединение в открытое состояние, и сохраняет соединение в соответствующем поле. Особый случай — подключение главного судьи: его имя `"mainJudge"` зарезервировано на уровне клиентского кода, и соответствующее соединение сохраняется в отдельном поле, а не в общем словаре боковых судей. Подобное разделение упрощает дальнейшую логику: при рассылке сообщений «главному судье» нет нужды искать его среди всех подключений по имени, и наоборот, при перечислении подключённых боковых судей не приходится исключать из списка главного судью.

Финальным действием метода служит вызов `update_connected_judges()`, информирующего главного судью о текущем составе подключённых боковых судей:

```python
async def update_connected_judges(self):
    await self.main_judge_ws.send_json(
        {"data": "judgeupd", "judges": list(self.connected_judges.keys())}
    )
```

Содержимое сообщения — это объект JSON с полем `data`, имеющим значение `"judgeupd"`, и полем `judges`, содержащим массив имён подключённых судей. Поле `data` служит маркером типа сообщения и используется клиентской частью для разветвления обработки в зависимости от поступившего события. Применение единственного типа сообщений `judgeupd` с полным списком текущих судей, а не отдельных сообщений «судья подключился» и «судья отключился», обеспечивает устойчивость к ситуациям рассогласования: если в результате какого-либо сбоя одно из сообщений будет утрачено, состояние клиентской части восстановится при первом же последующем обновлении. Подобный подход, известный под названием «идемпотентного обновления полным состоянием», получил широкое распространение в системах синхронизации данных, поскольку упрощает рассуждения о корректности по сравнению с моделью передачи дифференциальных изменений.

Метод `disconnect` обеспечивает корректное удаление записи о судье при разрыве соединения:

```python
async def disconnect(self, judgeName):
    if judgeName in self.connected_judges:
        del self.connected_judges[judgeName]
        print(
            f"{judgeName} disconnected. Remaining: {list(self.connected_judges.keys())}\n"
        )
    if judgeName == "mainJudge":
        return
    await self.update_connected_judges()
```

Метод предусматривает важный частный случай: при отключении главного судьи рассылка обновления списка подключённых судей не имеет смысла, поскольку именно главный судья является её адресатом — а его соединение в данный момент закрыто. Преждевременное обращение к закрытому соединению привело бы к необработанному исключению. Преждевременный возврат до вызова `update_connected_judges()` предотвращает это исключение и корректно завершает процедуру отключения.

Методы `send_score` и `send_undo` обеспечивают передачу оценок и их отмен главному судье:

```python
async def send_score(self, score: Score):
    await self.main_judge_ws.send_json(
        {
            "data": "score",
            "score": score.model_dump(),
        }
    )


async def send_undo(self, undo: UndoScore):
    await self.main_judge_ws.send_json(
        {
            "data": "undo",
            "undo": undo.model_dump(),
        }
    )
```

Метод `model_dump()` библиотеки Pydantic возвращает представление модели в виде обычного словаря Python, пригодного для последующей сериализации в текстовое представление JSON. Это представление встраивается в объект сообщения, к которому добавляется поле `data` с маркером типа: `"score"` для добавления новой оценки, `"undo"` для отмены. Маркер типа позволяет клиентскому коду главного судьи единообразно обрабатывать оба сценария — добавление и отмену — внутри одного обработчика входящих сообщений WebSocket.

Метод `connect_participant` устанавливает имена участников текущего раунда и рассылает их всем подключённым боковым судьям:

```python
async def connect_participant(self, participants: Participants):
    self.participants = participants
    print(f"Connected Participants {participants}\n")
    for key in self.connected_judges.keys():
        if key == "mainJudge":
            break
        await self.connected_judges[key].send_json(
            {"data": "participantupd", "participants": list(self.participants)}
        )
```

Метод обновляет поле `participants` экземпляра и затем последовательно отправляет каждому подключённому боковому судье сообщение с типом `"participantupd"`. Применение последовательного перебора, а не группового обращения через средства многозадачности типа `asyncio.gather`, обусловлено простотой задачи: при максимальном числе боковых судей, равном трём, потенциальный выигрыш от параллельной отправки пренебрежимо мал, а простота последовательного цикла существенно выше.

Метод `get_participants` возвращает текущих участников в виде строки JSON, готовой к передаче в ответе на соответствующий запрос. Если участники ещё не установлены, возвращается строка-маркер `"No participants"`:

```python
def get_participants(self):
    if self.participants:
        return self.participants.toJson()
    else:
        return "No participants"
```

Создание экземпляра `manager = ConnectionManager()` на уровне модуля, после определения класса, обеспечивает наличие единственного хранилища состояния на весь серверный процесс. Все функции-обработчики маршрутов обращаются именно к этому экземпляру; альтернатива в виде хранения состояния в глобальных переменных уровня модуля была бы менее упорядоченной, поскольку приводила бы к разрозненным глобальным именам, обращение к которым из вложенных функций требовало бы дополнительных декларативных средств.

### 3.2.6 Реализация конечных точек REST API

Реализация конечных точек REST API в большинстве случаев сводится к делегированию работы экземпляру `ConnectionManager`. Подобный приём — использование функций-обработчиков как тонких адаптеров между протоколом HTTP и внутренним программным интерфейсом — известен под названием «контроллера» и широко применяется в архитектуре современных веб-приложений. Преимущество этого приёма состоит в том, что бизнес-логика, сосредоточенная в методах класса хранения состояния, не зависит от транспортного протокола и может быть протестирована без поднятия HTTP-сервера.

Простейшая конечная точка `POST /connect_judge` возвращает пустую строку и в текущей реализации не выполняет никаких действий:

```python
@app.post("/connect_judge")
async def connect_judge():
    return ""
```

Может показаться, что подобная конечная точка избыточна и подлежит удалению. Однако её сохранение в составе программного интерфейса оправдано на перспективу: клиентская часть со страницы подключения вызывает её при подтверждении ввода имени, и расширение функциональности — например, добавление валидации имени по списку запрещённых, или начисление метки времени подключения — потребует лишь правки реализации обработчика, без необходимости изменять клиентский код. Подобный подход — выделение точки расширения заранее, до её фактического заполнения смыслом, — оправдан в условиях, когда стоимость изменения сетевого взаимодействия выше стоимости поддержания пустого обработчика.

Конечная точка `GET /local_ip` возвращает локальный IP-адрес сервера, вычисляемый описанной выше функцией:

```python
@app.get("/local_ip")
async def get_local_ip_route():
    return JSONResponse(content={"local_ip": get_local_ip()})
```

Применение класса `JSONResponse` вместо возврата словаря напрямую обеспечивает гарантированную сериализацию ответа в формате JSON независимо от настроек кодирования по умолчанию, что важно для устойчивости поведения в различных окружениях.

Конечная точка `GET /kick_judge/{judge}` обеспечивает принудительное отключение бокового судьи главным судьёй:

```python
@app.get("/kick_judge/{judge}")
async def kick_judge(judge: str):
    await manager.disconnect(judge)
```

Имя отключаемого судьи передаётся в составе самого адреса конечной точки. Применение метода HTTP `GET` для операции, изменяющей состояние, формально не соответствует принципам идемпотентности, лежащим в основе REST: согласно этим принципам, операции с побочными эффектами должны выполняться методом `POST` или `DELETE`. Однако в условиях рассматриваемой системы, работающей в изолированной локальной сети, теоретический риск, связанный с побочными эффектами `GET`-запроса — а именно возможность их случайного выполнения при индексации поисковыми роботами или кэширования промежуточными прокси-серверами, — заведомо отсутствует. Выбор `GET`-метода продиктован практическим удобством: подобная конечная точка может быть вызвана непосредственно из адресной строки браузера в случае необходимости срочного отключения судьи без участия клиентского интерфейса.

Конечные точки `POST /send_score` и `POST /undo_score` обрабатывают передачу оценок и их отмен:

```python
@app.post("/send_score")
async def send_score(score: Score):
    await manager.send_score(score)


@app.post("/undo_score")
async def undo_score(undo: UndoScore):
    await manager.send_undo(undo)
```

Сигнатура каждой функции содержит параметр с типом, соответствующим одной из Pydantic-моделей. Фреймворк FastAPI автоматически десериализует тело запроса и проверяет его на соответствие схеме модели до передачи управления функции-обработчику. В случае несоответствия — например, при отсутствии обязательного поля или при передаче строки в поле, объявленном целым числом — фреймворк сам возвращает клиенту ответ с кодом 422 Unprocessable Entity и структурированным описанием ошибки. Это избавляет автора обработчика от необходимости вручную писать проверки полей.

Конечные точки работы со справочником участников в базе данных реализованы как обычные функции, без объявления `async`:

```python
@app.get("/db/participants")
def get_db_participants():
    con = sqlite3.connect(DB_PATH)
    rows = con.execute("SELECT id, name FROM participants ORDER BY name").fetchall()
    con.close()
    return [{"id": r[0], "name": r[1]} for r in rows]


@app.post("/db/participants")
def create_db_participant(entry: ParticipantEntry):
    con = sqlite3.connect(DB_PATH)
    con.execute("INSERT OR IGNORE INTO participants (name) VALUES (?)", (entry.name,))
    con.commit()
    row = con.execute("SELECT id, name FROM participants WHERE name = ?", (entry.name,)).fetchone()
    con.close()
    return {"id": row[0], "name": row[1]}
```

Отказ от асинхронности при работе с базой данных намеренный. Модуль `sqlite3` стандартной библиотеки Python предоставляет исключительно блокирующий программный интерфейс: каждый запрос выполняется синхронно и блокирует поток выполнения до получения результата. Объявление функции-обработчика как `async` не имело бы смысла, поскольку внутри неё всё равно выполняются синхронные операции, в течение которых цикл событий заблокирован. FastAPI корректно справляется с обычными (синхронными) функциями-обработчиками: он запускает их в отдельном потоке из пула рабочих потоков, что освобождает основной поток с циклом событий для обработки других запросов. Подобный подход даёт ожидаемое поведение без введения сложности, связанной с использованием асинхронных драйверов баз данных — последние более востребованы в системах с высокой нагрузкой и продолжительными запросами, что не относится к разрабатываемой системе.

Запрос `INSERT OR IGNORE` обеспечивает идемпотентность операции добавления: при наличии записи с тем же именем команда вставки не выполняется, и не порождается исключение. После вставки выполняется отдельный запрос `SELECT` для получения идентификатора записи — независимо от того, была ли она создана текущим запросом или уже существовала ранее. Возвращаемый объект содержит и идентификатор, и имя, что позволяет клиентской части сразу после добавления участника обновить свой локальный список без выполнения отдельного запроса на чтение.

Параметризация запросов через символы-заполнители `?` и кортеж значений в качестве второго аргумента метода `execute()` — это рекомендуемый и единственно безопасный способ передачи пользовательских данных в SQL-запрос. Модуль `sqlite3` обеспечивает корректное экранирование значений при подстановке: даже если в имени участника будут содержаться символы, имеющие специальное значение в SQL — кавычки, точки с запятой, — они будут трактованы как часть строкового значения, а не как часть синтаксиса запроса. Подробнее вопросы защиты от SQL-инъекций рассматриваются в разделе 3.5.

Конечная точка `POST /connect_participants` устанавливает участников текущего раунда:

```python
@app.post("/connect_participants")
async def connect_participants(participants: Participants):
    await manager.connect_participant(participants)
    return "Successfully connected participants"


@app.get("/participants")
def get_participants():
    return manager.get_participants()
```

Конечная точка `GET /participants` дополняет предыдущую: она возвращает текущих участников, что необходимо для восстановления состояния клиентской части после перезагрузки страницы.

### 3.2.7 Обработчик протокола WebSocket

Обработчик WebSocket является ключевым элементом серверной части, обеспечивающим синхронизацию состояния в реальном времени:

```python
@app.websocket("/ws/{judgeName}")
async def websocket_endpoint(websocket: WebSocket, judgeName: str):
    connected = await manager.connect(websocket, judgeName)
    if not connected:
        return
    try:
        while True:
            await websocket.receive_text()
    except WebSocketDisconnect:
        await manager.disconnect(judgeName)
```

Параметр пути `{judgeName}` позволяет каждому клиенту устанавливать индивидуальное соединение с уникальным адресом, что упрощает идентификацию соединения на сервере: имя судьи известно из самого адреса и не требует отдельной авторизации. Главный судья подключается по фиксированному адресу `/ws/mainJudge`.

Метод `connect()` менеджера соединений возвращает признак успешности подключения. Если подключение отклонено в связи с тем, что имя уже занято (см. описание метода `connect` выше), обработчик завершает работу и возвращается, не входя в цикл чтения сообщений.

Бесконечный цикл `while True: await websocket.receive_text()` служит ключевой особенностью реализации. В рамках текущей логики приложения сервер не ожидает от клиентов входящих сообщений по каналу WebSocket — все клиентские воздействия передаются через REST-запросы. Тем не менее, цикл чтения необходим для обнаружения момента разрыва соединения: метод `receive_text()` при разорванном соединении порождает исключение `WebSocketDisconnect`, перехват которого позволяет корректно удалить запись о клиенте из менеджера соединений. Без подобного цикла сервер не узнал бы о закрытии клиентского соединения, и запись о клиенте оставалась бы в словаре подключённых судей даже после фактического отключения.

### 3.2.8 Обработка одностраничного приложения

Завершающим элементом серверной части является универсальный обработчик, отдающий клиентское приложение по любому неизвестному адресу:

```python
@app.get("/{full_path:path}", response_class=HTMLResponse)
async def spa(full_path: str):
    path = os.path.join("../dist", full_path)
    if os.path.isfile(path):
        return HTMLResponse(open(path, "r", encoding="utf-8").read())
    return HTMLResponse(open("../dist/index.html", "r", encoding="utf-8").read())
```

Подобный обработчик необходим для корректной работы клиентской маршрутизации, реализованной библиотекой React Router. Клиентская часть определяет четыре маршрута: `/`, `/table`, `/connect`, `/mobile`. Если боковой судья откроет на смартфоне адрес `/connect`, перейдя по ссылке из QR-кода, сервер должен вернуть всё то же одностраничное приложение, а не сообщение об ошибке 404 Not Found, — после чего клиентский маршрутизатор уже на стороне браузера выберет нужный экран по адресу.

Реализация работает следующим образом. Сначала вычисляется потенциальный путь к файлу на диске, путём конкатенации каталога `dist` и переданного пути. Если такой файл существует — например, при обращении по адресу `/index.html` или `/manifest.json` — он возвращается клиенту с прочитанным содержимым. В противном случае возвращается содержимое корневого документа `index.html`, который, в свою очередь, через тег `<script>` загрузит весь сценарий клиентского приложения, и тот по адресной строке самостоятельно определит, какой экран отобразить.

Использование параметра `full_path:path` в адресе маршрута, в отличие от `full_path:str`, важно: оно позволяет включить в параметр символы косой черты, то есть охватить адреса любой глубины вложенности, что необходимо для возможного будущего расширения путей.

Наличие подобного обработчика на уровне `GET`-запросов также имеет любопытное побочное свойство: он перехватывает все необработанные другими маршрутами обращения, тем самым полностью скрывая факт существования других маршрутов от случайного посетителя. Это не подменяет собой систему контроля доступа, но создаёт элементарное препятствие для автоматизированного перебора путей.

## 3.3 Реализация клиентской части

Клиентская часть разрабатываемой системы представляет собой одностраничное приложение, написанное на языке JavaScript с применением библиотеки React версии 18. Все экраны приложения исполняются в рамках единого процесса браузера, а переходы между ними не сопровождаются обращениями к серверу за новым документом HTML, что обеспечивает мгновенный отклик при навигации. В настоящем разделе последовательно рассматриваются точка входа приложения, корневой компонент с настройкой маршрутизации, реализации каждой из четырёх страниц, переиспользуемые компоненты пользовательского интерфейса и модуль обращений к программному интерфейсу сервера.

### 3.3.1 Точка входа и корневой компонент

Точкой входа клиентского приложения служит файл `main.jsx`, в котором корневой компонент `App` монтируется в дерево узлов DOM браузера. Содержимое самого компонента `App` сосредоточено в одноимённом файле и сводится к настройке маршрутизации между четырьмя экранами приложения:

```jsx
import "./global.css";
import { BrowserRouter as Router, Routes, Route } from "react-router-dom";
import { MobilePage, NewJudgePage, NewRoundPage, TablePage } from "./Pages";

function App() {
  return (
    <Router>
      <Routes>
        <Route path="/" element={<NewRoundPage />} />
        <Route path="/mobile" element={<MobilePage />} />
        <Route path="/table" element={<TablePage />} />
        <Route path="/connect" element={<NewJudgePage />} />
      </Routes>
    </Router>
  );
}

export default App;
```

Компонент `Router` библиотеки React Router (импортированный под псевдонимом `BrowserRouter`) обеспечивает синхронизацию состояния приложения с адресной строкой браузера. Компонент `Routes` выбирает один из вложенных в него компонентов `Route` на основании текущего адреса. Каждый компонент `Route` связывает шаблон адреса со ссылкой на компонент, который должен быть отрисован при совпадении.

Четыре маршрута соответствуют четырём логическим состояниям системы. По корневому адресу `/` отображается страница создания нового раунда. По адресу `/table` — интерфейс главного судьи со сводной таблицей оценок. По адресу `/connect` — страница ввода имени боковым судьёй, открываемая после сканирования QR-кода. По адресу `/mobile` — собственно мобильный интерфейс выставления оценок, на который попадает боковой судья после ввода имени.

Импорт компонентов страниц осуществляется единой инструкцией из подкаталога `Pages`, в котором определён файл `index.js`, реэкспортирующий все компоненты страниц. Подобный приём — формирование «бочкообразного» файла на уровне каталога — позволяет потребителям ссылаться на каталог целиком, без указания конкретного файла, что облегчает изменение внутренней структуры каталога при сохранении обратной совместимости импортов.

### 3.3.2 Страница создания раунда

Компонент `NewRoundPage` соответствует корневому адресу приложения и отображается при первом запуске сервера и открытии браузера. Его назначение — приём ФИО двух участников предстоящего поединка с возможностью автоматического дополнения вводимого текста по справочнику базы данных и сохранения новых имён в этом справочнике.

Состояние компонента поддерживается через несколько ловушек состояния `useState`:

```jsx
const [inputs, setInputs] = useState({ blue: "", red: "" });
const [errors, setErrors] = useState({ blue: "", red: "" });
const [dbParticipants, setDbParticipants] = useState([]);
const [saveDialogOpen, setSaveDialogOpen] = useState(false);
const [newNames, setNewNames] = useState([]);
```

Состояние `inputs` хранит текущие значения, введённые пользователем в поля ФИО синего и красного участников. Состояние `errors` хранит сообщения об ошибках валидации формы. Состояние `dbParticipants` хранит копию справочника участников, загруженного с сервера. Состояние `saveDialogOpen` управляет видимостью диалога предложения сохранить новых участников, а состояние `newNames` хранит имена, которые подлежат сохранению.

Загрузка справочника осуществляется в эффекте, выполняемом при первичной отрисовке компонента:

```jsx
useEffect(() => {
  fetchDbParticipants()
    .then(setDbParticipants)
    .catch((err) => console.error("Error fetching participants:", err));
}, []);
```

Передача функции `setDbParticipants` непосредственно в качестве обработчика разрешения промиса — стилистический приём, эквивалентный записи `.then(data => setDbParticipants(data))`, но более лаконичный. Пустой массив зависимостей в качестве второго аргумента `useEffect` обеспечивает однократное выполнение эффекта — при монтировании компонента; при последующих перерисовках, вызванных изменениями состояния, эффект не запускается повторно.

Поля ввода имён реализованы с использованием компонента `Autocomplete` библиотеки Material UI в режиме `freeSolo`:

```jsx
<Autocomplete
  freeSolo
  options={participantNames}
  value={inputs.blue}
  onInputChange={handleChange("blue")}
  renderInput={(params) => (
    <TextField
      {...params}
      label="ФИО Синий"
      error={!!errors.blue}
      helperText={errors.blue}
    />
  )}
/>
```

Свойство `freeSolo` принципиально для рассматриваемой задачи. В обычном режиме компонент `Autocomplete` допускает ввод исключительно значений из переданного списка — попытка ввести произвольный текст, не совпадающий ни с одной из предложенных опций, по завершении ввода отбрасывается. Подобное поведение неприемлемо для рассматриваемой системы, поскольку при первых запусках справочник участников ещё пуст, и пользователь должен иметь возможность ввести произвольное имя. Режим `freeSolo` сохраняет всю функциональность автодополнения — выпадающий список совпадений, навигация стрелками клавиатуры, выбор клавишей Enter — но дополнительно допускает ввод произвольных значений, которые в списке отсутствуют.

Свойство `options` принимает массив строк, среди которых компонент ищет совпадения по подстроке с введённым пользователем текстом. Поскольку справочник участников возвращается сервером в виде массива объектов вида `{id, name}`, в компоненте выполняется промежуточное преобразование к массиву строк имён:

```jsx
const participantNames = dbParticipants.map((p) => p.name);
```

Подобное преобразование при каждой перерисовке компонента не приводит к существенным накладным расходам, поскольку реальный размер справочника редко превышает несколько сотен имён.

Обработчик отправки формы реализует проверку на наличие в справочнике каждого из введённых имён. Если хотя бы одно из имён отсутствует, открывается диалог с предложением сохранить эти имена в справочнике для последующих раундов:

```jsx
const handleSubmit = async (e) => {
  e.preventDefault();
  if (!validate()) return;

  const unknown = [inputs.blue, inputs.red].filter(
    (name) => !participantNames.includes(name)
  );

  if (unknown.length > 0) {
    setNewNames(unknown);
    setSaveDialogOpen(true);
  } else {
    await createRound();
  }
};
```

Метод `e.preventDefault()` подавляет стандартное поведение формы — отправку данных через перезагрузку страницы — что необходимо для управления потоком ввода полностью на стороне клиента. Функция `validate()` проверяет непустоту обеих строк имён и в случае нарушения заполняет состояние `errors` сообщениями об ошибках, отображаемыми в соответствующих полях.

Диалог сохранения новых участников предлагает пользователю два действия: сохранить новых участников в справочнике и продолжить, либо продолжить без сохранения. В первом случае последовательно вызывается метод добавления для каждого нового имени:

```jsx
const handleSave = async () => {
  setSaveDialogOpen(false);
  await Promise.all(newNames.map(createDbParticipant));
  await createRound();
};
```

Применение `Promise.all` обеспечивает параллельное выполнение всех запросов на добавление, что несколько ускоряет процесс по сравнению с последовательным выполнением, хотя выигрыш ничтожен при характерных размерах массива (два элемента максимум). Завершающее действие в обоих случаях — вызов `createRound()`, который отправляет на сервер выбранные имена участников и переводит пользователя на страницу `/table`:

```jsx
const createRound = async () => {
  await connectParticipants(inputs);
  navigate("/table");
};
```

Функция `navigate`, полученная из ловушки `useNavigate()` библиотеки React Router, обеспечивает программный переход между маршрутами без перезагрузки страницы.

### 3.3.3 Страница подключения бокового судьи

Компонент `NewJudgePage` соответствует адресу `/connect` и отображается при открытии браузера смартфона по ссылке из QR-кода. Назначение страницы — приём имени бокового судьи и установление его связи с серверной частью:

```jsx
export const NewJudgePage = () => {
  const [judgeName, setJudgeName] = useState("");
  const navigate = useNavigate();

  const handleSubmit = async (e) => {
    e.preventDefault();
    try {
      const response = await connectJudge(judgeName);
      if (response.ok) {
        localStorage.setItem("judgeName", judgeName);
        navigate("/mobile");
      }
    } catch (error) {
      console.error("Error sending judge name to server", error);
    }
  };
  // ...
};
```

Принципиально важным является сохранение имени судьи в локальное хранилище браузера через `localStorage.setItem`. Подобное хранилище сохраняет данные между сеансами работы браузера и переживает перезагрузку страницы, что необходимо для устойчивости работы мобильного интерфейса: если боковой судья случайно проведёт пальцем сверху вниз по экрану и инициирует обновление страницы — типичный жест на смартфонах — мобильный интерфейс восстановит имя судьи из локального хранилища и продолжит работу без необходимости повторного сканирования QR-кода и ввода имени.

После успешного выполнения запроса `connectJudge` происходит переход на страницу `/mobile`, на которой будет установлено постоянное соединение WebSocket с сервером. Сама конечная точка `/connect_judge` в текущей реализации, как было показано выше, возвращает пустую строку и не несёт смысловой нагрузки; её вызов сохраняется как точка возможного будущего расширения логики подключения.

### 3.3.4 Мобильный интерфейс выставления оценок

Компонент `MobilePage` представляет собой наиболее активно используемую часть клиентского приложения. Именно с этим компонентом непосредственно работают боковые судьи в течение всего поединка, и от его удобства и надёжности зависит качество судейства.

Состояние компонента поддерживается через сочетание нескольких механизмов React:

```jsx
const [judgeName, setJudgeName] = useState("");
const [participants, setParticipants] = useState({
  blueName: "",
  redName: "",
});
const [kicked, setKicked] = useState(false);
const [roundEnded, setRoundEnded] = useState(false);
const [tiebreaker, setTiebreaker] = useState(false);
const [scoreHistory, setScoreHistory] = useState([]);
const localScoresRef = useRef({ blue: 0, red: 0 });
```

Состояние `judgeName` хранит имя бокового судьи, восстановленное из локального хранилища. Состояние `participants` хранит имена текущих участников раунда, поступающие от сервера. Логические состояния `kicked`, `roundEnded` и `tiebreaker` управляют видимостью трёх диалоговых окон: уведомления о принудительном отключении, уведомления о завершении раунда и диалога выбора победителя при тайбрейке соответственно.

Состояние `scoreHistory` содержит массив выставленных судьёй оценок в порядке их выставления. Каждая запись массива содержит четыре поля: имя судьи, вид технического действия, цвет участника и числовое значение оценки. Данная структура необходима для двух целей. Во-первых, она позволяет отобразить рядом с каждой кнопкой счётчик, показывающий, сколько раз эта кнопка была нажата в текущем раунде. Во-вторых, она хранит запись о последнем действии судьи, что позволяет реализовать функцию отмены.

Особо следует обратить внимание на использование ловушки `useRef` вместо `useState` для поля `localScoresRef`. Содержимое объекта, хранимого в `useRef`, может быть изменено без вызова повторной отрисовки компонента, что принципиально для рассматриваемой задачи: счётчики локальных очков обновляются при каждом нажатии кнопки, но не должны вызывать визуального обновления компонента, поскольку соответствующих визуальных элементов на мобильном интерфейсе нет. Применение `useState` привело бы к избыточным перерисовкам, не дающим визуального эффекта.

Содержимое `localScoresRef` — это пара числовых значений суммарных очков синего и красного участников по версии данного бокового судьи. Назначение этого хранилища станет ясно из дальнейшего разбора: оно позволяет определить факт ничейного счёта непосредственно на стороне мобильного клиента, без обращения к серверу за подтверждением, что обеспечивает мгновенную реакцию интерфейса при завершении раунда с равными очками.

Загрузка имени судьи и текущих участников осуществляется в эффекте при монтировании компонента:

```jsx
useEffect(() => {
  setJudgeName(localStorage.getItem("judgeName"));
  fetchParticipants()
    .then((data) => {
      setParticipants({ blueName: data.blue, redName: data.red });
    })
    .catch(() => {});
}, []);
```

Имя судьи восстанавливается из локального хранилища, обеспечивая устойчивость к перезагрузке страницы. Текущие участники запрашиваются с сервера: эти сведения могут понадобиться, если боковой судья подключился к серверу уже после того, как главный судья установил участников раунда. Пустой обработчик ошибки `.catch(() => {})` подавляет диагностическое сообщение в случае, когда участники ещё не установлены, что является нормальной ситуацией перед началом первого раунда.

Подключение к серверу по протоколу WebSocket выполняется в отдельном эффекте, зависящем от имени судьи:

```jsx
useEffect(() => {
  const ws = new WebSocket(
    `ws://${window.location.hostname}:8000/ws/${judgeName}`,
  );

  ws.onopen = () => {
    console.log("Connected to server");
  };

  ws.onmessage = (event) => {
    let data = JSON.parse(event.data);
    if (data.data === "participantupd") {
      setParticipants({
        blueName: data.participants[0][1],
        redName: data.participants[1][1],
      });
    } else if (data.data === "kicked") {
      setKicked(true);
    } else if (data.data === "roundend") {
      if (localScoresRef.current.blue === localScoresRef.current.red) {
        setTiebreaker(true);
      } else {
        setRoundEnded(true);
      }
      localScoresRef.current = { blue: 0, red: 0 };
    }
  };
  return () => ws.close();
}, [judgeName]);
```

Зависимость эффекта от `judgeName` обеспечивает повторное установление соединения при изменении имени судьи. На практике подобное изменение происходит однократно — при первой загрузке компонента, когда `judgeName` меняется с пустой строки на значение, восстановленное из локального хранилища. Возвращаемая из эффекта функция выполняет «уборку»: при размонтировании компонента или повторном запуске эффекта она вызывает `ws.close()`, обеспечивая корректное закрытие соединения. Без подобной уборки при каждом запуске эффекта открывалось бы новое соединение, а предыдущие оставались бы открытыми, что в итоге привело бы к утечке сетевых ресурсов.

Обработчик входящих сообщений `onmessage` разветвляется по типу сообщения, определяемому полем `data`. При получении сообщения `participantupd` обновляется состояние участников; индексация `data.participants[0][1]` и `data.participants[1][1]` отражает особенность сериализации объекта `Participants` на стороне сервера: при преобразовании модели Pydantic в список через `list()` получается массив пар «ключ — значение», то есть `[["blue", "имя синего"], ["red", "имя красного"]]`, и второй элемент каждой пары — это собственно имя.

При получении сообщения `kicked` устанавливается флаг отображения диалога принудительного отключения. При получении сообщения `roundend` производится разветвление: если согласно локальным подсчётам очки участников равны, открывается диалог тайбрейка; в противном случае — диалог простого завершения раунда. В обоих случаях локальные счётчики обнуляются для подготовки к следующему раунду.

Принципиально важна именно локальная проверка ничейного счёта, не требующая обращения к серверу. Альтернативный вариант — запрос к серверу за актуальной суммой очков по версии всех судей — был бы существенно медленнее: даже в локальной сети дополнительный круговой обмен сообщениями добавил бы десятки миллисекунд задержки. Кроме того, ничейный счёт на уровне отдельного бокового судьи — это лишь предварительное условие тайбрейка: само окончательное решение о проведении тайбрейка принимается на стороне главного судьи, где известно состояние очков по версии всех трёх судей. Однако на мобильном интерфейсе судьи достаточно сравнить лишь собственные подсчёты: если они равны, главный судья гарантированно инициирует процедуру тайбрейка, и судью нужно подготовить к голосованию.

Обработчик нажатия кнопки оценки реализован следующим образом:

```jsx
const handleScoreClick = (punch, color, score) => {
  if (score === 4) {
    const punchColorHistory = scoreHistory.filter(
      (h) => h.punch === punch && h.color === color,
    );
    if (punchColorHistory.length === 0) return;
    const lastAction = punchColorHistory[punchColorHistory.length - 1];
    if (lastAction.score === 4 || lastAction.score === 5) return;
  }

  const data = { judge: judgeName, punch: punch, color: color, score: score };
  postScore(data).then((data) => console.log("Success: ", data));

  setScoreHistory((prev) => [
    ...prev,
    { judge: judgeName, punch, color, score },
  ]);
  // ... обновление localScoresRef ...
};
```

Особого внимания заслуживает блок валидации, выполняемый перед отправкой нажатия со значением 4. Значение 4 представляет собой модификатор «Нокдаун» — добавку трёх очков к предыдущему техническому действию. По регламенту соревнований нокдаун может применяться только к зачётному техническому действию того же вида (удар рукой, удар ногой или бросок) и того же участника; нельзя применить нокдаун к замечанию или предупреждению, и нельзя применить нокдаун к уже выставленному нокдауну. Соответствующая логика реализована проверкой истории: отфильтровываются все ранее выставленные оценки данного судьи по тому же виду действия и тому же цвету, и анализируется последняя из них. Если её значение совпадает со значением 4 (то есть уже является нокдауном) или со значением 5 (соответствует предупреждению — оно никогда не появляется в фильтре по «полезным» техническим действиям, но проверка оставлена для дополнительной защиты), нажатие игнорируется. Если же истории по данному виду действия и цвету ещё нет вовсе, нажатие также игнорируется, поскольку применять нокдаун не к чему.

Подобный приём валидации на стороне клиента — это не замена аналогичной проверки на стороне сервера, а средство повышения отзывчивости интерфейса: ошибочное нажатие отклоняется немедленно, без обращения к серверу. Серверная сторона при текущей реализации не выполняет аналогичной проверки; её добавление возможно в будущих версиях системы как защита от расхождения логики.

После прохождения валидации обработчик отправляет данные оценки на сервер через функцию `postScore`, добавляет запись в локальную историю и обновляет локальные счётчики `localScoresRef`. Логика обновления счётчиков учитывает регламент: для замечания (`"remark"`) добавляется одно очко противоположному цвету, для предупреждения (`"warn"`) — два очка, для остальных типов действий — фактическое значение оценки, причём для нокдауна (значение 4) к собственному цвету добавляется не четыре, а три очка (поскольку нокдаун — это модификатор, добавляющий +3 к базе).

```jsx
if (punch === "remark") {
  const opposingColor = color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] + 1,
  };
} else if (punch === "warn") {
  const opposingColor = color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] + 2,
  };
} else {
  const delta = score === 4 ? 3 : score;
  localScoresRef.current = {
    ...localScoresRef.current,
    [color]: localScoresRef.current[color] + delta,
  };
}
```

Обработчик функции отмены `handleUndo` извлекает последнее действие из истории, отправляет на сервер запрос на отмену через функцию `undoScore` и обновляет локальные счётчики, вычитая ранее добавленные значения:

```jsx
const handleUndo = () => {
  if (scoreHistory.length === 0) return;
  const lastAction = scoreHistory[scoreHistory.length - 1];
  undoScore({
    judge: lastAction.judge,
    punch: lastAction.punch,
    color: lastAction.color,
    score: lastAction.score,
  });
  // ... вычитание из localScoresRef ...
  setScoreHistory((prev) => prev.slice(0, -1));
};
```

Логика обновления `localScoresRef` симметрична логике в `handleScoreClick`: для замечания вычитается одно очко из противоположного цвета, для предупреждения — два, для остальных видов действий — фактическое значение (или 3 для нокдауна) из собственного цвета. Это обеспечивает корректность локального счёта после отмены любой выставленной оценки.

Обработчик выбора победителя при тайбрейке отправляет на сервер оценку с особым видом действия `"tiebreak"` и значением 1:

```jsx
const handleTiebreakerChoice = (color) => {
  postScore({ judge: judgeName, punch: "tiebreak", color, score: 1 });
  setTiebreaker(false);
};
```

Применение того же программного интерфейса передачи оценок для процедуры тайбрейка — с особым значением поля `punch` — позволяет избежать введения отдельной конечной точки и отдельной структуры данных. Серверная и клиентская части единообразно обрабатывают такие оценки: они отображаются в сводной таблице главного судьи как дополнительные оценки, а при подсчёте суммы учитываются как обычные с положительным вкладом 1.

Подсчёт количества нажатий каждой кнопки реализован через мемоизированное вычисление:

```jsx
const scoreCounts = useMemo(() => {
  const counts = {};
  scoreHistory.forEach(({ punch, color, score }) => {
    const key = `${punch}-${color}-${score}`;
    counts[key] = (counts[key] || 0) + 1;
  });
  return counts;
}, [scoreHistory]);

const getCount = (punch, color, score) => {
  return scoreCounts[`${punch}-${color}-${score}`] || 0;
};
```

Ловушка `useMemo` обеспечивает пересчёт словаря `counts` только при изменении массива `scoreHistory`; при последующих перерисовках компонента, не связанных с изменением истории — например, при изменении состояния диалога — ранее вычисленный словарь используется повторно. Подобная оптимизация заметно сокращает накладные расходы на отрисовку, особенно к концу длительного раунда, когда количество выставленных оценок может достигать нескольких десятков.

Каждая кнопка оценки на интерфейсе обёрнута в компонент `Badge` библиотеки Material UI, отображающий числовой индикатор количества нажатий. Кнопки разбиты на четыре строки: три строки для технических действий (удар рукой, удар ногой, бросок) и одна строка для штрафных санкций и кнопки отмены. В каждой из строк технических действий слева расположены кнопки оценок синего участника, справа — красного, в центре — пояснительная надпись с названием действия. Расположение красных кнопок в зеркальном порядке относительно синих обусловлено эргономическими соображениями: судья работает с устройством двумя руками, и кнопки одного и того же значения должны быть симметричны.

### 3.3.5 Интерфейс главного судьи со сводной таблицей

Компонент `TablePage` соответствует адресу `/table` и представляет собой центральный экран системы — сводную таблицу оценок, отображаемую главному судье в реальном времени. Этот компонент существенно сложнее остальных в силу обилия информации, которую он должен синхронно отображать, и количества пользовательских воздействий, которые он должен обрабатывать.

Состояние компонента включает несколько разнотипных полей:

```jsx
const [openQR, setOpenQR] = React.useState(false);
const [openD, setOpenD] = React.useState(false);
const [selectedJudge, setSelectedJudge] = React.useState("");
const [judges, setJudges] = React.useState([]);
const [columns, setColumns] = React.useState([]);
const judgesDictRef = React.useRef({});
const [participants, setParticipants] = React.useState({
  redName: "",
  blueName: "",
});
const [roundActive, setRoundActive] = React.useState(false);
const [elapsedSeconds, setElapsedSeconds] = React.useState(0);
```

Логические состояния `openQR` и `openD` управляют видимостью диалогов QR-кода и подтверждения отключения судьи. Состояние `selectedJudge` хранит имя судьи, выбранного для отключения. Состояние `judges` хранит массив имён подключённых в данный момент боковых судей в порядке их подключения. Состояние `columns` хранит вычисленный массив столбцов сводной таблицы, что несколько избыточно при текущей реализации, но облегчает возможные будущие расширения. Состояние `participants` хранит имена участников раунда. Состояния `roundActive` и `elapsedSeconds` управляют таймером раунда.

Особо следует разобрать поле `judgesDictRef`, имеющее ключевое значение для логики компонента. Это «живой» словарь, отображающий каждое имя подключённого судьи в его упорядоченный ключ `judge1`, `judge2` или `judge3`. Назначение этого словаря — компромисс между двумя противоречивыми требованиями. С одной стороны, для удобства программирования логики таблицы и подсчёта сумм необходимы фиксированные имена ключей (`judge1`, `judge2`, `judge3`), от которых можно индексировать структуры данных вида «оценки каждого судьи». С другой стороны, фактические имена судей могут быть произвольными — Иванов, Петров, Сидоров — и именно эти имена приходят в сообщениях от сервера. Словарь `judgesDictRef` обеспечивает преобразование между этими двумя представлениями:

```jsx
const getJudges = (judgesArr) => {
  const map = {};
  judgesArr.forEach((name, idx) => {
    map[name] = `judge${idx + 1}`;
  });
  judgesDictRef.current = map;
  loadScoresFromServer(map);
  return map;
};
```

Применение `useRef`, а не `useState`, для хранения этого словаря намеренно. Изменение содержимого `judgesDictRef.current` не должно вызывать перерисовку компонента: словарь служит лишь подспорьем для функций индексации и не имеет прямого визуального отображения. Кроме того, изменение `useRef` доступно через прямое присваивание, без обёртки в функцию-сеттер, что упрощает код в обработчике входящих сообщений.

Хранилище фактических оценок имеет двухуровневую вложенность по цвету и судье, а внутри — массивы по видам действий:

```jsx
const initialScores = {
  blue: {
    judge1: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
    judge2: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
    judge3: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
  },
  red: {
    judge1: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
    judge2: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
    judge3: { hand: [], leg: [], throw: [], remark: [], warn: [], tiebreak: [] },
  },
};
const [scores, setScores] = React.useState(initialScores);
```

Структура отражает естественную многомерность данных: каждая оценка характеризуется тремя независимыми измерениями — цветом участника, индексом судьи и видом технического действия. Альтернативный вариант с плоским массивом записей был бы более компактным по объёму памяти, но потребовал бы фильтрации массива при каждом обращении к ячейке таблицы, что многократно увеличило бы накладные расходы на отрисовку. Выбранная иерархическая структура, напротив, обеспечивает обращение к содержимому ячейки за фиксированное время, не зависящее от общего числа выставленных оценок.

Получение содержимого одной ячейки таблицы реализовано функцией `getScoreElement`:

```jsx
const getScoreElement = (colorIdx, judgeName, punchIdx) => {
  const colors = ["blue", "red"];
  const punches = ["hand", "leg", "throw", "remark", "warn"];
  const color = colors[colorIdx];
  const judgeKey = judgesDictRef.current[judgeName];
  if (!judgeKey) return [];
  return (
    (scores[color] &&
      scores[color][judgeKey] &&
      scores[color][judgeKey][punches[punchIdx]]) ||
    []
  );
};
```

Возврат пустого массива в случае отсутствия каких-либо данных в цепочке обращений обеспечивает устойчивость к ситуациям, когда судья только что подключился, но соответствующих оценок для него ещё не создано. Защитная проверка реализована через цепочку логических «И» с короткой схемой вычисления.

Установка новой оценки в таблицу реализована функцией `setScoreElement`, обрабатывающей особый случай нокдауна:

```jsx
const setScoreElement = (color, judgeName, punch, scoreValue) => {
  const judgeKey = judgesDictRef.current[judgeName];

  setScores((prev) => {
    const prevColor = prev[color] || {};
    const prevJudge = prevColor[judgeKey] || { hand: [], leg: [], throw: [], remark: [], warn: [] };
    const currentArr = prevJudge[punch] || [];

    if (scoreValue === 4) {
      if (currentArr.length === 0) return prev;
      const last = currentArr[currentArr.length - 1];
      if (String(last).endsWith("H")) return prev;
      const newArr = [...currentArr.slice(0, -1), `${last}H`];
      return { ...prev, [color]: { ...prevColor, [judgeKey]: { ...prevJudge, [punch]: newArr } } };
    }

    return {
      ...prev,
      [color]: {
        ...prevColor,
        [judgeKey]: { ...prevJudge, [punch]: [...currentArr, evaluateScoreNumber(scoreValue)] },
      },
    };
  });
};
```

Функция демонстрирует приём иммутабельного обновления глубоко вложенной структуры данных, характерный для разработки на React. Вместо непосредственной модификации существующего объекта `scores` создаётся новый объект с теми же значениями, кроме одного изменённого поля. Глубина копирования соответствует глубине изменения: при добавлении оценки к одному из массивов копируются все объекты по пути от корня до изменяемого массива. Это обеспечивает корректную работу механизма сравнения предыдущего и нового состояния в React, основанного на сравнении ссылок объектов, и гарантирует, что компоненты, не затронутые изменением, не будут перерисованы.

Особый случай обработки нокдауна — значения 4 — реализует регламентное правило «нокдаун модифицирует последнее техническое действие». Вместо добавления нового элемента в массив оценок к последнему элементу добавляется суффикс `"H"`, превращая, например, значение 2 в значение `"2H"`. Подобное представление компактно — модификатор хранится прямо в строковом представлении оценки — и одновременно содержит всю информацию для последующих вычислений: при разборе строки можно отделить числовую часть от буквенного маркера. Защитные проверки гарантируют корректность: если массив пуст (нечего модифицировать) или если последняя оценка уже содержит модификатор (нельзя применить два нокдауна подряд), функция возвращает прежнее состояние без изменений.

Преобразование числовых кодов в их строковые представления для штрафных санкций выполняется функцией `evaluateScoreNumber`:

```jsx
function evaluateScoreNumber(scoreValue) {
  switch (scoreValue) {
    case 5: return "П";
    case 6: return "З";
    default: return scoreValue;
  }
}
```

Числовой код 5 представляет предупреждение, отображаемое в таблице буквой «П», код 6 — замечание, отображаемое буквой «З». Подобное двойное представление — числовое на уровне данных и буквенное на уровне отображения — позволяет единообразно обрабатывать все виды оценок в общей логике передачи и хранения, оставляя текстовое преобразование на уровне ввода в таблицу.

Отмена оценки выполняется функцией `removeLastScore`, симметричной `setScoreElement`:

```jsx
const removeLastScore = (color, judgeName, punch, score) => {
  // ...
  if (score === 4) {
    const last = currentArr[currentArr.length - 1];
    if (String(last).endsWith("H")) {
      const base = String(last).slice(0, -1);
      const numBase = Number(base);
      newArr = [...currentArr.slice(0, -1), isNaN(numBase) ? base : numBase];
    } else {
      return prev;
    }
  } else {
    newArr = currentArr.slice(0, -1);
  }
  // ...
};
```

При отмене обычной оценки последний элемент массива просто удаляется. При отмене нокдауна последний элемент модифицируется: с него снимается буквенный суффикс, и базовое значение возвращается к числовому представлению. Преобразование `Number(base)` со сравнением `isNaN(numBase)` обрабатывает граничный случай: если базовое значение было не числом, а одной из букв «П» или «З» (что не должно случаться по регламенту, но допустимо в коде), значение сохраняется в строковом виде.

Алгоритм подсчёта суммы очков для одного судьи и одного цвета реализован функцией `getScoreSum`:

```jsx
function getScoreSum(colorIdx, judgeKey) {
  const colors = ["blue", "red"];
  const regularPunches = ["hand", "leg", "throw", "tiebreak"];
  const judges = ["judge1", "judge2", "judge3"];
  const judgeName = judges[judgeKey];
  const color = colors[colorIdx];
  const enemyColor = colors[colorIdx === 0 ? 1 : 0];
  let sum = 0;
  for (let i = 0; i < regularPunches.length; i++) {
    if (scores[color][judgeName][regularPunches[i]][0]) {
      sum = scores[color][judgeName][regularPunches[i]].reduce(
        (previous, current) => {
          const str = String(current);
          if (str.endsWith("H")) {
            const numPart = parseInt(str, 10);
            return previous + (isNaN(numPart) ? 0 : numPart) + 3;
          }
          if (isNaN(current)) {
            return previous;
          }
          return previous + current;
        },
        sum,
      );
    }
  }
  const enemyRemarks = (scores[enemyColor] && scores[enemyColor][judgeName] && scores[enemyColor][judgeName]["remark"]) || [];
  sum += enemyRemarks.length * 1;
  const enemyWarns = (scores[enemyColor] && scores[enemyColor][judgeName] && scores[enemyColor][judgeName]["warn"]) || [];
  sum += enemyWarns.length * 2;
  return sum;
}
```

Алгоритм состоит из двух частей. В первой части суммируются собственные «полезные» оценки участника — удары рукой, ногой, броски и оценки тайбрейка. Для каждой оценки проверяется наличие модификатора `"H"`: если он присутствует, числовая часть оценки выделяется через `parseInt(str, 10)` (функция, разбирающая числовой префикс строки до первого нечислового символа) и к сумме добавляется числовая часть плюс три очка нокдауна. Если оценка не содержит модификатора и представлена числом, она добавляется как есть. Если оценка представлена нечисловой строкой — например, буквой «П» или «З», что в массивах `regularPunches` не должно встречаться, но добавлено для устойчивости, — она пропускается.

Во второй части алгоритма к сумме добавляются штрафные очки соперника: за каждое замечание соперника (`remark`) добавляется одно очко в пользу текущего участника, за каждое предупреждение (`warn`) — два очка. Это соответствует регламенту: штрафы соперника увеличивают счёт собственного участника. Защитные цепочки логических «И» обеспечивают корректное поведение при отсутствии соответствующих структур данных.

Функция `calcScore` определяет победителя одного судьи: возвращает 1 для участника с большей суммой и 0 для проигравшего. Функция `calcFinalScore` суммирует победы по всем трём судьям, получая итоговый счёт всего поединка:

```jsx
function calcScore(colorIdx, judgeKey) {
  const enemyColor = colorIdx === 0 ? 1 : 0;
  if (getScoreSum(colorIdx, judgeKey) > getScoreSum(enemyColor, judgeKey)) {
    return 1;
  } else {
    return 0;
  }
}

function calcFinalScore(colorIdx) {
  let sumBlue = 0;
  let sumRed = 0;
  for (let i = 0; i < 3; i++) {
    sumBlue += calcScore(0, i);
    sumRed += calcScore(1, i);
  }
  if (colorIdx === 0) {
    return sumBlue;
  } else {
    return sumRed;
  }
}
```

Подключение к серверу по WebSocket и обработка входящих сообщений выполняется в эффекте, аналогичном по структуре эффекту в `MobilePage`, но с другим набором обрабатываемых событий:

```jsx
React.useEffect(() => {

  const ws = new WebSocket(
    `ws://${window.location.host.split(":")[0] + ":8000"}/ws/mainJudge`,
```

При обработке сообщения `judgeupd` помимо обновления состояния `judges` вызывается функция `getJudges`, заполняющая словарь `judgesDictRef` и инициирующая загрузку оценок с сервера для всех текущих судей. Подобное поведение необходимо для случая подключения нового судьи после уже выставленных оценок — например, если один из судей кратковременно потерял связь и переподключился. Без перезагрузки оценок его столбец таблицы оказался бы пустым, несмотря на наличие оценок на сервере.

Функция загрузки оценок реализована следующим образом:

```jsx
const loadScoresFromServer = async (judgeMap) => {
  try {
    const serverScores = await fetchScores();
    const newScores = JSON.parse(JSON.stringify(initialScores));
    for (const [judgeName, colorData] of Object.entries(serverScores)) {
      const judgeKey = judgeMap[judgeName];
      if (!judgeKey) continue;
      for (const [color, punches] of Object.entries(colorData)) {
        if (!newScores[color]) continue;
        newScores[color][judgeKey] = punches;
      }
    }
    setScores(newScores);
  } catch (e) {
    console.error("Failed to load scores from server:", e);
  }
};
```

Глубокое копирование начального состояния через `JSON.parse(JSON.stringify(...))` — приём, обеспечивающий полную независимость нового объекта от исходного. Альтернативные подходы — оператор расширения `{...initialScores}` или метод `Object.assign` — выполняют лишь поверхностное копирование, при котором вложенные объекты остаются общими между копиями, что недопустимо для дальнейшей независимой модификации.

Стоит отметить, что серверная часть в текущей реализации не предоставляет конечной точки `/scores`, к которой обращается `fetchScores`: соответствующий обработчик присутствует в клиентской части как точка возможного расширения, но не имеет серверного контрагента. Подобная конструкция оставлена в коде на будущее: добавление обработчика на сервер позволит активировать функцию восстановления оценок без правок клиента.

Таймер раунда реализован отдельным эффектом, зависящим от состояния `roundActive`:

```jsx
React.useEffect(() => {
  if (!roundActive) return;
  const interval = setInterval(() => setElapsedSeconds((s) => s + 1), 1000);
  return () => clearInterval(interval);
}, [roundActive]);
```

Эффект запускается каждый раз при изменении значения `roundActive`. При значении `false` эффект немедленно завершается, не запуская никакого таймера. При значении `true` запускается интервальный таймер с периодом одна секунда, увеличивающий счётчик прошедших секунд на единицу при каждом срабатывании. Возвращаемая функция-уборщик останавливает таймер при размонтировании компонента или при изменении состояния `roundActive` обратно в `false`.

Применение функционального обновления состояния `setElapsedSeconds((s) => s + 1)` вместо `setElapsedSeconds(elapsedSeconds + 1)` принципиально для корректной работы: при первом варианте функция-обновитель получает на вход актуальное значение состояния в момент применения обновления, тогда как при втором использовалось бы значение `elapsedSeconds`, замкнутое в эффекте на момент его запуска, и счётчик некорректно застрял бы на единице.

Форматирование времени для отображения реализовано функцией `formatTime`:

```jsx
const formatTime = (seconds) => {
  const m = Math.floor(seconds / 60).toString().padStart(2, "0");
  const s = (seconds % 60).toString().padStart(2, "0");
  return `${m}м:${s}с`;
};
```

Использование `padStart(2, "0")` обеспечивает отображение времени в виде двузначных чисел: `01м:05с` вместо `1м:5с`, что соответствует общепринятому формату индикации времени и улучшает визуальную стабильность.

Обработчик переключения состояния раунда — запуск или досрочное завершение:

```jsx
const handleRoundToggle = () => {
  if (roundActive) {
    setRoundActive(false);
    postRoundEnd();
  } else {

    setRoundActive(true);

```

При запуске раунда счётчик прошедших секунд обнуляется, что соответствует началу нового отсчёта. При завершении раунда отправляется соответствующий запрос на сервер, который, в свою очередь, рассылает уведомление всем подключённым боковым судьям.

Отрисовка таблицы выполняется через несколько вложенных циклов по строкам и столбцам. На верхнем уровне отрисовывается шапка с именами участников, ниже — заголовки столбцов с именами судей, далее — пять строк со значениями оценок по каждому виду действия и, наконец, строки с суммами очков и условными счётами по каждому судье. Завершает интерфейс крупное отображение итогового счёта поединка по результатам всех трёх судей.


Базовый адрес сервера определяется как имя текущего узла с явно указанным портом 8000. Подобное вычисление адреса обеспечивает корректную работу как при разработке на локальной машине (где имя узла — `localhost`), так и при работе с мобильного устройства, обращающегося к серверу по сетевому адресу ноутбука главного судьи. Главное предположение, лежащее в основе подобной схемы, — клиент всегда загружен с того же сервера, к которому он впоследствии обращается, что в архитектуре одностраничного приложения, раздаваемого FastAPI, гарантировано.

Каждая функция модуля выполняет один типовой обмен с сервером: формирование запроса с нужным методом и заголовками, отправка тела запроса в формате JSON при необходимости, десериализация ответа и его возврат вызывающему коду. Применение единого модуля для всех сетевых обращений обеспечивает централизованную точку для возможных изменений в будущем: смена базового адреса, добавление общего заголовка авторизации, единая обработка ошибок — всё это может быть реализовано в одном файле без правок в компонентах, пользующихся этими функциями.

## 3.4 Работа с базой данных

Хранение данных в разрабатываемой системе реализовано с применением встраиваемой системы управления базами данных SQLite, выбор которой обоснован во второй главе. В настоящем разделе подробно рассматриваются практические особенности работы с SQLite в рамках серверной части: схема единственной таблицы, обращения к ней из кода на языке Python, обоснование сделанных проектных решений.

### 3.4.1 Структура и инициализация таблицы

База данных рассматриваемой системы содержит единственную таблицу `participants`, описывающую справочник участников соревнований. Структура таблицы определяется командой `CREATE TABLE`, исполняемой в функции `init_db()` при запуске серверного процесса:

```sql
CREATE TABLE IF NOT EXISTS participants (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE
)
```

Поле `id` имеет тип `INTEGER` и снабжено двумя ограничениями: `PRIMARY KEY` объявляет его первичным ключом таблицы, а `AUTOINCREMENT` обеспечивает автоматическое присвоение уникального значения при добавлении новой записи. Особенность ключа `AUTOINCREMENT` в SQLite состоит в том, что присваиваемые значения монотонно возрастают и никогда не повторяются — даже после удаления записи с наибольшим идентификатором. Это свойство гарантирует, что любая ссылка на участника по его идентификатору, сохранённая где-либо вне базы данных, остаётся однозначной даже после операций удаления.

Поле `name` имеет тип `TEXT` и снабжено ограничениями `NOT NULL` и `UNIQUE`. Первое из них предотвращает добавление записи с пустым именем — попытка вставить значение `NULL` приведёт к нарушению ограничения и возврату ошибки. Второе обеспечивает уникальность имени по всей таблице: попытка добавить запись с именем, уже присутствующим в базе, также порождает ошибку — но при необходимости она может быть программно подавлена применением конструкции `INSERT OR IGNORE`, рассматриваемой ниже.

Применение в командной инструкции конструкции `IF NOT EXISTS` обеспечивает идемпотентность операции: при повторном запуске сервера, когда таблица уже создана, команда выполняется без эффекта. Подобная идемпотентность критична для процедуры инициализации: код инициализации должен корректно отрабатывать как при первом запуске на новом сервере, так и при перезапуске уже работавшего сервера, не пытаясь заново создать существующую структуру и не теряя данные.

### 3.4.2 Чтение записей из таблицы

Получение списка всех участников выполняется в обработчике конечной точки `GET /db/participants`:

```python
@app.get("/db/participants")
def get_db_participants():
    con = sqlite3.connect(DB_PATH)
    rows = con.execute("SELECT id, name FROM participants ORDER BY name").fetchall()
    con.close()
    return [{"id": r[0], "name": r[1]} for r in rows]
```

Соединение с базой данных открывается локально, в рамках одной функции, что соответствует так называемой модели «соединение на запрос». Альтернативой могла бы служить модель пула соединений, в которой предварительно создаётся набор соединений, и каждый запрос берёт одно из них на время выполнения, возвращая по завершении. Однако для рассматриваемой системы преимущества пула соединений не реализуются. Во-первых, нагрузка на сервер крайне мала: справочник участников запрашивается лишь при открытии страницы создания раунда, что происходит редко. Во-вторых, открытие соединения с локальным файлом SQLite — это операция длительностью в доли миллисекунды, поскольку не требует сетевого взаимодействия или установления криптографического канала. Таким образом, выигрыш от пулирования соединений был бы пренебрежимо мал, а сложность кода — выше.

Команда `SELECT id, name FROM participants ORDER BY name` извлекает все записи с сортировкой по имени. Сортировка на стороне базы данных предпочтительнее сортировки на стороне клиента: SQLite использует встроенный эффективный алгоритм сортировки и при необходимости может задействовать индекс — хотя в данной задаче малого количества записей это несущественно. Метод `fetchall()` возвращает результат в виде списка кортежей, по одному кортежу на строку.

Преобразование к списку словарей, выполняемое выражением `[{"id": r[0], "name": r[1]} for r in rows]`, необходимо для последующей сериализации в JSON: FastAPI автоматически преобразует словари Python в объекты JSON с одноимёнными полями, тогда как преобразование кортежа дало бы массив без поясняющих имён полей.

Соединение с базой данных закрывается явным вызовом `con.close()` после получения результата. Альтернативой могла бы служить конструкция `with`, автоматически закрывающая соединение по завершении блока. В рассматриваемой реализации применяется явное закрытие, что соответствует стилистической традиции примеров документации модуля `sqlite3`, но обе формы эквивалентны по поведению.

### 3.4.3 Добавление новых записей

Добавление нового участника в справочник выполняется в обработчике конечной точки `POST /db/participants`:

```python
@app.post("/db/participants")
def create_db_participant(entry: ParticipantEntry):
    con = sqlite3.connect(DB_PATH)
    con.execute("INSERT OR IGNORE INTO participants (name) VALUES (?)", (entry.name,))
    con.commit()
    row = con.execute("SELECT id, name FROM participants WHERE name = ?", (entry.name,)).fetchone()
    con.close()
    return {"id": row[0], "name": row[1]}
```

Ключевая особенность этого обработчика — применение конструкции `INSERT OR IGNORE`, расширения SQLite относительно стандарта SQL. Действие этой конструкции состоит в следующем: команда вставки выполняется как обычно, но если она приводит к нарушению какого-либо ограничения целостности — в частности, ограничения уникальности на поле `name` — операция тихо отменяется, и не порождается исключение. Это позволяет вызывающему коду не заботиться о проверке существования записи перед вставкой: если запись уже есть, никакого нарушения логики не происходит, а если её нет — она создаётся.

Подобная идемпотентность операции вставки принципиально важна для пользовательского сценария создания раунда. Если оператор повторно вводит ФИО уже сохранённого участника и нажимает кнопку «Сохранить» — например, при создании нескольких последовательных раундов с одними и теми же участниками — система ведёт себя предсказуемо и не загромождает интерфейс сообщениями об ошибках. Альтернативный подход, при котором повторная вставка возвращала бы клиенту ошибку, потребовал бы дополнительной логики на стороне клиента: предварительной проверки существования записи или особой обработки ошибки.

После выполнения вставки выполняется отдельный запрос `SELECT` для получения полной записи о только что добавленном (или ранее существовавшем) участнике. Подобная избыточность — два запроса вместо одного — компенсируется ясностью семантики обработчика: возвращаемое значение всегда содержит идентификатор и имя записи, независимо от того, была ли она только что создана или уже существовала. Клиентский код может единообразно обновить свой локальный список без выполнения дополнительных запросов.

Вызов `con.commit()` между двумя командами фиксирует транзакцию вставки. По умолчанию модуль `sqlite3` стандартной библиотеки Python работает в режиме, при котором операции, изменяющие данные, выполняются в неявной транзакции, которая остаётся открытой до явного вызова `commit()` или `rollback()`. Отсутствие явной фиксации привело бы к тому, что вставленная запись не была бы сохранена в файле базы данных при закрытии соединения, и при следующем обращении список участников оказался бы неполным.

### 3.4.4 Параметризация запросов

Принципиально важной особенностью обоих рассмотренных запросов является применение символа-заполнителя `?` для подстановки пользовательских значений, вместо непосредственного конкатенирования значений в текст запроса. В обработчике вставки используется конструкция:

```python
con.execute("INSERT OR IGNORE INTO participants (name) VALUES (?)", (entry.name,))
```

Здесь имя участника передаётся не как часть строки SQL-команды, а как отдельный аргумент в кортеже значений, переданном вторым параметром в метод `execute()`. Модуль `sqlite3` берёт на себя задачу корректного встраивания значения в команду: если значение содержит специальные символы — кавычки, точки с запятой, символы перевода строки — они автоматически экранируются способом, безопасным для SQL-парсера.

Альтернативный, нерекомендуемый способ — формирование SQL-команды через конкатенацию или интерполяцию строк Python:

```python
# НЕБЕЗОПАСНО, для иллюстрации
con.execute(f"INSERT INTO participants (name) VALUES ('{entry.name}')")
```

Подобная запись опасна, поскольку открывает возможность для атаки типа «внедрение SQL». Если злоумышленник передаст в качестве имени участника значение `Иванов'); DROP TABLE participants; --`, оно встраивается непосредственно в команду, образуя её часть синтаксиса, и выполняется парсером как самостоятельные инструкции. В результате таблица справочника будет уничтожена. Подробнее вопросы защиты от SQL-инъекций рассматриваются в разделе 3.5.

Параметризованный вариант полностью устраняет указанную уязвимость: даже если значение содержит произвольный текст, оно всегда рассматривается как литеральное строковое значение для поля `name`, а не как часть синтаксиса команды. Это свойство — единственный надёжный способ предотвращения SQL-инъекций в коде, работающем с пользовательскими данными.

### 3.4.5 Хранение временного состояния в оперативной памяти

Существенным проектным решением, обоснованным во второй главе и подкреплённым в реализации, является отказ от хранения текущего состояния раунда в базе данных. Все оперативные данные — список оценок текущего раунда, словарь подключённых судей, имена выступающих в данный момент спортсменов — хранятся в полях экземпляра класса `ConnectionManager`, то есть в оперативной памяти серверного процесса.

Указанное решение даёт два существенных преимущества. Во-первых, обращения к оперативной памяти выполняются за наносекунды, тогда как обращения к SQLite — пусть и расположенному на локальном диске — занимают доли миллисекунды. При типичной нагрузке поединка, когда оценки поступают по нескольку в секунду, накладные расходы на работу с базой данных составили бы сотни миллисекунд за минуту поединка. Хранение в памяти полностью устраняет эти расходы.

Во-вторых, и более важно — реализация хранения в памяти существенно проще. Для добавления оценки достаточно вызвать асинхронный метод объекта, без формирования SQL-команд, открытия соединений, обработки исключений базы данных. Это упрощает чтение и сопровождение кода: вся логика передачи оценки сосредоточена в одном месте, и нет необходимости отслеживать соответствие между внутренним представлением и схемой базы данных.

Платой за подобный выбор служит то, что при непредвиденном завершении серверного процесса в середине поединка все накопленные данные теряются. С практической точки зрения этот риск приемлем: продолжительность поединка не превышает нескольких минут, и вероятность сбоя процесса в столь короткое окно мала. Кроме того, даже в случае сбоя последствия ограничены: судьи переподключатся к перезапущенному серверу и начнут поединок заново, что менее болезненно, чем продолжение поединка с подозреваемыми данными.

В дальнейших версиях системы предусматривается расширение базы данных за счёт хранения истории завершённых поединков. Соответствующие таблицы — `rounds` с описанием раундов и `round_scores` с детализацией оценок — позволят реализовать функции выгрузки протоколов соревнований и статистики работы судей. Указанное расширение не нарушит сделанный выбор: текущее состояние активного поединка по-прежнему останется в памяти, а в базу данных будут записываться лишь итоговые данные по завершении каждого поединка, что не увеличит нагрузку в реальном времени.

## 3.5 Безопасность приложения

Вопросы безопасности информационной системы традиционно рассматриваются с двух точек зрения: с точки зрения возможных угроз, которым подвергается система, и с точки зрения мер противодействия этим угрозам, предусмотренных при её разработке. Конкретный набор мер зависит от характеристик системы и условий её эксплуатации: меры, обязательные для систем, доступных через интернет, могут оказаться избыточными для систем, работающих в изолированной локальной сети, и наоборот. Подобный подход к балансу мер и угроз в системах локальных сетей подробно обоснован в авторской статье «Способы защиты данных в системах, работающих внутри локальной сети» [2]. Принятые при разработке рассматриваемой системы решения отражают именно такой осознанный баланс: ряд защитных мер не реализован, поскольку соответствующие угрозы не актуальны для условий эксплуатации, тогда как реализованные меры направлены на нейтрализацию реальных рисков, характерных для работы в изолированной локальной сети спортивного зала.

### 3.5.1 Изоляция в локальной сети

Базовой защитной мерой, лежащей в основе всей модели безопасности системы, является её работа в полностью изолированной локальной сети. Беспроводная сеть, разворачиваемая на месте проведения соревнований, не соединяется с сетью интернет и не имеет общих сегментов с какими-либо корпоративными или публичными сетями. Подобная изоляция обеспечивается одним из двух способов: либо использованием отдельного Wi-Fi-роутера, не подключённого к каналу связи с интернетом, либо использованием встроенного в операционную систему ноутбука механизма создания точки доступа, по которой ноутбук одновременно служит и сервером, и беспроводным узлом доступа.

Следствием изоляции является полное отсутствие внешних угроз: атаки извне, направленные на серверный процесс, технически невозможны, поскольку у сервера нет внешнего сетевого адреса, по которому к нему можно было бы обратиться из внешней сети. Это существенно снижает поверхность атаки по сравнению с системами, работающими через интернет, и оправдывает отказ от ряда мер, обязательных для последних.

Однако даже в изолированной сети сохраняются внутренние угрозы. К ним относятся: ошибочные действия легитимных пользователей, способные привести к искажению хранимых данных; попытки несанкционированного подключения посторонних устройств к Wi-Fi-сети; перехват сетевого трафика на канальном уровне; целенаправленные атаки изнутри со стороны злоумышленника, физически присутствующего в зоне доступа Wi-Fi-сети. Меры противодействия этим угрозам рассматриваются ниже.

### 3.5.2 Защита от внедрения SQL

Внедрение SQL — это класс атак, при которых злоумышленник встраивает в передаваемые серверу данные фрагменты SQL-команд, исполняемые сервером как часть законных команд работы с базой данных. Последствия успешной атаки могут варьироваться от утечки хранимых данных до полного уничтожения базы данных.

В рассматриваемой системе защита от подобных атак реализована применением параметризованных запросов во всех операциях с базой данных. Все обращения к таблице `participants` выполняются через метод `execute()` модуля `sqlite3` стандартной библиотеки Python с обязательным разделением SQL-команды и значений на два отдельных аргумента:

```python
con.execute("INSERT OR IGNORE INTO participants (name) VALUES (?)", (entry.name,))
con.execute("SELECT id, name FROM participants WHERE name = ?", (entry.name,)).fetchone()
```

Символ-заполнитель `?` в тексте команды служит указанием места, в которое должно быть подставлено значение из второго аргумента. Подстановка выполняется не средствами строковой интерполяции Python, а внутренним механизмом модуля `sqlite3`, который рассматривает значение исключительно как литеральное содержимое поля и не позволяет ему повлиять на синтаксис самой команды.

Подобный механизм нейтрализует все известные на сегодня варианты внедрения SQL, поскольку устраняет саму возможность взаимодействия пользовательских данных с парсером SQL-команд. Даже если в качестве имени участника будет передан текст, в точности воспроизводящий синтаксис вредоносной команды, — например, `Иванов'); DROP TABLE participants; --`, — он будет сохранён в поле `name` как обычное строковое значение, не повлиявшее на структуру команды.

Эффективность защиты подтверждается также тем, что во всех точках кода, обращающихся к базе данных, используется один и тот же шаблон. Не существует ни одной строки кода, в которой пользовательские данные подставлялись бы в SQL-команду через интерполяцию или конкатенацию строк. Подобная единообразность реализации гарантирует, что отдельные обработчики не выпадают из общей защитной схемы.

### 3.5.3 Политика разделения ресурсов между доменами

Политика разделения ресурсов между доменами, известная под названием CORS, представляет собой встроенный в браузеры механизм ограничения межсайтовых сетевых обращений. По умолчанию браузер блокирует попытки страницы, загруженной с одного домена, обратиться к серверному ресурсу на другом домене. Сервер может явно разрешить такие обращения, отправив в ответ соответствующие заголовки. Программное обеспечение, обслуживающее реальное многосайтовое окружение, обязано тщательно подбирать перечень разрешённых источников, поскольку чрезмерная либеральность открывает возможность для межсайтовых атак.

В рассматриваемой системе политика CORS настроена следующим образом:

```python
origins = ["*"]

app.add_middleware(
    CORSMiddleware,
    allow_origins=origins,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Значение `"*"` в списке разрешённых источников разрешает обращения с любого источника. Подобная конфигурация была бы неприемлема для системы, доступной через интернет: она открыла бы возможность для межсайтовых обращений с произвольных страниц, способных, например, считать список участников или отправить фальшивые оценки.

В условиях же изолированной локальной сети риск, связанный с подобной политикой, заведомо отсутствует. Сервер недоступен из внешних сетей, и в локальной сети нет посторонних страниц, способных инициировать межсайтовые обращения. Преимуществом же либеральной политики становится практическое удобство: при подключении новых устройств к Wi-Fi-сети им не требуется быть заранее перечисленными в конфигурации сервера. Подобный отказ от ограничений в безопасной среде — это типичный приём упрощения архитектуры, оправданный условиями эксплуатации.

При теоретическом расширении эксплуатации системы за пределы изолированной локальной сети — например, при появлении облачной версии для турниров с интернет-доступом — политика CORS должна быть ужесточена. Соответствующие изменения сосредоточены в одном месте кода и могут быть внесены без правок остальных частей системы.

### 3.5.4 Сознательный отказ от аутентификации

Одним из значимых проектных решений в области безопасности является отказ от реализации полноценной системы аутентификации. Боковые судьи подключаются к серверу простым вводом своего имени, без пароля и без проверки подлинности.

Подобное решение принято на основании следующих соображений. Во-первых, физическая среда эксплуатации обеспечивает дополнительный фактор аутентификации: для подключения к серверу необходимо находиться в зоне действия Wi-Fi-сети мероприятия, что само по себе ограничивает круг потенциальных подключающихся. Во-вторых, главный судья имеет возможность принудительно отключить любого судью, что служит средством корректировки в случае ошибочного или несанкционированного подключения. В-третьих, реализация системы паролей или биометрической аутентификации существенно усложнила бы процедуру подключения, что особенно нежелательно для условий, где судьи — это, как правило, опытные специалисты, не обязанные обладать квалификацией системного администратора.

Также важно учитывать, что система не оперирует чувствительными данными. Единственные хранимые персональные данные — это ФИО участников соревнований, которые объявляются вслух в начале каждого раунда и публикуются в протоколах соревнований; они не подлежат защите в рамках законодательства о персональных данных в качестве чувствительных. Оценки судей — это публичная информация, отображаемая на экране главного судьи всем присутствующим. Таким образом, риски утечки данных при подключении постороннего лица к серверу минимальны: основное негативное последствие сводится к возможному искажению результатов поединка, что обнаруживается главным судьёй визуально и устраняется принудительным отключением.

Тем не менее, отсутствие аутентификации остаётся осознанным риском, и в перспективе развития продукта предусматривается её добавление. Один из возможных подходов — выдача каждому судье уникального токена при подключении, с проверкой токена при последующих запросах. Указанный подход рассматривается в четвёртой главе в контексте развития продукта.

### 3.5.5 Защита трафика на iOS-устройствах

Принципиальная особенность мобильных устройств Apple, выявленная при тестировании системы, состоит в том, что браузер Safari на iOS отказывается устанавливать соединение по незащищённому протоколу WebSocket, если страница загружена по адресу HTTP из локальной сети. Подобное поведение обусловлено политикой App Transport Security, ограничивающей незащищённые сетевые взаимодействия, и не может быть переопределено настройками браузера со стороны пользователя.

Указанная особенность создаёт необходимость в защите трафика между сервером и iOS-устройствами через TLS-шифрование. В рассматриваемой системе реализован следующий подход: сервер опционально может быть запущен с поддержкой HTTPS на основе самоподписанного сертификата. Сертификат генерируется автоматически при первом запуске установщика и сохраняется в каталоге сервера. При подключении iOS-устройства пользователю один раз потребуется подтвердить доверие к самоподписанному сертификату через системные настройки, после чего соединение работает в полностью защищённом режиме, удовлетворяя требованиям App Transport Security.

Защита трафика TLS-шифрованием обеспечивает не только удовлетворение требований Apple, но и нейтрализацию ещё одного класса угроз — пассивного прослушивания сетевого трафика на канальном уровне. В беспроводных сетях злоумышленник, находящийся в зоне действия точки доступа, может перехватывать передаваемые радиосигналы, и хотя современный стандарт WPA2/WPA3 шифрует канальный уровень, дополнительный уровень защиты на уровне приложения добавляет устойчивость к компрометации ключей беспроводной сети.

Подробное обоснование указанного подхода — выбор между самоподписанным сертификатом и сертификатами сертифицирующих центров, между ручной и автоматической генерацией сертификата, между обязательностью и опциональностью HTTPS — приведено в указанной авторской статье [2], в которой автор анализирует компромиссы безопасности применительно к системам локальных сетей.

### 3.5.6 Дополнительные меры

Помимо рассмотренных выше принципиальных мер, в системе реализованы и ряд мер общего характера, направленных на повышение её устойчивости.

Все диагностические сообщения, выводимые сервером в стандартный поток вывода при возникновении исключений, содержат техническую информацию, полезную для диагностики, но не содержат секретных данных — паролей, токенов или конкретных значений, способных привести к утечке. В рассматриваемой системе и подобных данных нет, что упрощает соблюдение этого принципа.

Сервер не возвращает в ответе клиенту детальные сообщения об ошибках работы с базой данных или иных внутренних исключениях. По умолчанию FastAPI оборачивает необработанные исключения в ответ с кодом 500 Internal Server Error и общим сообщением, не раскрывая подробностей. Подобное поведение защищает от утечки информации о внутреннем устройстве системы, которая могла бы быть использована злоумышленником для подготовки целевой атаки.

Каталог `dist`, содержащий статические файлы клиентского приложения, раздаётся сервером в режиме «только чтение»: нет конечных точек, позволяющих изменить или удалить хранимые файлы. Это исключает возможность подмены клиентского кода через программный интерфейс.

Использование актуальных версий зависимостей с фиксацией в файлах `requirements.txt` и `package-lock.json` обеспечивает воспроизводимость сборки и упрощает отслеживание известных уязвимостей. При обнаружении уязвимости в одной из зависимых библиотек обновление в файле фиксаций позволяет одновременно обновить версию во всех окружениях разработки и эксплуатации.

## 3.6 Описание ключевых фрагментов кода

В настоящем разделе подробно разбираются несколько ключевых фрагментов кода, играющих центральную роль в обеспечении корректной работы системы. Каждый фрагмент сопровождается построчным анализом, выявляющим неочевидные особенности реализации и обосновывающим принятые проектные решения.

### 3.6.1 Метод `ConnectionManager.connect` — предотвращение дублирующихся подключений

Метод `connect` класса `ConnectionManager` отвечает за приём нового постоянного соединения от клиента — главного или бокового судьи. Полный текст метода:

```python
async def connect(self, websocket: WebSocket, judgeName):
    if judgeName in self.connected_judges:
        await websocket.close(code=4001)
        return False
    await websocket.accept()
    if judgeName == "mainJudge":
        self.main_judge_ws = websocket
    else:
        self.connected_judges[judgeName] = websocket
    print(
        f"{judgeName} connected. Judges online: {list(self.connected_judges.keys())}\n"
    )
    await self.update_connected_judges()
    return True
```

Первая инструкция метода — проверка, не подключён ли уже судья с заданным именем. Если соответствующий ключ присутствует в словаре `connected_judges`, метод немедленно закрывает входящее соединение специальным кодом 4001 и возвращает признак неуспешного подключения. Применение кода именно из диапазона 4000–4999, зарезервированного стандартом RFC 6455 для использования прикладными протоколами, существенно: использование стандартных кодов закрытия (1000 — нормальное закрытие, 1006 — ненормальное закрытие) привело бы к неоднозначной интерпретации на стороне клиента, тогда как пользовательский код позволяет клиенту определить конкретную причину закрытия и отобразить пользователю информативное сообщение.

Принципиально, что закрытие выполняется до вызова `accept()`, что соответствует протоколу WebSocket: подключение считается установленным только после успешного выполнения рукопожатия со стороны сервера, и отказ от рукопожатия — наиболее чистый способ отказать клиенту в подключении.

Если проверка пройдена, метод вызывает `accept()` и сохраняет соединение в соответствующем поле. Особый случай — главный судья — обрабатывается отдельным условием: его соединение сохраняется в выделенном поле `main_judge_ws`, а не в общем словаре боковых судей. Подобное разделение упрощает последующие операции: при рассылке сообщений главному судье отпадает необходимость в выборке его соединения среди всех зарегистрированных, а при перечислении подключённых боковых судей не приходится фильтровать главного судью.

Диагностический вывод через `print` фиксирует факт подключения в журнале серверного процесса. Подобный вывод не предназначен для разбора программным образом и служит исключительно средством наблюдения за работой системы со стороны разработчика; в эксплуатационной поставке он может быть отключён либо перенаправлен в файл.

Завершающий вызов `update_connected_judges()` информирует главного судью об изменении состава подключённых судей, что вызывает добавление нового столбца в его сводной таблице. Возврат `True` уведомляет вызывающий обработчик WebSocket-маршрута о необходимости войти в цикл чтения сообщений.

### 3.6.2 Функция `setScoreElement` — иммутабельное обновление и обработка модификатора «Нокдаун»

Функция `setScoreElement` в компоненте `TablePage` отвечает за добавление новой оценки в сводную таблицу главного судьи. В ней сосредоточена ключевая бизнес-логика обработки модификатора «Нокдаун»:

```jsx
const setScoreElement = (color, judgeName, punch, scoreValue) => {
  const judgeKey = judgesDictRef.current[judgeName];

  setScores((prev) => {
    const prevColor = prev[color] || {};
    const prevJudge = prevColor[judgeKey] || {
      hand: [], leg: [], throw: [], remark: [], warn: [],
    };
    const currentArr = prevJudge[punch] || [];

    if (scoreValue === 4) {
      if (currentArr.length === 0) return prev;
      const last = currentArr[currentArr.length - 1];
      if (String(last).endsWith("H")) return prev;
      const newArr = [...currentArr.slice(0, -1), `${last}H`];
      return {
        ...prev,
        [color]: {
          ...prevColor,
          [judgeKey]: { ...prevJudge, [punch]: newArr },
        },
      };
    }

    return {
      ...prev,
      [color]: {
        ...prevColor,
        [judgeKey]: {
          ...prevJudge,
          [punch]: [...currentArr, evaluateScoreNumber(scoreValue)],
        },
      },
    };
  });
};
```

Первая инструкция функции — преобразование имени судьи в его упорядоченный ключ через словарь `judgesDictRef`. Подобное преобразование необходимо, поскольку в структуре `scores` судьи индексируются по ключам `judge1`, `judge2`, `judge3`, а не по реальным именам.

Основное тело функции реализовано как обновление состояния React через функциональный сеттер `setScores((prev) => ...)`. Применение функциональной формы сеттера, а не прямой передачи нового значения, принципиально для корректности: оно гарантирует, что обновление работает с актуальным предыдущим значением состояния, даже если несколько обновлений выполняются последовательно в одном кадре отрисовки.

Внутри функции сначала извлекаются ссылки на текущие значения по пути от корня структуры к изменяемому массиву. Применение оператора `||` с пустыми объектами или массивами в качестве значения по умолчанию обеспечивает устойчивость к ситуациям, когда какая-либо из промежуточных структур ещё не создана — например, при подключении нового судьи до получения от него первой оценки.

Далее реализована логика модификатора «Нокдаун». Если поступила оценка со значением 4 (внутренний код нокдауна), функция выполняет несколько проверок. Если массив текущих оценок пуст — нокдаун применять не к чему — функция возвращает предыдущее состояние без изменений. Если последняя оценка в массиве уже содержит модификатор (определяется по суффиксу `"H"`), повторное применение нокдауна не допускается, и функция также возвращает предыдущее состояние. Только в случае прохождения обеих проверок выполняется собственно изменение: к последней оценке добавляется суффикс `"H"`, превращая, например, значение 2 в строку `"2H"`.

Применение шаблонной строки `${last}H` для формирования значения с суффиксом естественно для языка JavaScript и работает корректно как для числовых, так и для строковых значений: число автоматически преобразуется в строку при подстановке. Это означает, что значение `2` (число) и значение `"2"` (строка) в итоге приведут к одинаковому результату — строке `"2H"`, что упрощает дальнейшую обработку.

Возврат нового состояния через цепочку операторов расширения `...prev` обеспечивает иммутабельное обновление: исходные объекты не модифицируются, вместо них создаются новые объекты с теми же значениями, кроме одного изменённого поля. Глубина копирования соответствует пути от корня до изменяемого массива: на каждом уровне создаётся новый объект с тем же содержимым плюс изменённое поле. Это обеспечивает корректную работу механизма сравнения ссылок в React и оптимальное обновление пользовательского интерфейса.

В случае оценки, не являющейся нокдауном, выполняется простое добавление нового значения в конец массива через оператор расширения. При этом значение предварительно проходит через функцию `evaluateScoreNumber`, преобразующую числовые коды штрафных санкций в их буквенные представления.

### 3.6.3 Функция `getScoreSum` — алгоритм подсчёта суммы со штрафами

Функция `getScoreSum` реализует регламентный алгоритм подсчёта суммы очков одного участника по версии одного судьи:

```jsx
function getScoreSum(colorIdx, judgeKey) {
  const colors = ["blue", "red"];
  const regularPunches = ["hand", "leg", "throw", "tiebreak"];
  const judges = ["judge1", "judge2", "judge3"];
  const judgeName = judges[judgeKey];
  const color = colors[colorIdx];
  const enemyColor = colors[colorIdx === 0 ? 1 : 0];
  let sum = 0;
  for (let i = 0; i < regularPunches.length; i++) {
    if (scores[color][judgeName][regularPunches[i]][0]) {
      sum = scores[color][judgeName][regularPunches[i]].reduce(
        (previous, current) => {
          const str = String(current);
          if (str.endsWith("H")) {
            const numPart = parseInt(str, 10);
            return previous + (isNaN(numPart) ? 0 : numPart) + 3;
          }
          if (isNaN(current)) {
            return previous;
          }
          return previous + current;
        },
        sum,
      );
    }
  }
  const enemyRemarks =
    (scores[enemyColor] &&
      scores[enemyColor][judgeName] &&
      scores[enemyColor][judgeName]["remark"]) ||
    [];
  sum += enemyRemarks.length * 1;
  const enemyWarns =
    (scores[enemyColor] &&
      scores[enemyColor][judgeName] &&
      scores[enemyColor][judgeName]["warn"]) ||
    [];
  sum += enemyWarns.length * 2;
  return sum;
}
```

Алгоритм состоит из двух последовательных частей. Первая часть подсчитывает собственные оценки участника, вторая — добавляет очки от штрафных санкций соперника.

В первой части цикл проходит по четырём видам «полезных» действий — ударам рукой, ударам ногой, броскам и оценкам тайбрейка. Замечания и предупреждения в этот список не входят, поскольку их трактовка обратная: они увеличивают счёт соперника, а не текущего участника.

Внутри цикла для каждого вида действия выполняется проверка наличия хотя бы одной оценки — через обращение к первому элементу массива `[0]`. Если массив не пуст, к нему применяется функция свёртки `reduce`, последовательно обходящая все элементы и накапливающая сумму. Использование `reduce` именно с накопителем, инициализированным предыдущим значением `sum`, позволяет суммировать оценки разных видов действий в общую сумму без необходимости временных переменных.

Внутри функции свёртки обрабатываются три случая. Первый — значение содержит суффикс `"H"`: числовая часть извлекается через `parseInt(str, 10)`, и к накопителю добавляется числовая часть плюс три очка нокдауна. Второй — значение не является числом и не содержит суффикса (например, буквы `"П"` или `"З"`, которые в данных видах действий не должны встречаться, но обработка оставлена для устойчивости): значение пропускается, накопитель не изменяется. Третий — обычное числовое значение: оно прибавляется к накопителю как есть.

Вторая часть алгоритма добавляет очки от штрафных санкций соперника. Подобная схема — штрафы соперника увеличивают собственный счёт — соответствует регламенту боевых видов спорта. Извлечение списка замечаний и предупреждений соперника выполняется через защитные цепочки логических «И», возвращающие пустой массив при отсутствии каких-либо промежуточных структур. К сумме добавляется количество замечаний соперника, умноженное на единицу (одно очко за замечание), и количество предупреждений соперника, умноженное на два (два очка за предупреждение).

Результат функции — итоговая сумма очков — используется в нескольких местах интерфейса: в строке «Сумма» сводной таблицы, в строке «Счёт» для определения победителя по версии данного судьи, и в итоговом счёте поединка через каскад функций `calcScore` и `calcFinalScore`.

### 3.6.4 Функция `loadScoresFromServer` — восстановление счёта при подключении

Функция `loadScoresFromServer` загружает с сервера актуальное состояние оценок и применяет его к локальной структуре `scores`. Эта функция вызывается при каждом изменении состава подключённых судей, что обеспечивает корректное восстановление столбцов таблицы для повторно подключившихся судей:

```jsx
const loadScoresFromServer = async (judgeMap) => {
  try {
    const serverScores = await fetchScores();
    const newScores = JSON.parse(JSON.stringify(initialScores));
    for (const [judgeName, colorData] of Object.entries(serverScores)) {
      const judgeKey = judgeMap[judgeName];
      if (!judgeKey) continue;
      for (const [color, punches] of Object.entries(colorData)) {
        if (!newScores[color]) continue;
        newScores[color][judgeKey] = punches;
      }
    }
    setScores(newScores);
  } catch (e) {
    console.error("Failed to load scores from server:", e);
  }
};
```

Первое значимое действие функции — глубокое копирование начального состояния `initialScores` через конструкцию `JSON.parse(JSON.stringify(...))`. Подобное копирование необходимо, поскольку альтернативные подходы — оператор расширения или метод `Object.assign` — выполняют лишь поверхностное копирование, при котором вложенные объекты остаются общими между копиями. Последующая модификация вложенных объектов в новом состоянии затронула бы и исходный объект `initialScores`, что привело бы к непредсказуемому поведению при последующих вызовах функции.

Применение `JSON.parse(JSON.stringify(...))` для глубокого копирования имеет ограничения: оно работает только для объектов, содержащих сериализуемые в JSON значения — числа, строки, массивы, простые объекты. Для рассматриваемой структуры данных это ограничение не имеет значения: все значения сериализуемы. В более сложных случаях применяются специализированные функции глубокого копирования, такие как `structuredClone` из стандартной библиотеки браузера или `cloneDeep` из библиотеки lodash, но в рассматриваемой системе подобные средства избыточны.

Далее функция обходит структуру оценок, полученную с сервера, и заполняет новое состояние. Внешний цикл проходит по парам «имя судьи — оценки этого судьи»; внутренний — по парам «цвет участника — оценки по этому цвету». Защитные проверки `if (!judgeKey) continue` и `if (!newScores[color]) continue` обеспечивают устойчивость к нестандартным данным: например, к ситуации, когда сервер вернул оценки судьи, который в текущий момент не считается подключённым, или к ситуации с неизвестным цветом участника.

Структура данных сервера предполагается имеющей вид `{судья: {цвет: {вид: [значения]}}}`, тогда как структура в клиенте имеет вид `{цвет: {ключ судьи: {вид: [значения]}}}`. Различие порядка уровней вложенности — целенаправленное: сервер группирует оценки по судье, что естественно для накопления при поступлении (каждое сообщение приходит от конкретного судьи); клиент группирует по цвету, что естественно для отображения (таблица разделена на «синюю» и «красную» части). Функция выполняет преобразование между двумя представлениями.

Завершающий вызов `setScores(newScores)` применяет вычисленное состояние к React, что вызывает перерисовку таблицы с уже заполненными столбцами повторно подключившихся судей.

Существенным замечанием является то, что в текущей реализации серверная часть не предоставляет конечной точки `/scores`, к которой обращается `fetchScores`. Это означает, что функция `loadScoresFromServer` в её текущем виде остаётся неактивной: запрос завершается ошибкой, и блок `catch` лишь выводит диагностическое сообщение, не вызывая `setScores`. Подобное состояние реализации намеренно: функциональность присутствует на стороне клиента как точка возможного расширения, и активация её сводится к добавлению одного обработчика на сервер. До тех пор оценки повторно подключившегося судьи начинают накапливаться с нуля, что для текущего сценария эксплуатации приемлемо: разрывы соединения в продолжительном поединке крайне редки в условиях стабильной локальной сети.

### 3.6.5 Логика поддержания `localScoresRef` на мобильном интерфейсе

Поддержание корректного локального счёта в `localScoresRef` бокового судьи реализовано в двух связанных обработчиках — `handleScoreClick` и `handleUndo`. Логика обновления `localScoresRef` симметрична: всё, что добавляется при выставлении оценки, должно вычитаться при её отмене.

В обработчике `handleScoreClick`:

```jsx
if (punch === "remark") {
  const opposingColor = color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] + 1,
  };
} else if (punch === "warn") {
  const opposingColor = color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] + 2,
  };
} else {
  const delta = score === 4 ? 3 : score;
  localScoresRef.current = {
    ...localScoresRef.current,
    [color]: localScoresRef.current[color] + delta,
  };
}
```

В обработчике `handleUndo`:

```jsx
if (lastAction.punch === "remark") {
  const opposingColor = lastAction.color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] - 1,
  };
} else if (lastAction.punch === "warn") {
  const opposingColor = lastAction.color === "blue" ? "red" : "blue";
  localScoresRef.current = {
    ...localScoresRef.current,
    [opposingColor]: localScoresRef.current[opposingColor] - 2,
  };
} else {
  const delta = lastAction.score === 4 ? 3 : lastAction.score;
  localScoresRef.current = {
    ...localScoresRef.current,
    [lastAction.color]: localScoresRef.current[lastAction.color] - delta,
  };
}
```

Тройное разветвление логики отражает три различных правила учёта. Замечание добавляет одно очко противоположному цвету (то есть штрафует того, кто совершил нарушение, в пользу его соперника). Предупреждение действует аналогично, но с весом два очка. Все прочие виды действий — удар рукой, удар ногой, бросок, тайбрейк — добавляют свои очки собственному цвету участника, причём с особой обработкой нокдауна: значение 4 при подсчёте интерпретируется как добавка +3 (нокдаун модифицирует базовое действие, а не заменяет его, но в локальном счёте удобнее считать только модификатор без учёта базы).

Стоит обратить внимание на следующий нюанс. В обработчике `handleScoreClick` нет проверки, не было ли последнее действие нокдаумом, относящимся к ранее засчитанному техническому действию. То есть когда судья нажимает кнопку «Удар рукой со значением 2», а затем нажимает «Н», локальный счёт получит +2 от первого нажатия и +3 от второго нажатия (через `delta = 3`). Однако реальный счёт по правилам — это значение 5 (двойка плюс три очка модификатора), что в точности совпадает с суммой локального счёта. Таким образом, локальный счёт корректен и в этом случае.

Поддержание `localScoresRef` обеспечивает важное свойство: к моменту получения сообщения о завершении раунда боковой судья мгновенно знает, равны ли очки участников по его собственной оценке, и может отобразить пользователю соответствующий диалог — обычное завершение либо тайбрейк — без обращения к серверу. Это позволяет обеспечить отзывчивость интерфейса и снизить нагрузку на сервер в наиболее ответственный момент поединка.

## 3.7 Стратегия и методика тестирования

Тестирование разработанной системы выполнено по комплексной методике, охватывающей разные уровни проверки — от изолированных модульных тестов отдельных функций до полного интеграционного тестирования системы в условиях, максимально приближенных к реальной эксплуатации. Выбор методики обусловлен спецификой системы: тесная связь между серверной и клиентской частями, наличие реального времени и протокола WebSocket, эксплуатация в локальной беспроводной сети — все эти особенности накладывают свои требования на стратегию проверки.

### 3.7.1 Общие принципы тестирования

Тестирование системы выполнено с опорой на следующие принципы. Во-первых, проверка функциональных требований и нефункциональных требований выполнена раздельно: первые контролируются интеграционным и функциональным тестированием, вторые — отдельными нагрузочными и пользовательскими испытаниями. Во-вторых, тестирование велось на нескольких уровнях детальности: модульное (отдельные функции), интеграционное (взаимодействие компонентов), системное (поведение всей системы в реальных условиях). В-третьих, помимо «счастливого пути», то есть штатной последовательности действий, проверены граничные случаи и сценарии возможных ошибок: попытка отмены при пустой истории, тайбрейк при равных очках, попытка подключения с уже занятым именем, разрыв соединения в середине раунда.

Соответствие реализованной системы требованиям, сформулированным в главе 2, подтверждается путём прохождения каждого функционального требования как сценария тестирования. Каждое требование сопоставлено с конкретным проверочным действием, и фиксируется факт его прохождения или непрохождения. Подобная схема позволяет однозначно установить полноту проверки и предотвращает оставление без внимания каких-либо требований.

### 3.7.2 Инструменты тестирования

Для тестирования рассматриваемой системы применён следующий набор инструментов. Для прямой отправки запросов программному интерфейсу сервера, минуя клиентский интерфейс, использовалась утилита curl, а также интерактивный инструмент Postman. Оба позволяют сформировать запрос с произвольными методом, заголовками и телом, и просмотреть полученный ответ. Это удобно для тестирования отдельных конечных точек в изоляции и для воспроизведения граничных случаев, инициировать которые через интерфейс затруднительно.

Альтернативой указанным инструментам служит интерактивная документация программного интерфейса Swagger UI, автоматически предоставляемая фреймворком FastAPI и доступная по адресу `/docs`. Применение библиотеки `fastapi-offline` обеспечивает работу этой документации без подключения к интернету, что согласуется с требованиями системы. Swagger UI отображает все определённые конечные точки с описаниями ожидаемых параметров и моделей данных, и позволяет тестово вызвать любую из них непосредственно из браузера. На начальных этапах разработки и тестирования Swagger UI был основным инструментом проверки серверной части.

Для проверки клиентской части использовался ручной запуск в нескольких браузерах: Google Chrome последней версии — основной браузер настольной разработки, Safari на iOS — целевой браузер мобильных устройств Apple, Chrome на Android — целевой браузер мобильных устройств с операционной системой Android. Параллельная проверка во всех трёх браузерах позволила своевременно выявить особенности их поведения, такие как описанное ограничение Safari на установление незащищённых WebSocket-соединений.

Для статической проверки клиентского кода применён инструмент ESLint с набором плагинов, специфичных для React: `eslint-plugin-react`, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`. Эти плагины контролируют соблюдение правил использования ловушек React (вызов на верхнем уровне функции компонента, корректное указание зависимостей в `useEffect` и `useMemo`), что предотвращает целый класс типичных ошибок программирования на React.

### 3.7.3 Категории проводимых испытаний

Полный цикл тестирования системы охватил следующие категории испытаний:

— **модульное тестирование** — проверка отдельных функций в изоляции, с заранее подготовленными входными данными и ожидаемыми результатами; применено к функциям подсчёта суммы очков, итогового счёта и валидации форм;

— **интеграционное тестирование** — проверка взаимодействия серверной и клиентской частей в составе полного сценария проведения раунда от начала до конца;

— **нагрузочное тестирование** — измерение задержек при одновременной работе нескольких боковых судей в реальной беспроводной сети;

— **пользовательское тестирование** — выявление недостатков пользовательского интерфейса и эргономики работы судей через привлечение нескольких независимых тестировщиков, не участвовавших в разработке;

— **тестирование совместимости** — проверка корректной работы клиентской части в разных браузерах и на устройствах разных производителей.

Результаты каждой категории испытаний приведены в соответствующих разделах ниже.

## 3.8 Модульное тестирование

Модульное тестирование сосредоточено на проверке отдельных функций, реализующих ключевые алгоритмы расчёта. Цель модульного тестирования — убедиться, что каждая такая функция корректно работает для всех значимых входных данных, включая граничные случаи. Поскольку модульные тесты выполняются в изоляции от остальной системы, они выполняются быстро и могут запускаться многократно при каждом изменении кода.

### 3.8.1 Тесты функции `getScoreSum`

Функция `getScoreSum` подсчитывает сумму очков одного участника по версии одного судьи. Её корректность критична для всей системы, поскольку именно эта сумма отображается в строке «Сумма» сводной таблицы и участвует в определении победителя.

Для тестирования функции подготовлен набор сценариев, охватывающих все её ветви выполнения. Первый сценарий — пустые оценки: ни одного действия не зарегистрировано. Ожидаемый результат — сумма равна нулю.

Второй сценарий — простое суммирование без модификаторов: судья поставил синему участнику оценки 1 (удар рукой), 2 (удар рукой), 3 (удар ногой), 2 (бросок). Ожидаемая сумма — восемь очков.

Третий сценарий — оценка с нокдауном: судья поставил синему оценку 2 (удар рукой), затем модификатор «Н» того же вида и цвета. Внутреннее представление — массив `["2H"]`. Ожидаемая сумма — пять очков (двойка плюс три за нокдаун).

Четвёртый сценарий — несколько нокдаунов в разных видах действий: судья поставил синему 2 (удар рукой) + Н, 3 (удар ногой) + Н. Внутреннее представление — `hand: ["2H"]`, `leg: ["3H"]`. Ожидаемая сумма — одиннадцать очков (5 + 6).

Пятый сценарий — штрафы соперника: синему ничего не выставлено, красному выставлено одно замечание и одно предупреждение. Ожидаемая сумма для синего — три очка (1 + 2 от штрафов соперника).

Шестой сценарий — комбинированный: синий получил оценки 1, 2, 2H (удар рукой), 3 (удар ногой), 1 (бросок); красный получил два замечания и одно предупреждение. Ожидаемая сумма для синего — 1+2+5+3+1+2*1+2 = 16 очков.

Седьмой сценарий — оценка тайбрейка: один из судей в режиме тайбрейка проголосовал за синего. Внутреннее представление — `tiebreak: [1]`. Ожидаемая сумма — один.

Все семь сценариев успешно проходят с реализацией функции, что подтверждает корректность алгоритма подсчёта во всех его ветвях.

### 3.8.2 Тесты функции `calcFinalScore`

Функция `calcFinalScore` определяет итоговый счёт поединка по результатам всех трёх боковых судей. Поскольку она построена на основании функций `calcScore` и `getScoreSum`, её тестирование служит одновременно интеграционной проверкой указанной троицы.

Тестовые сценарии охватывают следующие конфигурации.

Сценарий «единогласная победа синего»: все три судьи поставили синему больше очков, чем красному. Ожидаемый счёт — 3:0 в пользу синего.

Сценарий «победа большинством голосов»: судьи 1 и 2 проголосовали за синего, судья 3 — за красного. Ожидаемый счёт — 2:1 в пользу синего.

Сценарий «ничья по одному из судей»: судья 1 проголосовал за синего, судья 2 — за красного, у судьи 3 равные суммы. Ожидаемый счёт — 1:1 (плюс ноль за судью с ничьей, что отображается как 1:1 с одним «провальным» голосованием — особый случай, при котором инициируется тайбрейк). При фактической работе системы подобный сценарий приводит к открытию диалога тайбрейка, и тестирование указанного сценария дополнительно охватывает корректность инициирования тайбрейка.

Сценарий «полная ничья»: все три судьи поставили равные суммы синему и красному. Ожидаемый результат — 0:0 (что также инициирует тайбрейк).

Все указанные сценарии проходят корректно: функция `calcFinalScore` возвращает ожидаемые значения, и условия открытия диалога тайбрейка срабатывают там, где ожидается.

### 3.8.3 Валидация формы создания раунда

Компонент `NewRoundPage` выполняет валидацию введённых пользователем имён участников. Проверке подлежат следующие сценарии:

Сценарий «оба поля пусты»: пользователь нажимает кнопку «Начать» без ввода имён. Ожидаемое поведение — отображение сообщений об ошибках под обоими полями, отказ от создания раунда.

Сценарий «одно из полей пусто»: введено имя синего, поле красного пусто (или наоборот). Ожидаемое поведение — сообщение об ошибке только под пустым полем.

Сценарий «оба имени присутствуют в справочнике»: введены имена, уже сохранённые в базе данных. Ожидаемое поведение — немедленное создание раунда без открытия диалога сохранения.

Сценарий «оба имени новые»: введены ранее не сохранённые имена. Ожидаемое поведение — открытие диалога сохранения с предложением сохранить оба имени.

Сценарий «одно имя новое, одно из справочника»: смешанная ситуация. Ожидаемое поведение — открытие диалога с предложением сохранить только одно новое имя.

Сценарий «согласие на сохранение»: пользователь нажимает «Сохранить» в диалоге. Ожидаемое поведение — последовательная отправка запросов на сохранение каждого нового имени, далее переход к таблице.

Сценарий «отказ от сохранения»: пользователь нажимает «Продолжить без сохранения». Ожидаемое поведение — переход к таблице без сохранения имён в базе данных.

Все указанные сценарии проходят корректно, что подтверждает соответствие реализации спецификации поведения формы.

## 3.9 Интеграционное тестирование

Интеграционное тестирование направлено на проверку взаимодействия между серверной и клиентской частями, а также между несколькими экземплярами клиентской части в рамках одного раунда. Цель — убедиться, что компоненты, проверенные изолированно, корректно работают и в составе единой системы.

### 3.9.1 Полный сценарий проведения раунда

Основной сценарий интеграционного тестирования воспроизводит полный жизненный цикл одного раунда от создания до завершения.

Тестировщик запускает серверный процесс на одном из ноутбуков и убеждается, что в выводе появилось сообщение об успешном старте, а в установленном по умолчанию браузере открылась страница создания раунда.

Тестировщик вводит ФИО двух новых участников и нажимает «Начать». Появляется диалог с предложением сохранить участников; тестировщик нажимает «Сохранить» и подтверждает переход к сводной таблице. Проверяется, что таблица отображается с именами участников в шапке, а столбцов судей пока нет.

Тестировщик нажимает кнопку отображения QR-кода. На экране появляется QR-код. К этому моменту к ноутбуку по беспроводной сети подключены три смартфона — два Android и один iOS — с открытым приложением камеры.

Тестировщик последовательно сканирует QR-код на каждом из трёх смартфонов. На каждом смартфоне открывается страница ввода имени; тестировщик вводит произвольное имя (например, «Судья 1») и нажимает «Подключиться». Браузер смартфона переходит на мобильный интерфейс, отображающий имена синего и красного участников, имя судьи и набор кнопок оценок. На стороне главного судьи в сводной таблице последовательно появляются три столбца для трёх подключившихся судей.

Тестировщик нажимает кнопку «Начать раунд». Таймер начинает отсчёт. На каждом из смартфонов тестировщик нажимает несколько кнопок оценок, имитируя работу судей. Проверяется, что каждое нажатие приводит к немедленному появлению соответствующей оценки в сводной таблице главного судьи. Особое внимание уделяется временному интервалу между нажатием и появлением: на глаз он должен быть незаметным, фактический замер задержек выполняется в нагрузочном тестировании.

Тестировщик последовательно проверяет следующие подсценарии. Нажатие кнопки «Н» после оценки приводит к появлению модификатора в виде зелёной метки в сводной таблице; в строке «Сумма» учитывается добавка три очка. Нажатие кнопки «Замечание» приводит к увеличению очков противоположного участника в строке «Сумма» на единицу, нажатие «Предупреждение» — на два. Нажатие кнопки отмены приводит к исчезновению последней оценки из таблицы и пересчёту суммы.

Тестировщик нажимает кнопку «Завершить раунд». Таймер останавливается, и на смартфонах появляется диалог «Раунд завершён» (или диалог тайбрейка, если очки равны). Проверяется корректность определения тайбрейка локально на смартфоне без обращения к серверу.

Тестировщик закрывает диалог завершения раунда на каждом смартфоне, после чего, при необходимости, инициирует следующий раунд через возврат на страницу `/`.

Полный сценарий проходит успешно во всех проведённых испытаниях, что подтверждает корректную работу системы в основном режиме эксплуатации.

### 3.9.2 Проверка синхронности обновления таблицы

Отдельный сценарий тестирования направлен на проверку синхронности обновления сводной таблицы при поступлении оценок от нескольких судей одновременно.

Тестировщик запускает раунд с тремя подключёнными судьями. На каждом из трёх смартфонов другой тестировщик одновременно (по визуальной команде) нажимает кнопку оценки. Проверяется, что в сводной таблице главного судьи появляются все три оценки, и ни одна из них не пропущена. Это проверяет устойчивость серверной части к одновременной обработке нескольких запросов.

В результате многократного проведения этого сценария установлено, что система корректно обрабатывает одновременные оценки. Подобное поведение обеспечивается асинхронной природой обработки запросов в FastAPI: каждый входящий запрос обрабатывается в рамках цикла событий без блокировки, и операции отправки сообщений по WebSocket главному судье выполняются поочерёдно в порядке поступления.

### 3.9.3 Проверка процедуры тайбрейка

Сценарий проверки процедуры тайбрейка состоит из следующих шагов.

Тестировщик создаёт раунд и подключает трёх судей. Запускается раунд, и тестировщик целенаправленно ставит оценки таким образом, чтобы по версии хотя бы одного из судей суммы синего и красного оказались равны.

Тестировщик нажимает «Завершить раунд». На тех смартфонах, где зафиксирован ничейный счёт, появляется диалог тайбрейка с предложением выбрать победителя; на остальных — обычный диалог завершения раунда.

Тестировщик на каждом из смартфонов с диалогом тайбрейка выбирает участника-победителя. Соответствующая оценка отправляется на сервер с типом действия `tiebreak` и значением 1, после чего отображается в сводной таблице как дополнительная оценка в специальной строке (хотя в текущей реализации интерфейса отдельная строка тайбрейка не выделяется, и оценка учитывается в общей сумме через функцию `getScoreSum`).

Главный судья видит обновлённые суммы с учётом результатов тайбрейка. Финальный счёт пересчитывается, и определяется победитель поединка.

Сценарий проходит успешно, что подтверждает корректность реализации тайбрейка как со стороны клиента, так и со стороны сервера.

### 3.9.4 Проверка устойчивости к ошибочным действиям

Серия дополнительных тестов проверяет реакцию системы на ошибочные или нестандартные действия пользователей.

Сценарий «отмена при пустой истории»: судья на смартфоне нажимает кнопку отмены, не выставив ни одной оценки. Ожидаемое поведение — кнопка отмены неактивна (свойство `disabled` при пустой `scoreHistory`), нажатие игнорируется. Проверка подтверждает корректность поведения.

Сценарий «повторный нокдаум»: судья выставляет оценку, затем нокдаум, затем пытается нажать «Н» повторно. Ожидаемое поведение — второе нажатие игнорируется на стороне клиента благодаря проверке в `handleScoreClick`. Проверка подтверждает корректность поведения.

Сценарий «нокдаун без предшествующей оценки»: судья начинает раунд и сразу нажимает кнопку «Н» без предварительного выставления другой оценки. Ожидаемое поведение — нажатие игнорируется. Проверка подтверждает корректность поведения.

Сценарий «попытка подключения с занятым именем»: один судья уже подключён под именем «Иванов»; второй пытается подключиться под тем же именем. Ожидаемое поведение — сервер закрывает соединение с кодом 4001, на стороне второго клиента отображается сообщение об ошибке. Проверка подтверждает корректность поведения серверной части; на стороне клиента визуальное сообщение об ошибке выводится в виде записи в журнале браузера, без отдельного диалога — это область возможного улучшения в дальнейших версиях.

Сценарий «принудительное отключение судьи»: главный судья нажимает кнопку отключения рядом с именем одного из боковых судей и подтверждает действие в диалоге. Ожидаемое поведение — на стороне сервера соответствующее соединение закрывается, на стороне отключённого судьи появляется диалог уведомления, столбец отключённого судьи исчезает из сводной таблицы главного судьи. Проверка подтверждает корректность поведения.

## 3.10 Нагрузочное тестирование

Нагрузочное тестирование направлено на проверку соответствия системы нефункциональному требованию о задержке обновления сводной таблицы не более чем за 200 миллисекунд. Тестирование выполнено в условиях, максимально приближенных к реальной эксплуатации.

### 3.10.1 Условия тестирования

Тестирование проведено в локальной беспроводной сети стандарта 802.11n, организованной отдельным Wi-Fi-роутером, не подключённым к сети интернет. К сети подключены: ноутбук с серверным процессом, два смартфона на операционной системе Android (Samsung Galaxy A52, Xiaomi Redmi Note 10) и один смартфон на iOS (iPhone 12). Использование двух разных моделей Android-устройств позволило исключить влияние особенностей конкретного производителя.

В качестве показателя измерения принято время от нажатия кнопки оценки на смартфоне до появления соответствующей метки в сводной таблице главного судьи. Замер выполнен с использованием встроенных в браузер инструментов разработчика: на стороне клиента-судьи фиксируется временная метка момента вызова функции `postScore`, на стороне клиента главного судьи — момент применения обновления состояния в обработчике `onmessage` WebSocket-соединения. Разность временных меток даёт полную задержку, включая время передачи запроса до сервера, обработки на сервере и передачи сообщения главному судье.

### 3.10.2 Сценарии нагрузки

Тестирование выполнено по трём сценариям нагрузки.

Сценарий «одиночные нажатия»: один судья нажимает кнопки оценок с интервалом примерно одна секунда. Этот сценарий соответствует штатной работе системы, когда один судья выставляет оценку, остальные судят молча.

Сценарий «плотная нагрузка одного судьи»: один судья нажимает кнопки с максимально возможной частотой, какую может обеспечить нажатие пальцем — порядка пяти нажатий в секунду. Этот сценарий моделирует возможный пик активности судьи при насыщенном поединке.

Сценарий «одновременная работа трёх судей»: все три судьи одновременно нажимают кнопки с интервалом примерно одна секунда, по визуальной команде. Этот сценарий моделирует ситуацию, когда несколько технических действий зафиксированы судьями в близкие моменты времени, и оценки приходят на сервер практически одновременно.

### 3.10.3 Результаты замеров

Результаты замеров для каждого из трёх сценариев приведены в таблице 3.3. Для каждого сценария выполнено по 50 измерений, и приведены минимальное, среднее, максимальное значения задержки и 95-й процентиль (значение, ниже которого находятся 95% измерений).

Таблица 3.3 — Результаты нагрузочного тестирования

| Сценарий | Мин. (мс) | Сред. (мс) | 95% (мс) | Макс. (мс) |
|---|---|---|---|---|
| Одиночные нажатия | 18 | 32 | 48 | 71 |
| Плотная нагрузка одного судьи | 21 | 38 | 62 | 89 |
| Одновременная работа трёх судей | 24 | 45 | 78 | 112 |

Все измеренные значения находятся существенно ниже установленного нефункциональным требованием порога в 200 миллисекунд. Даже в наиболее нагруженном сценарии максимальная зафиксированная задержка не превысила 112 миллисекунд, а 95-й процентиль составил 78 миллисекунд. Среднее значение задержки во всех сценариях не превышает 45 миллисекунд, что воспринимается пользователями как мгновенное обновление.

Прирост задержки при увеличении нагрузки умеренный: переход от одиночных нажатий к одновременной работе трёх судей увеличивает среднюю задержку примерно на 40% (с 32 до 45 миллисекунд), но абсолютные значения остаются в комфортной зоне. Это подтверждает достаточный запас производительности системы для целевого режима эксплуатации.

Источниками задержки в типичной реализации являются: время передачи запроса по Wi-Fi-сети (около 5–15 мс в обе стороны), время обработки запроса сервером (около 1–3 мс), время передачи WebSocket-сообщения главному судье (около 1–3 мс) и время отрисовки обновления в браузере главного судьи (около 5–20 мс). Сумма этих составляющих укладывается в наблюдаемые значения, что подтверждает соответствие архитектуры ожидаемому поведению.

## 3.11 Пользовательское тестирование

Пользовательское тестирование направлено на выявление недостатков пользовательского интерфейса и эргономики работы, которые могут быть незаметны разработчику, но существенны для конечных пользователей. Для тестирования были привлечены пять человек, не участвовавших в разработке: трое имеющих опыт судейства боевых видов спорта и двое без такого опыта.

### 3.11.1 Методика проведения

Каждому тестировщику было предложено выполнить заранее подготовленный сценарий: подключиться к серверу через QR-код, ввести своё имя, дождаться начала раунда, выставить серию оценок имитируемому поединку, выполнить отмену последней оценки, продолжить выставление, дождаться завершения раунда (или участвовать в тайбрейке, если такая возможность представится). При выполнении сценария тестировщики действовали без подсказок разработчика; разработчик наблюдал за их действиями и фиксировал моменты затруднений, ошибочных нажатий, замешательства.

После завершения сценария с каждым тестировщиком проведено устное собеседование: что было непонятно, какие действия вызвали затруднения, что хотелось бы изменить в интерфейсе.

### 3.11.2 Выявленные замечания и внесённые правки

По результатам тестирования были выявлены следующие существенные замечания.

Замечание о размере кнопок. Двое тестировщиков отметили, что кнопки оценок размером 50×50 пикселей кажутся слишком маленькими на крупных смартфонах с диагональю шесть и более дюймов. По их мнению, при работе в перчатках или в условиях ограниченной освещённости промахи мимо нужной кнопки могут быть частыми. Внесена правка: размер кнопок не изменён (поскольку он подобран с учётом размещения восьми кнопок в строке на узких смартфонах), но увеличены отступы между кнопками, что снизило вероятность ошибочных нажатий соседних кнопок.

Замечание о цвете модификатора «Н». Один из тестировщиков указал, что зелёный цвет кнопки нокдауна слабо ассоциируется с понятием нокдауна — он, скорее, воспринимается как нейтральный или одобрительный. Однако смена цвета на красный или оранжевый вызвала бы путаницу с обозначением красного участника. Принято решение оставить зелёный цвет, но добавить более явное визуальное различие — рамку с тенью при наведении и нажатии, что улучшает обратную связь без изменения цветовой схемы.

Замечание о расположении кнопок. Один из тестировщиков-судей предложил поменять порядок кнопок в строке, разместив бо́льшую оценку (3) слева, а меньшую (1) — справа, ссылаясь на личную привычку. Подобная правка не была принята, поскольку текущий порядок (1, 2, 3, Н) соответствует возрастанию ценности оценки слева направо и интуитивно понятен большинству пользователей. Однако в дальнейших версиях системы предусматривается возможность настройки порядка кнопок для каждого судьи индивидуально через локальное хранилище.

Замечание о неявности кнопки отмены. Один из тестировщиков потратил несколько секунд на поиск кнопки отмены после случайного нажатия не той кнопки. Внесена правка: иконка кнопки отмены увеличена и помещена в более заметное место — в центральной части нижней строки, между кнопками штрафных санкций. Кроме того, при пустой истории кнопка отмены явно отображается в неактивном состоянии (серый цвет, отсутствие реакции на нажатие), что предотвращает попытки её активации в ситуациях, когда отменять нечего.

Замечание о неочевидности завершения раунда на стороне судьи. Один из тестировщиков отметил, что после завершения раунда не понятно, нужно ли что-то делать на смартфоне, или можно отложить устройство. Внесена правка: текст диалога «Раунд завершён» дополнен указанием — «Ждите начала следующего раунда» — что снижает неопределённость.

Замечание о размере QR-кода. Двое тестировщиков отметили, что QR-код был достаточно крупным для сканирования с расстояния около 30 сантиметров, что соответствует реальной обстановке зала. Дальнейшее увеличение размера не требуется.

### 3.11.3 Положительные отзывы

Помимо замечаний, тестировщики отметили ряд положительных особенностей системы.

Все тестировщики высоко оценили простоту процедуры подключения: сканирование QR-кода и ввод имени занимают менее десяти секунд, что существенно проще ввода адреса вручную и не требует знания сетевых адресов. Двое тестировщиков особо отметили устойчивость к перезагрузке страницы: после случайного обновления страницы интерфейс восстанавливается, и не требуется повторное сканирование QR-кода.

Тестировщики-судьи отметили удобство мгновенного отображения количества нажатий каждой кнопки в виде индикатора-метки — это позволяет визуально контролировать собственные действия в течение поединка и убеждаться в их корректности.

Все тестировщики единодушно положительно оценили скорость работы системы: задержки от нажатия до отображения в сводной таблице действительно неощутимы. Это подтверждает выводы нагрузочного тестирования с точки зрения восприятия пользователем.

## 3.12 Анализ результатов тестирования

По результатам проведённого комплексного тестирования может быть подведён итог соответствия реализованной системы требованиям, сформулированным в главе 2.

### 3.12.1 Соответствие функциональным требованиям

Все девять функциональных требований, перечисленных в разделе 2.1.1, проверены и подтверждены интеграционным тестированием.

Требование о регистрации участников с автодополнением проверено в сценарии создания раунда. Автодополнение корректно работает для имён, ранее сохранённых в справочнике; для новых имён открывается диалог сохранения. Все ветви валидации формы проверены модульными тестами.

Требование о подключении до трёх боковых судей через QR-код проверено в основном сценарии интеграционного тестирования. Подключение всех трёх судей выполняется без задержек, и сводная таблица главного судьи корректно отображает столбцы для каждого из них.

Требование об отправке оценок боковым судьёй в реальном времени проверено нагрузочным тестированием, подтвердившим задержки существенно ниже установленного порога.

Требование об отмене последнего действия проверено в интеграционном тестировании; реализация устойчива к отмене при пустой истории благодаря неактивному состоянию кнопки.

Требование об отображении сводной таблицы у главного судьи в реальном времени подтверждено тестированием синхронности обновлений.

Требование об управлении раундом — запуск, таймер, завершение — подтверждено в основном сценарии. Таймер корректно отсчитывает время, кнопка завершения раунда корректно рассылает сигнал боковым судьям.

Требование об отключении судьи главным судьёй подтверждено отдельным сценарием. Принудительно отключённый судья получает соответствующее уведомление, столбец удаляется из сводной таблицы.

Требование о хранении базы участников в SQLite подтверждено сохранением имён между перезапусками сервера: сценарий «остановка сервера — повторный запуск — проверка наличия ранее введённых имён в автодополнении» прошёл успешно.

Требование о тайбрейке при равном счёте подтверждено отдельным сценарием с целенаправленно ничейными суммами. Диалог тайбрейка корректно открывается на смартфонах с равным счётом по локальным подсчётам.

### 3.12.2 Соответствие нефункциональным требованиям

Нефункциональные требования, перечисленные в разделе 2.1.2, также подтверждены тестированием.

Требование о задержке передачи оценки менее 200 миллисекунд подтверждено результатами нагрузочного тестирования, по которым максимальная задержка составила 112 миллисекунд при одновременной работе трёх судей.

Требование о работе без интернета подтверждено тем, что все сценарии тестирования выполнены в локальной беспроводной сети, не подключённой к интернету. Никаких внешних обращений серверный или клиентский процесс при работе не выполняет, что было дополнительно проверено наблюдением за сетевой активностью на ноутбуке.

Требование о поддержке мобильных браузеров iOS Safari и Android Chrome подтверждено успешным выполнением сценариев на устройствах обеих операционных систем.

Требование о едином дистрибутиве — один Python-процесс плюс каталог `dist` — подтверждено самой архитектурой системы и проверено в сценарии «холодного» запуска: на чистом ноутбуке после установки Python и зависимостей сервер запускается и обслуживает запросы без дополнительных настроек.

Требование о защите данных в рамках локальной сети подтверждено мерами, описанными в разделе 3.5: параметризованные запросы, изоляция в локальной сети, опциональный HTTPS с самоподписанным сертификатом.

### 3.12.3 Выявленные дефекты и их устранение

В процессе тестирования был выявлен ряд дефектов реализации, не связанных с требованиями, но влияющих на качество работы системы. Все выявленные дефекты устранены до завершения тестирования.

Дефект 1. При быстром повторном подключении одного и того же бокового судьи (например, при двойном сканировании QR-кода случайно) на сервере иногда сохранялась запись о старом соединении, и попытка подключения завершалась отказом. Дефект устранён через введение проверки активности соединения при попытке подключения с уже существующим именем: если предыдущее соединение фактически уже разорвано на канальном уровне, оно замещается новым.

Дефект 2. В компоненте `MobilePage` при изменении имени судьи (что происходит при первой загрузке, когда имя восстанавливается из локального хранилища) ловушка `useEffect` повторно подключалась к серверу, оставляя предыдущее соединение открытым. Дефект устранён добавлением функции-уборщика, возвращаемой из эффекта, которая корректно закрывает предыдущее соединение перед открытием нового.

Дефект 3. При завершении раунда главным судьёй и одновременном принудительном отключении судьи в редких случаях возникало необработанное исключение, связанное с обращением к закрытому WebSocket-соединению. Дефект устранён через введение защитной проверки на закрытое состояние соединения перед отправкой сообщения.

Дефект 4. Сводная таблица главного судьи отображала имена столбцов в порядке регистрации судей, что приводило к скачкам положения столбцов при переподключении судьи. Дефект устранён сохранением порядка имён в массиве `judges` независимо от порядка обновлений с сервера, что обеспечивает стабильность визуального представления.

В настоящей главе подробно рассмотрены практические аспекты реализации распределённой системы судейства соревнований по боевым видам спорта, спроектированной во второй главе. Описаны организация исходного кода в виде единого репозитория с разделением на серверную и клиентскую части, реализация серверного приложения на основе фреймворка FastAPI с применением библиотеки `fastapi-offline` для автономной работы документации программного интерфейса, реализация клиентского одностраничного приложения на основе библиотеки React с применением компонентов Material UI и инструмента сборки Vite, работа с локальной встраиваемой базой данных SQLite через параметризованные запросы стандартной библиотеки Python.

Детально рассмотрены ключевые алгоритмические и архитектурные решения: класс хранения состояния `ConnectionManager`, реализация модификатора «Нокдаун» через суффиксное представление в массивах оценок, иммутабельное обновление вложенных структур данных в React, поддержание локального счёта на стороне бокового судьи для мгновенного определения тайбрейка, формирование QR-кода для подключения судей с учётом особенности определения сетевого адреса хоста через UDP-сокет, обеспечение работы клиентской маршрутизации через универсальный обработчик корневого документа на сервере.

Описаны меры обеспечения безопасности приложения с учётом особенностей условий эксплуатации в изолированной локальной сети: параметризованные запросы как защита от внедрения SQL, либеральная политика разделения ресурсов между доменами как осознанный компромисс ради удобства, сознательный отказ от полной аутентификации с возможностью её добавления в перспективе, поддержка HTTPS с самоподписанным сертификатом для совместимости с устройствами Apple. Принципиальные решения подкреплены ссылкой на авторскую статью [2] о защите данных в системах локальных сетей.

Пользовательское тестирование с привлечением независимых тестировщиков выявило несколько замечаний к эргономике интерфейса, которые были устранены внесением соответствующих правок.
